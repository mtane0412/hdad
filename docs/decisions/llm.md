# LLMの呼び先・使用状況・モデルの選択

## 呼び先の決め方（`worker/llm.ts`）

LLMを呼ぶのは4か所（`LLM_USAGES`: `aiChat`（トリガーの動作のチャットの文面）・`sideSuper`・`viewerSummary`・`streamSummary`）だが、**呼び先を決めるのは `worker/llm.ts` だけ**である。呼び出し側はモデル名ではなく**どこで使うか**を指名し、どの提供元（Cloudflare の Workers AI・OpenRouter）のどのモデルを使うかは保存された設定（`worker/llm-config.ts`。KVのキーは `llm-settings`）が決める。

**提供元は箇所ごとに選べる**（あらすじだけ賢いモデルに任せ、発言ごとに呼ばれるチャットの文面は無料枠の Workers AI に留める、といった使い分けをするためである。1回の cron の中で両方の提供元を呼ぶこともある）。

**モデル名は提供元ごとに別に持つ**（`models['workers-ai']`・`models.openrouter`）。`@cf/…` と `提供者/モデル` で書き方がまったく違うので、1組にすると切り替えるたびに両方を書き直すことになり、戻したときに前の名前も消える。使っていない提供元のモデル名も検証するのは、保存時にしか検証しない約束（`speech-config.ts` と同じ）のもとで空のまま保存できると、切り替えた瞬間に初めて呼び出しが失敗するためである。

保存されている形が古ければ（用途を `chat`・`summary` の2つにまとめていたころの形）`loadLlmSettings` が読み替えずにエラーにし、直し方（KVのキーを消して保存し直す）を文面に出す（`loadAlertConfig` と同じ考え方である）。応答の形の読み分け（従来は `response`、新しいモデルと OpenRouter は OpenAI 互換の `choices`）は `llm.ts` の `readResponse` 1か所に持つ。

設定の読み出しは最初に使われたときの1回だけで、覚えておく（チャットの発言のたびに通る道なので、一度も使わなければKVを読まない。`alert-state.ts` の「要らなければ読まない」と同じ考え方である）。

**失敗は黙って別の提供元へ落とさない**（Fail-Fast）。OpenRouter を選んでいるのに鍵（シークレット `OPENROUTER_API_KEY`）が無い・残高が足りない・非2xxが返った、はすべて投げて呼び出し側が失敗として記録する。黙って Workers AI に落ちると、配信者は課金したモデルが使われていないことに気づけない。

鍵は設定ではなくシークレットなので、KVにも管理画面の応答にも含めず、`GET /api/admin/llm` は「設定されているか」（`apiKeyConfigured`）だけを添える。`.dev.vars.example` にはコメントとして書く（Deploy to Cloudflare ボタンの必須の入力欄に出さないため。任意のシークレットだからである）。

テストの代役は2種類ある（`worker/fake-ai.ts` の `createFakeWorkersAi` はバインディングの代役で Env を組み立てる経路のテストが使い、`createFakeAi` は用途を指名して呼ぶ側の代役で材料を組み立てる関数のテストが使う）。

管理画面は `/llm/`（`src/llm/llm-page.tsx`。Workerの呼び出しは `src/llm/api.ts` に分けてテストする）で、箇所ごとに提供元とモデルの選択欄を1組ずつ並べる（箇所の日本語の名前と説明は `USAGE_LABELS` が持ち直す）。鍵が無いのに OpenRouter を選んでいる箇所があれば、その箇所の名前を挙げて保存前に知らせる。

## 使用状況を自前で数える

**LLMの使用状況は自前で数える**（`worker/llm-usage-store.ts`。D1の `llm_usage`。`migrations/0014_llm_usage.sql`）。記録するのは `llm.ts` だけで、ここがLLMへの唯一の入口なので4か所を取りこぼさずに数えられる。

**1回の呼び出しで1行を足さず、「日 × 箇所 × 提供元 × モデル」の1行へ足し込む**（チャットの文面は発言ごとに呼ばれるので、1呼び出し1行では行が際限なく増える。`viewers` が「発言ではなく人を貯める」のと同じ考え方である）。モデルを主キーに含めるのは、日の途中でモデルを変えたときに前のモデルのぶんと混ざらないようにするためである。**日の区切りはUTC**（Workers AI の無料枠がUTCの日で切り替わるため。配信者の時間帯に合わせると無料枠の区切りとずれる）。

失敗（無料枠切れ・残高不足・推論モデルで本文が空）も `failures` として数える（`collection_failures` には最新の50件しか残らないので、「今日は何回失敗したか」はここから読む）。トークン数は応答の `usage` から読み（`llm.ts` の `readUsage`。返さないモデルでは 0 のまま回数だけ増える）、実費は OpenRouter だけが返す（`usage: { include: true }` を付けて頼む）。

**Workers AI の残り無料枠（Neurons）は出せない**（GraphQLの分析APIがアカウント単位のAPIトークンを要求するため。`llm-models.ts` がモデルの一覧を手で持つのと同じ理由で、そのために強い鍵を増やさない）。

**使用状況の記録に失敗しても、作れた文面はそのまま返す**（`llm.ts` の `recordUsage`）。モニターのための記録のために配信中のチャットの文面やあらすじが出なくなるのは本末転倒である。この1か所だけは Fail-Fast の例外で、黙って捨てずに `llm-usage-record-failed` として記録し、その記録まで失敗したらあきらめる。

OpenRouter の残高は `worker/llm-credits.ts` が公開API（`/api/v1/credits`）から読み、**KVに貯めない**（読むのは画面を開いたときだけなので問い合わせは増えず、貯めると課金した直後に古い残高を見せる）。

経路は `GET /api/admin/llm/usage`（日ごとの行をそのまま返す。まとめ方は画面が持つ）と `GET /api/admin/llm/credits`（鍵が無ければ400）である。提供元ごとに分けてあるのは、片方の失敗をもう片方に波及させないためである。

画面では「今日」「直近7日」へのまとめを `src/llm/usage.ts` の `summarizeLlmUsage` が作り（`src/stats/summary.ts` と同じ分け方）、使用状況・残高のどちらを読めなくても**設定の画面はそのまま出して理由だけを添える**（表示のために提供元やモデルを直せなくならないようにする）。残高は鍵が設定されているときだけ読む。

## モデルは入力させず選ばせる

**モデルは入力させず選ばせる**（打ち間違いに気づくのが「配信中に文面が作られなかったとき」になるため）。候補は `worker/llm-models.ts` が返し、経路は `GET /api/admin/llm/models?provider=…`（`requireAdmin`）である。

Workers AI の候補はこのファイルが手で持つ（Cloudflareのモデル一覧のAPIはアカウント単位のAPIトークンを要求し、このWorkerはそれを持たない。モデルを選ぶだけのために強い鍵を増やさない。増えたらここに足す＝素材の `registry.ts` と同じ扱いである）。載せるのは文面づくりに向く汎用のモデルだけで、LoRAの土台・コード専用・翻訳専用と、**考えた過程を書き出す推論モデルは載せない**（短い文言や2行のテロップに思考の文が混ざり、長さの検分に落ちる）。

OpenRouter の候補は公開API（`https://openrouter.ai/api/v1/models`。鍵は要らない）から取り、画像だけを返すモデルを外して名前順に並べ、KVに1時間貯める（`chat-routes.ts` と同じ考え方である）。**提供元ごとに分けて読む**（使っていない提供元の一覧を取りに行かず、片方の失敗をもう片方の選択欄に波及させないためである）。

取れなかったときは空の一覧を返さずに投げ、画面は理由を出したうえで保存済みの値だけを選択欄に残す（空の選択欄では「選べるモデルが無い」のか「一覧を取れていない」のか見分けられない。保存済みの値が候補に無いときもそれを足して残し、画面を開いただけで別のモデルへ移らないようにする）。

**検証では Workers AI のモデル名だけを候補と照らし合わせる**（`llm-config.ts`）。OpenRouter 側を照らし合わせないのは、一覧が遠隔で日々変わり、保存のたびの問い合わせが失敗すると正しいモデル名まで拒んでしまうためである（呼び出しのときに OpenRouter が答える）。

**OpenRouter へは推論を切って送る**（`llm.ts` が `reasoning: { enabled: false }` を付ける）。このツールが送る上限は箇所ごとに100〜400トークンと小さく、推論モデルではそれを思考トークンが使い切って、`content` が `null` のまま `finish_reason` が `length` で返る（`openai/gpt-6-luna` をあらすじに選んだ配信で、5分おきの収集がすべてこれで失敗した）。Workers AI の候補には推論モデルを載せないので済んでいたが、OpenRouter の候補は遠隔の一覧をそのまま出すため選べてしまう。推論を持たないモデルでは無視される項目なので、モデルによる場合分けは持たない。

それでも上限で切れたときは、「応答の形が違う」と混ぜずに推論モデルの可能性を挙げた文面で投げる（`readResponse`。原因がモデルの選択にあることに気づけるようにするためである）。

Twitch以外への通信が要る経路のために `Context.fetch` を足してある（Twitchへの通信は `twitch` が持つ）。

## 判定には Jev を使う（`worker/jev.ts`）

「配信者の発話が、そのコメントへの反応か」のように、文面ではなく**判定**が欲しい箇所には、TypeSafe の Jev を OpenRouter から使う（issue #145）。Jev は材料（`state`）と質問を渡すと、質問ごとに型の決まった答え（Noul は yes の確率・Choice は選ばれた選択肢・Score は段階の位置）を返す。文面を作らせて読み解く形にしないのは、答えの形が崩れる心配が無く、確率をしきい値と比べて使えるためである。

**入口は `llm.ts` とは別に持つ。** `llm.ts` は `chat/completions` で文面（文字列）を返す作りで、Jev は別の API（Decisions API）で型の決まった答えを返すため、同じ入口に押し込むと両方の場合分けが増える。呼び出し側がモデル名ではなく使う箇所（`JEV_USAGES`）を指名する形は LLM と揃えた。

**モデルは版を固定し（`typesafe/jev-1.13`）、設定で選ばせない。** 答えの確率をしきい値と比べて使うので、しきい値は版ごとに観察して決めるものである。`jev-latest` のように中身が黙って変わる名前だと、しきい値が知らぬ間に合わなくなる。選べる候補が1つしかないので、`/llm/` の箇所ごとの選択にも入れない。

**答えが欠けている・型が違う・確率が 0〜1 に収まらない場合は投げる。** 欠けた答えを「いいえ」として扱うと、判定されなかったものが判定されたように見える（`docs/principles.md` の4）。

**使用状況は LLM と同じ `llm_usage` へ足し込む**（箇所の名前が重ならないので表を分けない）。記録に失敗しても判定の結果は返すのも `llm.ts` と同じである。

**エンドポイントは `https://openrouter.ai/api/alpha/decisions` である。** OpenRouter の API リファレンスに載っている `/api/v1/api/alpha/decisions` は 404 を返す（実際に呼んで確かめた）。応答は約250msで、1回およそ1,000トークン・$0.00004 だった（入力 $0.042/100万トークン、出力は無料）。
