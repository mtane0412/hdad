# 市町村紹介

レイドを受けたとき、レイド元の紹介の代わりにランダムな市区町村の紹介を流すネタ機能を3段階で作る（issue #227 一覧と地図・#228 紹介文をその場で作る API・#229 トリガーの動作と素材）。ここには3段階すべての判断を書く。

## 一覧も地図も国土数値情報の N03 1本から作る

当初は geolonia の `japanese-addresses`（`api/ja.json`）から一覧を取り、地図の N03 と名前で突き合わせて検証する計画だった。調べると、`ja.json` は 2023-11-15 から更新が止まっており、リポジトリの README にも「現在更新されておりません」とあった（後継は `japanese-addresses-v2`）。一方、N03 は都道府県・郡・市区町村名・行政区域コードを属性に持つので、一覧も地図も同じ版から作れる。同じ源から作れば名前の突き合わせ（表記ゆれ・合併の反映時期のずれ）がそもそも起きないので、N03 に一本化した。一覧と地図の食い違いは、片方だけ作り直したり手で直したりしたときにしか起きないので、`src/town-tour/towns.test.ts` がコードの1対1で検出する。

使う版は令和8年（2026年）1月1日時点の全国版（`N03-20260101`）。

## 一覧と地図はリポジトリに同梱する

引くたびに外部へ取りに行くと、相手の都合で配信中に止まる（方針7・8）。作り直す手順は `scripts/town-tour/build-data.ts` として残す。地図は静的アセット（`public/town-tour/japan.topo.json`）に置き、OBSに載せるページから読む。一覧（`src/town-tour/towns.json`）は Worker（#228 の紹介文づくり）と合成ページの両方が読むので `src/` に置く。地図の形を Worker に持ち込むと Worker の容量を食うので、一覧と地図は別のファイルにした。

## 政令市の区は市にまとめ、東京23区は1区ずつ残す

政令市の区は行政区で、Wikipedia の記事も紹介の単位としても市のほうが自然なので、市にまとめる。N03 は政令市を区の単位でしか持たず、市そのもののコードが無い。区のコードから市のコードは機械的に導けない（札幌市清田区は 01110 だが札幌市は 01100、浜松市は 2024年の再編で区が 22138〜 になったが市は 22130）ので、20市の表で持ち、表に無い政令市が現れたらエラーで止める。

東京23区は特別区で、市と同格の地方公共団体であり、市に属していないので1区ずつ残す。

## 北方領土の6村は入れ、所属未定地は外す

北方領土の6村（色丹村・泊村・留夜別村・留別村・紗那村・蘂取村）は N03 に形とコードがあり、配信者の判断で引く対象に入れた。北海道の泊村は古宇郡と国後郡の2つがあり名前だけでは見分けられないので、一覧に郡名（`county`）を持たせ、識別はコードで行う。

N03 の「所属未定地」（埋立地などで、どの市町村にも属さない区域。7都府県にある）は紹介できないので、一覧からも地図からも外す。

## 地図は頂点の3%を残して簡略化する

N03 の全国版の shp は約260MB ある。Workers の静的アセットは1ファイル25MiBまでなので、mapshaper で頂点を減らし TopoJSON（量子化 1e5）にした。1%（約2.0MB）と3%（約3.8MB、gzip で約1MB）を、いちばん小さい村の富山県舟橋村（約3.5km²）に寄って比べると、1%は数個の頂点の多角形になって形が分からず、3%は形が分かったので3%にした。

OBSに載せるページには外部のタイルも MapLibre も持ち込まず、この TopoJSON を Canvas 2D で描く（#229）。重心やズームの範囲もこの形から計算できるので、緯度経度の一覧は持たない。

## 紹介は貯めずに、呼ばれるたびに作る（#228）

当初は、紹介を1日1件ずつ cron で作って D1 に貯め、レイドのときは1件取り出すだけにする計画だった（待ち時間・配信中の失敗・方針8「トリガーのたびにLLMを呼ばない」のため）。Claude Code で事前に全件を作ってリポジトリに同梱する案も検討したが、全件で数MBあり、Worker に同梱すると Free プランのサイズ上限（圧縮後 3MB）に当たる。静的アセットや D1 に置くと、作り直しの仕組みと Wikipedia の更新への追従が別に要る。

一方、待ち時間は合成ページの素材（#229）が日本地図からズームする演出のあいだに吸収でき、実測でも1件2〜5秒だった。レイドは1回の配信で多くても数回なので、無料枠への影響も小さい。そこで配信者の判断で、呼ばれるたびに作る形にした。方針8の例外にあたる。

Twitch の Webhook の中では作らない。Webhook には早く2xxを返す必要があり、続きを預ける `waitUntil` は Free プランで30秒で打ち切られる。LLM の待ち時間の上限（`worker/llm.ts` の `LLM_TIMEOUT_MS`、60秒）がこれに収まらない。合成ページが `GET /api/overlay/town-tour` を呼べば、応答を待つ時間に Webhook の制約が掛からない。

## 記事は名前で検索せず、全国地方公共団体コードで Wikidata から引く（#228）

市町村の名前は一意でない（府中市は東京都と広島県に、泊村は北海道に2つある）。Wikidata の項目は全国地方公共団体コード（P429）を持つので、一覧のコードに検査数字を付けた6桁（総務省の規則。`(11 − 重み付きの和 mod 11) mod 10`）で項目を引き、その日本語版の記事を採る。1,747件のうち1,746件は1つの記事に決まった。残る読谷村（473243）は、読谷村文化センターの項目にも同じコードが付いていた（Wikidata の誤り）。

この対応づけは実行時ではなく `scripts/town-tour/build-articles.ts` で行い、`src/town-tour/articles.json` として同梱する。実行時の外部呼び出しを1回減らせるうえ、曖昧な対応を生成の時点で止めて人が確かめられる。曖昧なものを項目の種類（P31）で選ぶ規則も考えたが、市の項目でも「日本の市」が付いていないものがあり、別の誤りを招くので、見つかった分だけを表（`PREFERRED_ITEMS`）で指名する。

検索 API（`haswbstatement:P429=…`）を1件ずつ呼ぶと、数百件で制限にかかった。生成には SPARQL の1回の問い合わせを使う。

## 材料は記事の節を見出しの名前で拾い、LLM には項目を埋めさせるだけにする（#228）

REST の summary は冒頭の1文しか返さないので、TextExtracts の見出し付きプレーンテキストで本文を取る。長い記事（府中市 (広島県)）でも応答は約70KBで、CPU 10ms の中で解析できる。全文は LLM に渡さず、見出しの名前で系統（冒頭と概要・地理・名前の由来・歴史・名物・そのほかの話題）ごとに拾い、系統ごとに1,000文字で切る。

見出しの名前は記事ごとに違う（名物の節は「名物」「名品」「特産品」、出身者の節は「著名な出身者」「出身有名人」）。名前の型は実際の記事で確かめて決めた。「祭」だけだと「葬祭場」に、「文化」だけだと「文化施設」の一覧に当たる。また「町名一覧」「大字」の節は、名前が並ぶだけで系統の長さの枠を埋めてしまう。そのため、語を長くとり、一覧の節は拾わない。子の見出しが親と別の系統に当てはまれば子の系統に入れる（府中市 (広島県) では「名物」が「名所・旧跡・観光スポット」の下にある）。

LLM だけに書かせると、人口や名産をもっともらしく捏造する。そこで、材料にある内容で項目を埋めさせるだけにし、材料に無い項目は空のまま返させる（方針6・11）。試した5件（府中市 (広島県)・檜枝岐村・北島町・葛飾区・泊村 (北海道根室振興局)）では、出てきた事実はどれも記事の本文にあった。既定のモデルは、あらすじと同じ大きいもの（`llama-3.3-70b`）にした。

## 項目は「知らない自治体について、へえとなるか」で選ぶ（#228）

当初の案は、名前と読み・人口と面積・市町村の木と花・名産・出身の有名人・ひとことの6項目だった。配信者の判断で、リスナーがまったく知らない自治体の知識が増える面白さがあるかどうかで選び直した。市町村の木や花は「ふーん」で終わるが、歴史には興味が湧く。

採った項目は次の5つ（当時の `worker/town-tour.ts` の `TOWN_TOUR_ITEMS`。#249 で大見出しの形に変えた）である。
- どこにあるか（人口は規模感として触れる程度）
- 名前の由来
- 歴史のひとこま
- 名物・名産
- 意外な一面

出身の有名人は記事に載っていないことが多い（試した5件のうち2件だけ）ので、独立した項目にせず、「意外な一面」の材料に含める。

## 固定の5項目をやめ、一本の切り口を大見出しに立てる（#249）

#228 の固定5項目を1項目6秒ずつ同じ重さで流す形は、百科事典の朗読に近く、コーナーとして弱かった。そこで、テレビのコーナーのように、その町ならではの一本の切り口を大見出し（「この町、実は○○」の○○）に立て、それを支える項目を1〜3つと、配信者への振りを1つ LLM に作らせる形に変えた（`worker/town-tour.ts` の `TownTour`）。項目の並びは「ゆさぶり → オチ」で、最後の項目をオチとして扱う。項目の見出しは固定の5つから選ばせず、LLM に短く付けさせる。

決めたことは次のとおり（いずれも配信者の判断。2026-10-05）。

- 大見出しを立てられない（材料が薄い）町は、大見出しを空にして項目と振りだけを流す。旧来の5項目へ戻す案は2つの形を持ち続けることになり、失敗（502）にする案はレイドで何も流れない町を作るので採らなかった。大見出しが空の形は LLM に明示的に許した形であり、黙って別の形に落とすものではない（方針4）。項目が1つも無い・振りが空の応答は、従来どおり失敗にする
- 効果音の枠は増やさず、「項目ごと」を大見出しと各項目の出だしで、「締め」を振りの出だしで鳴らす。振りが「配信者の番」の合図になる。枠を増やすと保存済みの音の設定が古い形になり、作り直しが要るためでもある
- 場面の長さは、大見出し7秒（はじめの1.5秒は「この町、実は…」だけで溜める）・ゆさぶり6秒・オチ5秒・振り6秒、出典だけを残す時間は4秒から2秒に縮めた。大見出しと3項目で約36.5秒、2項目で約30.5秒になり、これまでの30〜40秒を超えない

プロンプトでは、#228 で項目から外した人口・面積の数字や人口の増減を使わせないようにした。最初の試行では5件中3件の大見出しが人口・面積の数字（「人口減少が進む町」など）になったためである。「日本一」「県内一」のような順位は使わせる（檜枝岐村の「日本一人口密度の低い村」）。また、「です・ます」で終えるとだけ指示すると「指定されているです」のような文が出たので、自然な文の例を添えた。大見出しで市町村を指す語は名前の最後の字（市・町・村・区）にそろえさせた（檜枝岐村が「町」と呼ばれたため）。

既定のモデル（`llama-3.3-70b`）で9市町村・のべ14件を試した（府中市 (広島県)・檜枝岐村・北島町・葛飾区・泊村 (北海道根室振興局)・出雲崎町・三種町・うきは市）。大見出し・項目・振りに出てきた事実は、どれも材料の本文にあった。ただし、項目の見出しと中身のずれ（檜枝岐村の「星」姓の話に「名前の由来」と付けた）や、「である」調の文が混ざることは残っている。

## 人口と面積は公的な統計から同梱し、いま見ている人数で「挑む」文にする（#250）

「人口3,200人」と出しても大きさは伝わらないので、この配信でしか作れない比較として、いま見ている人数と人口を比べて見せる。決めたことは次のとおり（いずれも配信者の判断。2026-10-05）。

- 人口と面積は LLM に記事から読ませない（数字を捏造・取り違えるため。方針11）。総務省の住民基本台帳人口（令和8年1月1日現在）と国土地理院の面積調（令和8年7月1日時点）を `scripts/town-tour/build-stats.ts` で `src/town-tour/stats.json` にし、同梱する。issue では一覧（`towns.json`）に入れる案だったが、一覧は N03 の shp が無いと作り直せないので、記事名の表（`articles.json`）と同じく一覧のコードをキーにした別の表にした。人口と面積は公表の周期が N03 と違い、単独で作り直せるほうがよい
- 突き合わせはコード（人口は6桁の団体コードの先頭5桁、面積は0の落ちた標準地域コードを0埋め）で行い、名前は取り違えの検出にだけ使う。名前の揺れは規則で吸収せず、見つかった分だけを表（`POPULATION_NAME_VARIANTS`）で持つ。令和8年の表では須恵町（人口の表は「須惠町」）だけだった
- 北方領土の6村は、人口の表に0人の行がある村も含めて人口を null にする。0人と「記録が無い」は違う（方針6）。画面では「人口の記録なし（北方領土）」と出し、挑む文を出さない
- 比較を出す場面は、ズームの着地（形の塗りに合わせる）で、冒頭の一文の帯のすぐ下に添え、最後まで残す。項目の1つにする案は、紹介が6秒伸び、場面の長さと音の時刻（`sound-cues.ts`）の追随が要るので採らなかった
- 面積の物差しは山手線の内側（約63km²）にした。市町村の面積は約3.5km²（舟橋村）〜約2,178km²（高山市）の幅があり、東京ドーム（約4.7ha）では大きい市が「4万6千個分」になって大きさが伝わらない。山手線の内側なら0.06〜35個分に収まる。約63km²は一般に言われる概算で、一次資料は見つけられていない
- 人口との比べ方は、issue の例の「レイドの人数＝人口の1.5%」のような割合をやめ、「いま見ている人数で住民全員に挑むと、ひとり何人倒せば制圧できるか」（端数は切り上げ）にした。割合だと、レイドや同接が少ないときに「0.0001%」のように小ささが目立ち、レイドしてくれた人や配信者が気にするおそれがあるため。挑む文なら人数の多少にかかわらず遊びとして読めるので、人数が少ないときに隠す下限は設けない
- 挑む人数は、レイドでは最後に記録した同接にレイドの人数を足した数（レイドで来た人もいま見ている人に入るため）、キーワードと試し再生では最後に記録した同接にする。同接は cron が5分おきに `viewer_samples` に残す値で、配信中の配信に記録が無ければ（配信中でなければ）キーワードと試し再生では挑む文を出さない。Webhook の中で Twitch の API を呼ばないのは、レイドの通知のたびに外への呼び出しを増やさないためである
- 文は合成ページのコード（`src/town-tour/scale.ts`）が組み立て、Worker は人口・面積・見ている人数の数だけを押し出す。LLM のプロンプトで人口・面積の数字を使わせない約束（#249）はそのまま残す

## 冒頭を都道府県当てクイズにし、判定は Worker と D1 で行う（#251）

レイドで来た人は最初の10秒は何が起きているか分からないので、チャットに書き込める問いを冒頭に置いた。決めたことは次のとおり（配信者の判断。2026-10-05）。

- 回答を待つのは15秒。4秒ごとにヒントを1つ足す（3つ）。1件は最長で15秒伸びる（時間切れのとき）
- レイドだけでなくキーワード（`!darts`）でもクイズにする。ダーツを投げた人もチャットにいるので成り立ち、きっかけで流れを分けずに済む。試し再生も同じに流す（Twitch の `channel.chat.message` は配信外でも届くので、配信していなくても書き込んで確かめられる）。管理画面のプレビューは Worker につながないので、いつも時間切れになる
- 市町村の名前は出し、都道府県だけを伏せる。「青森市」のように名前で答えが分かる町もあるが、それも当たりの楽しさとする。伏せる一文（`quizHeadline`）は Worker が冒頭の一文と同じ組み立てで、都道府県と郡を除いて作る（郡の名前も手がかりになるため）
- 正解者には名前を出すだけにする。チャンネルポイントを渡す API は無く、仕組みを作るのは範囲が大きい
- ヒントは地図の形から機械的に作れるものに限る（issue の条件）。「海に面しているか」は、どの市町村とも分け合わない弧を見るだけだと、県境の未定地や湖の縁を海と取り違える（N03 では群馬・長野の県境などに市町村に属さない土地がある。試すと嬬恋村や秩父市など23市町村を海沿いと誤った）。そこで分け合わない弧を輪につなぎ、市町村の外周と同じ向きの輪（陸地全体の外周＝海岸線）だけを海岸と見なし、逆向きの輪（陸地の中の穴）を外した（`src/town-tour/topo.ts` の `decodeTownBorders`）。地方は都道府県の番号から八地方区分で、隣り合う都道府県は境界の弧を分け合う市町村の都道府県から求める
- 1つ目のヒントは、はじめ「出題した市町村が海に面しているか」にしたが、答えは都道府県で、残りの2つ（地方・隣り合う都道府県）も都道府県についてのヒントなので、都道府県のことと読まれた（宮崎県の内陸の町に「海に面していません」と出て、宮崎県は海に面していると混乱した）。そこで、ヒントはどれも答えの都道府県についてのものにし、1つ目を「その都道府県の市町村の数」に替えた。都道府県が海に面しているかは、内陸の県が8つしかなくほとんどが「面している」になるため採らなかった。市町村の数は地図の市町村を数えるので、区は市にまとめ、北海道は北方領土の6村を含めた数になる。海に面しているかの判定（`decodeTownBorders` の `coastal`）はクイズでは使わなくなった
- 回答の読み取り（`src/town-tour/quiz.ts` の `answeredPrefectureOf`）は、発言を先頭から見て、各位置でいちばん長い書き方を取る。こうしないと「東京都」の中の「京都」を京都府と読む。2つ以上の都道府県を挙げた発言は、数打てば当たるので回答とみなさない。「都・府・県」を省いた書き方は、すぐ後が発言の終わり・記号・答える言い方（「かな」「だ」など）のときだけ数える。どこにあっても数えると、出題が大分県のとき「大分むずかしい」が正解者になってしまうため（レビューの指摘）
- 判定は issue のとおり Worker で行う。出題中かどうかと最初の正解者は D1（`town_tour_quizzes`）に持ち、正解者の記録は「まだ正解者がいない行」だけを書き換える1つの文（RETURNING）で行う。読んでから書くと、ほぼ同時の2人がどちらも正解者になる。AlertChannel に持たせる案は、Durable Object を判定者にしない約束（`.claude/rules/implementation.md`）に反するので採らなかった。KV は書いた直後の読みが保証されないので使えない。D1 を読むのは発言に都道府県が1つだけ書かれたときだけにし、チャットの全件では読まない
- 出題を開くのは合成ページで、クイズを流しはじめたときに `POST /api/overlay/town-tour/quiz` を呼ぶ。Worker が呼び出しを押し出した時点で開くと、合成ページが前の1件を流している最中（立て続けのレイドや `!darts`）には、画面に問いが出る前から回答を受け付け、出る前に締め切ってしまう。正解の都道府県は合成ページから受け取らず、Worker が一覧のコードから引く。受け付ける長さは15秒に、発言が届くまでの遅れの余裕2秒を足した長さで、同じ出題を2回開いても（合成ページを2つ開いていても）延ばさない
- 出題を開けなかったら（Worker に断られた・届かなかった）、合成ページはその場でクイズを打ち切り、「クイズを受け付けられませんでした」として正解を明かす。失敗を箱に出すだけで15秒の問いを出し続けると、答えても届かない問いを視聴者に投げることになるため
- Webhook でクイズの回答を照らす処理（D1 と押し出し）の失敗は投げず、`town-tour-quiz-failed` として記録して続ける。投げると Twitch へ2xx以外を返して再送させ、作業机のコマンドやコマンドの応答まで止めてしまう（マイグレーションを適用する前にも起きる）
- 正解者は呼び出しと同じ接続（目印 `townTour`）へ `type: 'answer'` を付けて押し出す。合成ページは届いた時刻（合成ページの時計）をクイズを終えた時刻にし、地図の演出・音の時刻・配信のBGMを下げる長さをそこから数える（`timeline.ts` の `quizEndOf`）。Worker の時計を使わないのは、OBS の PC の時計とずれても場面が飛ばないようにするため。クイズの長さを過ぎてから届いた正解者は出さない（画面はもう時間切れで先へ進んでいる）

## 紹介した市町村を記録し、締めで全国制覇マップを出す（#252）

ネタのコーナーは続くことで育つので、紹介した市町村を記録し、締めで「1,747のうち何市町村を紹介したか」を見せてシリーズにした。決めたことは次のとおり（配信者の判断。2026-10-05）。

- 記録は D1 の `town_tour_visits` に1市町村1行（コード・紹介した日時・きっかけ・相手の名前）で持つ。行の数は一覧の数（1,747）が上限で、古い行も消さない。同じ市町村をもう一度記録しても最初の行を残す（`ON CONFLICT DO NOTHING`）。合成ページを2つ開いていて同じ紹介が2回届いても、行は増えない
- 引くときは紹介済みの市町村を除く。どの紹介でも制覇数が必ず1つ増え、シリーズとして伸びが見えるため。1,747をすべて紹介したら一覧の全体から引く（紹介は止めない。2周目の紹介では制覇数は増えず、節目の一文も出さない）
- 試し再生は記録しない（配信の外で試した市町村まで制覇に数えるのは不自然なため）。ただし引くときは紹介済みを除き、締めの制覇マップも出す（見栄えを確かめられるように）。プレビュー（`?demo=true`）も記録しない
- 記録するのは流しきった紹介だけ。紹介を作れなかった再生は記録しない。「流しきった」は配信者への振りまで流し終えたときとし、合成ページがその時刻に `POST /api/overlay/town-tour/visit` を呼ぶ（`timeline.ts` の `visitRecordAtOf`）。Worker が押し出した時点で記録すると、作れなかった紹介や、合成ページを開いていないときの紹介まで数えてしまう。記録するきっかけと相手は、Worker が呼び出しに `visit` として載せたものを合成ページがそのまま送り返す（試し再生は `visit` が null なので送らない）
- 制覇マップは振りの後に6秒（`CONQUEST_MS`）出す。寄っていた市町村から日本全体へ引き（1.5秒）、これまでに紹介した市町村を今回の市町村とは別の色で塗り、引ききって一呼吸おいた2.5秒の時点で制覇数を1つ増やして今回の市町村に印を付ける（日本全体を映すと小さな市町村は点にしか見えないため、印は画面上で一定の大きさにする）。それまであった「出典だけを2秒残す」場面はやめた。制覇マップのあいだも出典を出し続けるので、出典を残す役目は制覇マップが引き継ぐ
- 節目の一文は、初めての都道府県（「○○県に初上陸！」）・離島（「離島の○○に上陸！」）・都道府県の全制覇（「○○県を完全制覇！」）・10件ごと（「祝・20市町村制覇！」）の4つで、重なればすべて出す。離島は「地図の上で隣り合う市町村が無い市町村」とした（佐渡市・色丹村など）。島に複数の市町村がある場合（淡路島・隠岐など）は離島と判定されないが、地図の形から機械的に決められる範囲に留めた。都道府県は全国地方公共団体コードの上2桁で見分け、全体の数と都道府県ごとの市町村は地図の形の市町村を数える（`src/town-tour/conquest.ts`）
- これまでの記録は、市町村を引くときに Worker が D1 から読み、呼び出しに `visited` として載せて押し出す（引くのにどのみち読むので、合成ページから読み直さない）。押し出した時点の記録なので、立て続けに届いた2件目にはまだ1件目が入っていない。そこで合成ページは、自分が記録させた市町村を足してから制覇マップを決める
- **記録に失敗しても紹介（制覇マップ）は止めない**。Worker は失敗を `collection_failures`（`town-tour-visit-failed`）に残して502を返し、合成ページは素材の箱に失敗を出すだけにする。これは Fail-Fast の例外である（`docs/principles.md` の方針5）。記録は配信の後でも直せる（D1 に1行足せばよい）が、締めの6秒を止めると配信中のコーナーが途中で切れてしまい、被害のほうが大きいため。失敗は黙って捨てず、箱とダッシュボードの両方に出す

## 締めの振りを、レイド元との「意外な共通点」に置き換える（#275）

「ところで…」の振りは、オチの直後に話題を変える問いで勢いが落ち、問われるのが配信者だけなのでレイドで来た人たちが当事者になれなかった。そこで振りを、レイドしてきた配信者とこの市町村の「意外な共通点」に置き換え、同じ共通点を認定証の任命理由として回収する。決めたことは次のとおり（配信者の判断。2026-10-06）。

- 共通点は「こじつけですが」と断らず、自信満々に言い切らせる。見当違いの結び方は配信者がツッコむ余地になる。ただし結ぶ2つの事実は実在するものに限る。町についての嘘の事実は、視聴者に本当だと受け取られてしまうため
- そのため、結ぶ語句を町の材料と配信者の情報から一字一句そのまま抜き出させ（`townQuote`・`raiderQuote`）、元の文字列に含まれるかをコードで照らす（`worker/town-bond.ts` の `parseTownBond`）。試作では全件で元の文字列に含まれていた。含まれない・長すぎる・任命理由の結びが違う応答は切り詰めずに捨て、1回だけ作り直させる（紹介と同じ扱い）
- 紹介とは別の呼び出しにする。同じ呼び出しで作らせると、共通点に引っ張られて紹介の項目が薄くなった。待ち時間は重ねないよう、`GET /api/overlay/town-tour` の中で紹介と並べて作り、揃ってから返す（合成ページは紹介・代表画像・ナレーションと一緒に待つ）。別の要求にして場面までに届かなければ出さない案は、経路と状態が1つずつ増えるので採らなかった
- 共通点だけの失敗では紹介を止めない。共通点を null にして理由（`bondFailure`）を返し、`collection_failures`（`town-tour-bond-failed`）に残す。合成ページは理由を素材の箱に出し、共通点の代わりにいまの振りを出す（場面ごと飛ばす案より、紹介の長さが変わらない）
- OpenRouter の鍵が無い配信者には共通点を出さない（失敗ではなく決めた形）。Workers AI の `llama-3.3-70b` は例文の中身を写して町の事実を作り（「村も塩辛が好き」）、使えなかったため。既定は OpenRouter の `google/gemini-3.8-flash`（約2.5秒・約0.3円）。`deepseek-v4.1-flash` は配信者の情報に無いことを言い切る外れがあり、`gpt-5.6-luna` は平凡な形が多く、flash-lite 系は禁じた抽象語が戻って字の一致を偽った。Claude Sonnet は高いので候補にしなかった。推論モデル（`gpt-oss-120b`）の試行は Workers AI の1日の無料枠を使い切り、本番の機能を止めた
- 例文の中身は写されるので、例はこの町・この配信者と無関係な題材にし、「形だけの例」と明記する
- 材料は Twitch の公開情報だけ（表示名・ログイン名・自己紹介・配信カテゴリ・配信タイトル・タグ・連れてきた人数）。タグの「日本語」は外す（ほぼ全員に付いていて、「日本でつながる」ばかりになった）。`viewers` テーブルの人物像とメモは画面に出さないものなので使わない。自己紹介とタイトルは誰でも書ける文なので、指示として受け取らせない注意書きを入れる
- 字が重なる語の手がかり（配信者の情報と材料の両方に出てくる語）をコードで探して渡す。「星野」はどのモデルも拾った。漢字1字・「日本」を含む語・ひらがなだけの語・2文字のカタカナの断片（「スト」）は雑音になったので除き、漢字を含む2文字以上か3文字以上のカタカナの語だけを渡す（`sharedWordsOf`）
- 配信者をけなさせない（見た目・配信の規模・腕前はいじらせない）
- Twitch の公開情報は、合成ページが紹介を頼んだときに Worker が引く（Webhook の中で Twitch を呼ばない約束（#250）を守る）。呼び出しにはレイド元のログイン名と連れてきた人数だけを載せる（`TownTourCall.raider`）
- 場面は12秒（`BOND_MS`。振りの6秒では左右の2枠と50文字の文を読みきれない）。見出しは「○○さんとこの町、実は…」で、左右の2枠に配信者側の語句（レイド元のアイコン付き）と町側の語句、その下に共通点の文を出す。ナレーションは見出しから読む
- キーワード（`!darts`）は配信者本人の動作確認用にし、配信者本人が書いたときだけ流す。本人をレイド元とみなして共通点と認定証まで流し、制覇の記録には数えない。本人かどうかは通知の `broadcaster_user_id` と発言者を比べる（Shared Chat 中の読み取りが置き換える書かれたチャンネルでは比べない）
- 試し再生には、ユーザー名の入力欄を置く。入力したログイン名の配信者をレイド元とみなし、Twitch にいなければ押し出さずに404で知らせる（打ち間違いに気づけるように）

## 締めにレイド元を名誉町民に任命する認定証を出す（#253）

レイドした側が持ち帰れるお土産として、締めにレイド元をその市町村の名誉町民に任命する認定証を出した。スクリーンショットされてレイド元の配信や SNS で話題になることを狙う。決めたことは次のとおり（配信者の判断。2026-10-05）。

- 出すのはレイドだけで、キーワード（`!darts`）では出さない。お土産はレイドへの返礼で、誰でも打てるキーワードで出すと認定証の重みが薄れるため（#275 でキーワードを配信者本人だけが使える動作確認用にしたので、キーワードでも本人を名誉町民にして出すよう改めた）
- 置く場所は全国制覇マップの後（振り → 制覇マップ6秒 → 認定証8秒 → 終わり）。issue を書いた時点では制覇マップがなく「出典を残す場面の前」としていたが、制覇マップがその場面を引き継いだので、お土産が最後に残って撮りやすい制覇マップの後にした。長さは文面を読んでスクリーンショットを撮れる8秒（`CERTIFICATE_MS`）
- 試し再生では見本の名前（「レイド元の配信者」）で出す。試し再生には相手がいないが、出さないと見た目を本物のレイドでしか確かめられないため
- 名誉町民にする相手は Worker が決めて呼び出しに `honoraryCitizen` として載せる（レイドはレイド元、試し再生は見本の名前、キーワードは null）。合成ページが `visit` のきっかけから推し量る案は採らなかった。`visit` は「流しきったら記録するか」を表すもので、試し再生が null なのは記録しないためであり、認定証を出すかどうかとは別の判断だから
- 文面はコードで組み立て（`src/town-tour/certificate.ts`）、LLM に作らせない（#275 で、任命理由だけは共通点と一緒に LLM に書かせるよう改めた。理由は共通点と同じ照合を通ったものを、40文字以内・「〜につき」か「〜と認められるため」で終わる形に限って添える）。自治体の名義や町章は使わず、発行者は「HDAD 市町村紹介」にする（町の公式なものと誤解されないため）。「町民」の字は市町村の名前の最後の字に合わせる（名誉市民・名誉村民・名誉区民）。日付は配信画面を開いた環境の時間帯に左右されないよう、日本時間の和暦（`Intl.DateTimeFormat` の `ja-JP-u-ca-japanese`）で数え、再生を始めた時刻から決める（描画は時刻だけから決める約束を守るため）
- 紙は画面の中央に重ね、後ろは暗い幕で沈める。画面で試したところ、紙の上端が冒頭の一文の帯と重なって雑然と見えたため。出典は幕より手前に描き、終わりまで出し続ける

## ズームの着地のあとに、記事の代表画像を作者とライセンスと一緒に出す（#254）

地図と文字だけでは町の姿が見えないので、着地のあとに記事の代表画像を1枚出した。決めたことは次のとおり（配信者の判断。2026-10-05）。

- 画像は日本語版 Wikipedia の PageImages（`prop=pageimages`・`pilicense=free`）の代表画像だけにする。代表画像のファイル名は本文と同じ問い合わせで受け取り、作者とライセンスは imageinfo の extmetadata で別に取る（`worker/town-image.ts`）。もう1回の問い合わせは LLM の待ち時間のあいだに並べて行う
- Google の Street View Static API で記事の座標の風景を出す案も出たが、#254 では採らなかった。代表画像が「名所」を見せるのに対しストリートビューは「現地の道路」を見せるもので、片方が無いときにもう片方で埋めると「黙って別の画像で埋めない」に反する。鍵と請求先アカウントが要り、規約（保存の禁止・帰属表示・配信に映すこと）の確認も要るので、別の場面として #263 に切り出した
- 出せる画像が無い記事（外した・代表画像が無い）は、画像の場面を飛ばす（Worker は `image: null` を返す。失敗ではなく決めた形）
- 地図・位置図・町章の見分けはファイル名の型で行う。全1,747件の記事の代表画像を調べたところ（2026-10-05）、代表画像の無い記事は無く、地図や町章が代表画像になっている記事も無かった。型に当たったのは、写真の無い記事の代わりの絵（鮫川村の `Gthumb.svg`）の1件だけだった。記事は書き換わるので、SVG と「位置」「Location」「map」「章」「Emblem」「Flag」「旗」の型は残す。「Symbol」は塔の名前（`Symbol_Tower_MiRAi_1.jpg`）にも使われるので入れない
- 出してよいライセンスは、extmetadata の機械向けの名前（`License`）が `cc-…`・`cc0`・`pd` のものに限る。同じ調査で 1,727 件がこれに当たり、外れたのは GFDL・FAL・「Copyrighted free use」・名前の無いものの20件だった。表示は人向けの名前（`LicenseShortName`）で行う
- 作者は extmetadata の `Artist`（HTML）からタグを外して文にする。CC で作者が無い画像（同じ調査で14件ほど）は表記を満たせないので出さない。パブリック・ドメインと CC0 は作者が無くても出す。組み写真では撮影者が並んで数百文字になる（100文字を超えるのは14件）ので、100文字（`MAX_ARTIST_LENGTH`）を超えたら出さない
- 画像の情報の問い合わせが失敗したら、紹介ごと 502 にする（`town-tour-failed`）。外したのではないので黙って `null` にはしない。同じ Wikipedia への問い合わせで、本文が取れて画像の情報だけが取れないことはまれなので、例外を増やさない
- 長さは項目と同じ6秒（`IMAGE_MS`）。画像は紹介が届いてから合成ページが読み込み、読み込み終えてから流しはじめる（描画のたびに待たない）。読み込めなかった・10秒（`IMAGE_LOAD_TIMEOUT_MS`）で読み込めなかったときは、素材の箱に失敗を出し、画像を外した紹介として流す
- 画像は Worker を通さず、合成ページが Wikimedia の URL から直接読む（Worker の CPU 時間と転送を増やさないため）。画面に出す大きさは幅1280px の縮小版（`TOWN_IMAGE_WIDTH`）

## 紹介を VOICEVOX のナレーションで読み上げる（#255）

テレビのコーナーにはナレーションがあり、配信者が画面を見ずにリアクションできるようにもなるので、紹介を読み上げるようにした。決めたことは次のとおり（配信者の判断。2026-10-06）。

- 話者と速度はチャットの読み上げ（`speech-settings`）と別に、市町村紹介の設定として持つ（`worker/town-tour-narration.ts`。KV の `town-tour-narration`）。ナレーションをチャットの読み上げと別の声にできるようにするためである。音の設定（`town-tour-sound`）とも分けた。音の設定の形は押し出しの中身と同じで（`src/town-tour/sound.ts`）、項目を足すと保存済みの設定の読み直しに手当てが要るためである。画面は同じ「市町村紹介」のカードの別の区画で、保存のボタンも分ける
- 合成はチャットの読み上げの「さくら」と同じ `createSakuraTts` を使い、Worker の `POST /api/overlay/town-tour/narration` を経由する（APIキーをブラウザに置かない）。読み上げない設定なら409で断り、話者と速度は要求ではなく保存済みの設定から取る（オーバーレイ用キーは配信画面に映りうるので、選んでいない配信者に課金を起こさない）。文は100文字（`TOWN_TOUR_NARRATION_TEXT_MAX_LENGTH`）までに限る。冒頭の一文（表示名25文字と最長の市町村名）と、LLM が作れる最長の項目が収まることはテストで確かめる。未保存の既定は「読み上げない」（従量課金のため）
- 読み上げるのは冒頭の一文・大見出し・各項目・振りのすべて（issue の案は冒頭と項目だけだったが、配信者がすべてにした）。大見出しと振りは見出し（「この町、実は…」「ところで…」）から読み、項目は見出しを読まない。大見出しの見出しは画面でも文より先に出る溜めなので、声でも溜めにする
- 表示の長さは「読み上げの長さ＋余白（0.8秒。`NARRATION_TAIL_MS`）」にし、いまの決まった長さを下限にする（配信者が決めた）。短い文でも読む間がなくならないようにするためである。冒頭の一文は着地で読み、大見出しへ進むのを読み終えるまで待つ（代表画像があれば画像を出しながら読み、長ければ画像の場面を延ばす）
- 場面は時刻だけから決まる形を保つため、合成ページは紹介が届いたら全部の文を並べて合成させ、音声の長さを読み終えてから紹介を届いたものとする（`ReadyIntro.narration`。代表画像の読み込みと並べて待つ）。読み上げの長さを場面の時刻に含めるので、鳴らす時刻（`sound-cues.ts`）も配信の BGM を下げる長さ（`bgm-duck.ts`）も同じ流れ（`tourSpanOf`）から決まる
- 合成・読み込みに失敗した文は、素材の箱に失敗を出してその場面だけ無音で流す（紹介ごと失敗にはしない。配信者が決めた。代表画像を読み込めなかったときと同じ扱い）。Worker は失敗の記録（`collection_failures`）には残さない（チャットの読み上げの合成と同じ。失敗は素材の箱で見える）
- 読み上げているあいだは紹介の BGM を設定の音量の4割（`NARRATION_BGM_RATIO`）まで下げ、読み終えた時刻に戻す。下げる行と戻す行も音の表に載せる。タイマーが遅れて読み上げを鳴らさなかったときは BGM も下げない（戻す行は遅れても行う）
- 費用は1件で最大およそ500モーラ（約0.15円）。さくらの課金は合計モーラで、1件ごとの切り上げはない（2026-10-04 に実機で確認済み）。1件で5〜6回合成するので、月50回の無料枠は8〜10件で尽きる

## CPU 時間は Workers Free の上限ぎりぎりで、超えたら材料づくりを合成ページへ移す（#228）

デプロイ後に `wrangler tail` で本番の `GET /api/overlay/town-tour` を5件測った（2026-10-04）。CPU 時間は色丹村 10ms・府中市 (広島県) 11ms・葛飾区 11ms・檜枝岐村 4ms・松茂町 4ms で、5件とも打ち切られず `ok` で終わった。かかった時間は1件2.7〜5.1秒だった。

先に呼んだ3件だけが重く、記事の短い色丹村も 10ms だったので、記事の長さよりも、Worker が起動して最初に呼ばれたときの準備が効いていると見ている。手元で処理ごとに測ると、記事の JSON の解析・材料の拾い出し・プロンプトの組み立てを合わせても 0.3〜2.4ms だった。同じ時間帯の cron（配信の記録の収集）も 15ms で `ok` だったので、10ms ちょうどで打ち切られるわけではないが、どこまで超過が許されるかは確かめていない。

ただし、これは推測である。tail の記録には各呼び出しが起動直後だったかどうかが出ないので、5件からは、重かった3件が起動直後で軽かった2件がそうでない、とまでは確かめられていない。この推測が正しければ、レイドはたまにしか来ないので本番では毎回が起動直後に近く、毎回 10〜11ms 前後になる。いまは超過していないので手を入れない。`exceededCpu` で打ち切られるようになったら、Wikipedia からの取得と材料の拾い出し（`worker/town-wikipedia.ts`）を合成ページ（ブラウザ）側へ移し、Worker は LLM を呼ぶだけにする。

## 流すのは素材で、Worker は市町村を引いて冒頭の一文を添えるだけにする（#229）

トリガーの動作 `townTour` は、Worker が市町村を1つ引き（`worker/town-tour-call.ts` の `pickTown`）、冒頭の一文を添えて `AlertChannel` の6つ目の目印（`townTour`）の接続へ押し出すだけにした。紹介は素材が受け取ってから `GET /api/overlay/town-tour` で作らせる。Webhook の中で紹介まで作らない理由は #228 と同じ（`waitUntil` の30秒に LLM の待ち時間が収まらない）。冒頭の一文を Worker が組み立てるのは、素材を「受け取ったものを流すだけ」に保つためである（`.claude/rules/alerts.md`）。

アラートの列（`src/alerts/queue.ts`）には入れず、素材の中で別の列を持つ。紹介は1件30〜40秒あり、アラートの列に入れるとそのあいだほかのアラートが止まるためである。そのかわり、アラートと重なって出ることは受け入れた（配信者の判断。2026-10-04）。

1項目の表示時間は6秒にした（配信者の判断。8秒では1件50秒近くになり長い）。場面ごとの長さは #249 で変えた（上の「固定の5項目をやめ、一本の切り口を大見出しに立てる」）。

`POST /api/admin/town-tour/demo` で、トリガーと同じ `AlertChannel` から押し出す。合成ページのプレビュー（`?demo=true`）では Worker につながず決まった1件（千代田区）を流すので、本物の経路が動くかはこの試し再生で確かめる。冒頭は「試し再生: 」で始め、配信中に押しても試しだと分かるようにした。

## 音は鳴らす枠をコードで決め、枠ごとに素材を選ばせる（#243）

BGMと効果音を付けるにあたり、鳴らす時刻を配信者が組み立てる形は採らなかった。演出の場面はコードで決まっている（`src/town-tour/timeline.ts`）ので、自由に時刻を置けても意味のある置き方はほとんど無いためである（`docs/principles.md` の 1）。枠は BGM・始まり・ズーム・着地・項目ごと・締めの6つに固定し、一覧は `src/town-tour/sound.ts` の1か所に置いて Worker・管理画面・合成ページが読む（Worker から `src/` を読み込む例外を1つ増やした。同じ一覧を2か所に書くと食い違うため）。

それでも枠ごとの素材は選ばせる。音声はリポジトリに入れられないからである。リポジトリは公開しており、魔王魂の規約は曲単品の再配布を禁じている。そこで BGM と同じく配信者が R2 にアップロードした音声から選ぶ形にし、おすすめの素材は `docs/guide/town-tour.md` に配布元へのリンクで載せた。選んでいない枠は「鳴らさない」という選択として扱い、ほかの音で埋めない。音量は枠ごとには持たず、BGM と効果音の2つにした。

設定はトリガーの動作（`townTour`）ごとには持たず、市町村紹介として1つだけにした。レイドとキーワードで音を変えたい場面が思い当たらず、試し再生で聞き比べた音がそのまま本番で鳴るほうが分かりやすいためである。画面は試し再生のボタンと同じカードに置いた。

音は押し出しの中身に、音声の URL（オーバーレイ用キーつき）にして載せる。紹介と一緒に返すと、紹介が届く（2〜5秒）まで始まりの音を鳴らせないためである。音を選んでいるのにオーバーレイ用キーが未発行なら、黙って無音で流さずに押し出しの失敗（`town-tour-push-failed`）として残す。枠に選ばれている素材は、トリガーやBGMの曲と同じく削除させない。

魔王魂の著作表記は Twitch のパネルに書くことにし、画面には出さない。アプリはアップロードされた音声の配布元を知らず、画面に出すなら表記の文言を入力させることになるためである。

## 音を鳴らす時刻は表で決め、鳴らしたことは合成ページが覚える（#244）

場面は経過時間だけから決める約束だが、効果音は「もう鳴らしたか」を覚えないと毎フレーム鳴ってしまう。そこで、いつ何を鳴らすかは再生を始めた時刻・紹介が届いた時刻と音の設定だけから作る表（`src/town-tour/sound-cues.ts`）に決めさせ、合成ページは鳴らした行の id を1件の再生ごとに覚えるだけにした。表の秒数は場面と同じ定数と `tourSpanOf` から作り、場面と音が別々の計算で食い違わないようにした。

時刻を迎えたかの確認は描画のループ（`requestAnimationFrame`）ではなく、50ミリ秒のタイマーで刻む。OBS のブラウザソースは映っていないあいだ描画を間引くことがあり、描画に合わせると音が遅れたりまとめて鳴ったりするためである（BGM の `src/bgm/player.ts` と同じ理由）。再生の終わりもこのタイマーで確かめ、描画が止まっていても BGM を止めて次の1件へ進める。それでもタイマー自体が遅れることはあるので、時刻から0.5秒より遅れた効果音は鳴らさず、BGM を下げる時刻を過ぎてからは BGM を鳴らしはじめない（場面とずれた音をまとめて鳴らすより、鳴らさないほうが害が小さい）。

紹介を作れなかった再生は表を空にし、鳴りはじめていた BGM も止める。始まりとズームの音は紹介が届く前（2〜5秒）に鳴るので、失敗した再生で一切鳴らさないことはできないが、失敗が分かった時点から先は鳴らさない。

## 配信のBGMは「下げておく長さ」を送り、裏方のページが自分で戻す（#245）

紹介の BGM と配信の BGM が重ならないよう、紹介の BGM を鳴らすあいだ配信の BGM を下げる。合成ページと裏方のページは別のページなので、合成ページが `POST /api/overlay/bgm/duck` へ知らせ、Worker が `AlertChannel` を通して裏方のページへ押し出す。

知らせは「下げる」「戻す」の2つにせず、「受け取ってから何ミリ秒下げておくか」の1つにした。「戻す」を送る形では、紹介の途中で合成ページが閉じられた・再読み込みされた・知らせが届かなかったときに、配信の BGM が下がったまま残るためである。長さで送れば、裏方のページは届いてから数えて自分で戻すので、送り手がいなくなっても戻る。時刻ではなく長さにしたのは、合成ページと裏方のページの時計がずれていても下げる長さが変わらないようにするためである。

紹介が届くまで（2〜5秒）は再生の終わりが決まらないので、鳴らしはじめたときは決まった長さ（30秒。`src/town-tour/bgm-duck.ts` の `LOADING_DUCK_HOLD_MS`）だけ下げ、紹介が届いたら終わりまでの長さを送り直す。紹介を作れなかったら 0（すぐ戻す）を送る。Worker は5分を超える長さを受け取らない（送り手が壊れても長く下げたままにしない）。長さの判断は再生の状態と現在時刻だけから決める関数にして、合成ページは鳴らしはじめた・届いた・失敗したときに送るだけにした。

押し出しの経路は、曲の切り替え（目印 `bgm`）とは別の目印 `bgmDuck` にした。`bgm` の接続には素材「再生中の曲」と管理画面もつながっていて、どちらも届いたものを曲の切り替えとして読むため、読まない知らせを混ぜると両方を直すことになる。裏方のページは2本目の WebSocket を開くが、Hibernation で待っているあいだは課金されない。つながっていない間の知らせは読み直さない（取りこぼしても、下げないほうへ倒れるだけである）。

下げる量（元の音量の4分の1）は設定項目にしない（`docs/principles.md` の 1）。裏方のページが開いていなければ配る先が無いだけで、失敗にはしない。プレビューでは配信の BGM を動かさないので送らない。

## 日本地図は自前で読み、正距円筒図法で描く（#229）

TopoJSON の読み解きは使う範囲（量子化と差分の復元・弧の向き）が小さいので、topojson-client を持ち込まずに `src/town-tour/topo.ts` で読む。投影は北緯36度で東西の縮みをそろえる正距円筒図法にした。日本の範囲なら形が大きく崩れず、拡大しても線の太さが縦横で変わらない。

ズームしきったときの広さには下限（`src/town-tour/camera.ts` の `MIN_TOWN_SPAN`。緯度でおよそ0.15度）を置いた。東京の区のような小さな市町村を目いっぱい拡大すると、3%に簡略化した形が角ばって見えるためで、0.3度では千代田区が小さすぎ、0.15度で形が見分けられて角ばりも目立たなかった（プレビューで確認。2026-10-04）。

紹介を作れなかったときは、その1件をすぐに終えて素材の箱に失敗を出し、次の1件へ進む（`docs/principles.md` の 4。黙って何も流さないと壊れていることに気付けない）。

## 長すぎる紹介は、問題を伝えて1回だけ作り直させる

試し再生で、LLM が上限より長い紹介を返して失敗した（2026-10-05）。LLM は日本語の文字数の指示を守りきれず、上限（大見出し30文字・項目の文80文字など）を少し超えることがある。

上限を緩める案は採らなかった。上限は合成ページの行数と読み上げの長さから決めたもので、緩めると枠からはみ出す。超えた分を切り詰める案も、文が途中で切れた紹介を配信に出すことになるので採らなかった。

代わりに、決まりに合わない応答（長すぎるほか、JSON でない・項目が欠けているなど `TownTourContentError` になるもの）が返ったら、どの項目が何文字超えたかと前回の応答を伝えて、1回だけ作り直させる（`worker/town-tour.ts` の `generateTownTour`）。呼び先の会話の役に assistant が無いので、前回の応答は作り直しの指示の中に引用する。作り直しても合わなければこれまでどおり投げて502にする。LLM そのものの失敗（無料枠切れなど）は作り直させない。作り直すと紹介が届くまでが数秒延び、LLM の呼び出しが1回増える。

## 写真の説明は LLM に書かせ、紹介文の出典は「紹介文」と書く

実配信で、代表画像を出しても何の写真か分からない・画像を消したあとも「出典: Wikipedia「記事名」」が残り続けて画像の出典に見える、という指摘があった（2026-10-06）。

写真の説明は、Wikimedia Commons の説明（ImageDescription）をそのまま出す案ではなく、ファイル名と Commons の説明を材料に LLM に紹介と一緒に書かせる形にした（配信者の選択）。Commons の説明は英語だけ・無い・長い解説のことがあり、そのままでは画面の1行に収まらない。LLM は画像そのものを見ないので、ファイル名と説明から分からなければ空にさせ、合成ページは説明を出さない。材料にするため、代表画像の情報は LLM を呼ぶ前に取るようにした（これまでは LLM の待ち時間のあいだに並べて取っていた。紹介が届くまでが Wikipedia の問い合わせ1回ぶん延びる）。

右下の出典の行は、Wikipedia の本文が CC BY-SA なので紹介を流すあいだ出し続ける決まりのまま残した。代わりに表記を「紹介文: Wikipedia「記事名」」に変え、上の行の「写真: 作者（ライセンス）」と並べて、どちらが何の出典かを読み分けられるようにした。

## 振りは、題材を入れ替えるだけでどの町にも使える問いにさせない

振りが「祭りに行ったことがありますか？」のように、題材だけを差し替えればどの町にも使える問いになりがちだった（2026-10-06）。指示の例が「この名物、食べたことありますか？」だけだったためである。項目のいちばん意外な事実を固有名詞ごと名指しし、配信者がその場で答えて話を広げられる問い（どっち派か・自分ならどうするか）にするよう指示し、悪い例として元の型を示した。良い例には、材料に無い事実を足させないよう、材料から言えることだけでできた問いを置いた。
