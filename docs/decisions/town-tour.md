# 市町村紹介（引く対象の一覧と日本地図）

レイドを受けたとき、レイド元の紹介の代わりにランダムな市区町村の紹介を流すネタ機能を3段階で作る（issue #227 一覧と地図・#228 紹介文をその場で作る API・#229 トリガーの動作と素材）。ここには1段階目（#227）と2段階目（#228）の判断を書く。

## 一覧も地図も国土数値情報の N03 1本から作る

当初は geolonia の `japanese-addresses`（`api/ja.json`）から一覧を取り、地図の N03 と名前で突き合わせて検証する計画だった。調べると、`ja.json` は 2023-11-15 から更新が止まっており、リポジトリの README にも「現在更新されておりません」とあった（後継は `japanese-addresses-v2`）。一方、N03 は都道府県・郡・市区町村名・行政区域コードを属性に持つので、一覧も地図も同じ版から作れる。同じ源から作れば名前の突き合わせ（表記ゆれ・合併の反映時期のずれ）がそもそも起きないので、N03 に一本化した。一覧と地図の食い違いは、片方だけ作り直したり手で直したりしたときにしか起きないので、`src/town-tour/towns.test.ts` がコードの1対1で検出する。

使う版は令和8年（2026年）1月1日時点の全国版（`N03-20260101`）。

## 一覧と地図はリポジトリに同梱する

引くたびに外部へ取りに行くと、相手の都合で配信中に止まる（方針7・8）。作り直す手順は `scripts/town-tour/build-data.ts` として残す。地図は静的アセット（`public/town-tour/japan.topo.json`）に置き、OBSに載せるページから読む。一覧（`src/town-tour/towns.json`）は Worker（#228 の紹介文づくり）と合成ページの両方が読むので `src/` に置く。地図の形を Worker に持ち込むと Worker の容量を食うので、一覧と地図は別のファイルにした。

## 政令市の区は市にまとめ、東京23区は1区ずつ残す

政令市の区は行政区で、Wikipedia の記事も紹介の単位としても市のほうが自然なので、市にまとめる。N03 は政令市を区の単位でしか持たず、市そのもののコードが無い。区のコードから市のコードは機械的に導けない（札幌市清田区は 01110 だが札幌市は 01100、浜松市は 2024年の再編で区が 22138〜 になったが市は 22130）ので、20市の表で持ち、表に無い政令市が現れたらエラーで止める。

東京23区は特別区で、市と同格の地方公共団体であり、市に属していないので1区ずつ残す。

## 北方領土の6村は入れ、所属未定地は外す

北方領土の6村（色丹村・泊村・留夜別村・留別村・紗那村・蘂取村）は N03 に形とコードがあり、配信者の判断で引く対象に入れた。北海道の泊村は古宇郡と国後郡の2つがあり名前だけでは見分けられないので、一覧に郡名（`county`）を持たせ、識別はコードで行う。

N03 の「所属未定地」（埋立地などで、どの市町村にも属さない区域。7都府県にある）は紹介できないので、一覧からも地図からも外す。

## 地図は頂点の3%を残して簡略化する

N03 の全国版の shp は約260MB ある。Workers の静的アセットは1ファイル25MiBまでなので、mapshaper で頂点を減らし TopoJSON（量子化 1e5）にした。1%（約2.0MB）と3%（約3.8MB、gzip で約1MB）を、いちばん小さい村の富山県舟橋村（約3.5km²）に寄って比べると、1%は数個の頂点の多角形になって形が分からず、3%は形が分かったので3%にした。

OBSに載せるページには外部のタイルも MapLibre も持ち込まず、この TopoJSON を Canvas 2D で描く（#229）。重心やズームの範囲もこの形から計算できるので、緯度経度の一覧は持たない。

## 紹介は貯めずに、呼ばれるたびに作る（#228）

当初は、紹介を1日1件ずつ cron で作って D1 に貯め、レイドのときは1件取り出すだけにする計画だった（待ち時間・配信中の失敗・方針8「トリガーのたびにLLMを呼ばない」のため）。Claude Code で事前に全件を作ってリポジトリに同梱する案も検討したが、全件で数MBあり、Worker に同梱すると Free プランのサイズ上限（圧縮後 3MB）に当たる。静的アセットや D1 に置くと、作り直しの仕組みと Wikipedia の更新への追従が別に要る。

一方、待ち時間は合成ページの素材（#229）が日本地図からズームする演出のあいだに吸収でき、実測でも1件2〜5秒だった。レイドは1回の配信で多くても数回なので、無料枠への影響も小さい。そこで配信者の判断で、呼ばれるたびに作る形にした。方針8の例外にあたる。

Twitch の Webhook の中では作らない。Webhook には早く2xxを返す必要があり、続きを預ける `waitUntil` は Free プランで30秒で打ち切られる。LLM の待ち時間の上限（`worker/llm.ts` の `LLM_TIMEOUT_MS`、60秒）がこれに収まらない。合成ページが `GET /api/overlay/town-tour` を呼べば、応答を待つ時間に Webhook の制約が掛からない。

## 記事は名前で検索せず、全国地方公共団体コードで Wikidata から引く（#228）

市町村の名前は一意でない（府中市は東京都と広島県に、泊村は北海道に2つある）。Wikidata の項目は全国地方公共団体コード（P429）を持つので、一覧のコードに検査数字を付けた6桁（総務省の規則。`(11 − 重み付きの和 mod 11) mod 10`）で項目を引き、その日本語版の記事を採る。1,747件のうち1,746件は1つの記事に決まった。残る読谷村（473243）は、読谷村文化センターの項目にも同じコードが付いていた（Wikidata の誤り）。

この対応づけは実行時ではなく `scripts/town-tour/build-articles.ts` で行い、`src/town-tour/articles.json` として同梱する。実行時の外部呼び出しを1回減らせるうえ、曖昧な対応を生成の時点で止めて人が確かめられる。曖昧なものを項目の種類（P31）で選ぶ規則も考えたが、市の項目でも「日本の市」が付いていないものがあり、別の誤りを招くので、見つかった分だけを表（`PREFERRED_ITEMS`）で指名する。

検索 API（`haswbstatement:P429=…`）を1件ずつ呼ぶと、数百件で制限にかかった。生成には SPARQL の1回の問い合わせを使う。

## 材料は記事の節を見出しの名前で拾い、LLM には項目を埋めさせるだけにする（#228）

REST の summary は冒頭の1文しか返さないので、TextExtracts の見出し付きプレーンテキストで本文を取る。長い記事（府中市 (広島県)）でも応答は約70KBで、CPU 10ms の中で解析できる。全文は LLM に渡さず、見出しの名前で系統（冒頭と概要・地理・名前の由来・歴史・名物・そのほかの話題）ごとに拾い、系統ごとに1,000文字で切る。

見出しの名前は記事ごとに違う（名物の節は「名物」「名品」「特産品」、出身者の節は「著名な出身者」「出身有名人」）。名前の型は実際の記事で確かめて決めた。「祭」だけだと「葬祭場」に、「文化」だけだと「文化施設」の一覧に当たる。また「町名一覧」「大字」の節は、名前が並ぶだけで系統の長さの枠を埋めてしまう。そのため、語を長くとり、一覧の節は拾わない。子の見出しが親と別の系統に当てはまれば子の系統に入れる（府中市 (広島県) では「名物」が「名所・旧跡・観光スポット」の下にある）。

LLM だけに書かせると、人口や名産をもっともらしく捏造する。そこで、材料にある内容で項目を埋めさせるだけにし、材料に無い項目は空のまま返させる（方針6・11）。試した5件（府中市 (広島県)・檜枝岐村・北島町・葛飾区・泊村 (北海道根室振興局)）では、出てきた事実はどれも記事の本文にあった。既定のモデルは、あらすじと同じ大きいもの（`llama-3.3-70b`）にした。

## 項目は「知らない自治体について、へえとなるか」で選ぶ（#228）

当初の案は、名前と読み・人口と面積・市町村の木と花・名産・出身の有名人・ひとことの6項目だった。配信者の判断で、リスナーがまったく知らない自治体の知識が増える面白さがあるかどうかで選び直した。市町村の木や花は「ふーん」で終わるが、歴史には興味が湧く。

採った項目は次の5つ（`worker/town-tour.ts` の `TOWN_TOUR_ITEMS`）である。
- どこにあるか（人口は規模感として触れる程度）
- 名前の由来
- 歴史のひとこま
- 名物・名産
- 意外な一面

出身の有名人は記事に載っていないことが多い（試した5件のうち2件だけ）ので、独立した項目にせず、「意外な一面」の材料に含める。
