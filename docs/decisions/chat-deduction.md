# チャットで推理（`/chat-deduction/`）

視聴者が「はい／いいえ」で答えられる質問を繰り返して答えを絞り込み、当てるゲームを、issue #375〜#378 の4段階で作る。ここには段階2（#376）までの判断を書く。参考にした既存のゲームはあるが、その名前はリポジトリに残さず、機能の名前は「チャットで推理」とした。

## 質問と解答はチャンネルポイントで受ける

チャットの発言から質問と解答を拾う案（`!q`・`!a` のコマンド、または「？」で終わる発言を質問とみなす）もあったが、チャンネルポイントの報酬（ユーザー入力つき）で受けることにした。質問1件ごとに LLM を呼ぶので、雑談の疑問文まで拾うと呼び出しの回数が視聴者の発言数しだいになる（`docs/principles.md` の方針8）。ポイントを払う形なら、参加する意思のある質問だけが届く。報酬はゲームのあいだだけ交換できるようにし、ゲームの外では視聴者の画面に出さない。

## 報酬は HDAD が作り、既存の報酬を選ばせない

Twitch が報酬の更新（交換できるかどうかの切り替えを含む）を許すのは、同じ Client ID で作った報酬だけである（`docs/decisions/rewards.md`）。Twitch のダッシュボードで作った報酬を選ばせると、ゲームを始めるときに初めて403で失敗する。そこで `/chat-deduction/` に「報酬を作る」を置き、HDAD が2つの報酬を作って ID を控える。選択欄すら置かないので、打ち間違い・選び間違いも起きない（方針2）。必要ポイントや説明を変えたいときは、HDAD が作った報酬なので `/rewards/` でそのまま変えられる。

切り替えには `is_enabled` だけを送る Helix の更新（`setCustomRewardEnabled`）を足した。既存の `updateCustomReward` は全項目を送るので、ゲームの開始と終了のたびに配信者が `/rewards/` で変えた値を読み直して送り返す必要があり、読み書きのあいだに変えた値を戻してしまうおそれがあるためである。

報酬は待ち行列に入れる形（`should_redemptions_skip_request_queue: false`）で作る。受け付けなかった質問のポイントを返す（交換を CANCELED にする。#376）には、交換が未完了のまま残っている必要があるためである。

## 切り替えに失敗したら、開始も終了も黙って進めない

開始では、ゲームの行を作ってから報酬を交換できるようにする。報酬を切り替えられなかったときに行を残すと、視聴者が参加できない「開催中」のゲームができてしまうので、行を消して始めなかったことにする。2つの報酬は順に切り替えるので、片方だけ交換できるようになっている場合があり、交換できない状態へ戻してから失敗を返す。戻すのにも失敗したら、そのこともメッセージに添えて `/rewards/` で確かめるよう促す（方針4）。

終了では、先に報酬を交換できないようにし、それが済んでから行を終える。逆の順にすると、報酬の切り替えに失敗したときに「終わったのに交換できる」状態が残り、視聴者のポイントが答えの出ないゲームに消える。

## 問題集は自前で持ち、正誤は別名との照合で決める

問題（人物・場所・出来事・もの）は `src/chat-deduction/problems.json` に配信者が確かめたものだけを持つ（漢字クイズの問題集と同じ考え方）。質問への答えは LLM に作らせるが、材料は問題集の正解と事実メモだけに限り、メモに無いことは「分からない」と答えさせる（#376）。LLM の知識だけで答えさせると、もっともらしい作り話で視聴者を誤った方向へ導いても気づけない。

解答の正誤は LLM に判定させず、別名の一覧との完全一致で決める（#377）。正解かどうかでゲームが終わるので、同じ解答が呼び出しのたびに違う判定にならないようにするためである。表記の揺れは、問題を作るときに別名として書き足して吸収する。

## 問題集は Worker と画面で同じものを読む

問題集は、Worker（開始のときの問題の確かめ・質問への答え・解答の照合）とアプリのページ（問題を選ぶ欄）の両方が読む。2か所に書き分けると食い違うので、漢字クイズと同じく Worker から `src/chat-deduction/` を読み込む例外にした（`.claude/rules/implementation.md`）。

## 質問の受け付けは、交換のIDの鍵と同じ1つの文で決める（#376）

質問の交換は、交換のID（`redemption_id`。一意）で行を作るのと、受け付けるかどうか（開催中のゲームがあるか・1問あたりの上限・同じ人の待ち時間）の判断を、1つの `INSERT ... SELECT` で行う（`worker/chat-deduction-store.ts` の `reserveQuestion`）。数えてから書く2つの文に分けると、同時に届いた交換がどちらも上限の手前で数えて、上限を越えて LLM を呼んでしまう。開催中のゲームが無かった交換も、理由 `no-game` を付けた行として残す（なぜポイントを返したかを後から確かめられるように）。

上限は1問あたり30件、同じ人の待ち時間は60秒の定数にした（方針8）。設定項目にしないのは、LLM の呼び出しの回数の天井をコードで決めておくためである。数えるのは答え待ちと答えた質問だけで、受け付けなかった質問と答えられなかった質問は数えない。どちらもポイントを返したので、視聴者から見れば質問していないのと同じだからである。

`game_id` は外部キーにしていない。報酬を片方だけONにできたあとに開始を取り消す（`cancelGame` が行を消す）までのわずかな間に質問が届くと、外部キーがあると取り消しが失敗するためである。

## LLM と交換の更新は、Twitch へ応答を返したあとに行う（#376）

LLM の応答を待ってから2xxを返すと、Twitch が同じ通知を再送する（`aiChat` と同じ事情）。そこで鍵の確保（行を作る）までを応答の前に行い、LLM と交換の更新は `waitUntil` に回す。応答のあとの失敗は投げても誰も受け取らないので、収集の失敗として残す（`recordLateFailure`）。

交換を完了・取り消しにできなかったとき（トークンのスコープ不足・Twitch の失敗）は、D1 の質問の行を書き戻さない。答えたこと・受け付けなかったことは事実で、交換は Twitch の待ち行列に未処理のまま残るので、配信者が Twitch の画面で処理できる。

## 返事に正解か別名が入っていたら拒む（#376）

LLM には答えの名前を書かないよう伝えるが、守られる保証はない（方針11）。答えを漏らした返事を映すとゲームが壊れるので、照合（`parseChatDeductionAnswer`）で1文に正解か別名が含まれていないかを確かめ、含まれていたら失敗としてポイントを返す。別名は解答の照合（#377）のためにすでに問題集にあるので、新しいデータは要らない。

## 交換の通知は、アラートとは別に読む（#376）

質問の受け口は交換のID・視聴者のID・質問の文字列を読むが、アラートの読み取り（`worker/alert-event.ts` の `extract`）はどれも読まない。`extract` に足すと、トリガーの照合しかしない通知でも項目が欠けていれば失敗するようになるので、「質問」の報酬の交換と分かってから `worker/chat-deduction-question.ts` が読む。

## 解答は表記を揃えてから別名と照らす（#377）

完全一致だけでは、カタカナで書いた・中黒を省いた・全角の英字で書いたといった、意味の同じ解答が不正解になる。そのたびに別名を書き足すと問題集が書き分けで膨らむので、解答と別名の両方に同じ揃え方（`src/chat-deduction/guess.ts` の `normalizeChatDeductionGuess`）を通してから完全一致で比べる。揃えるのは、空白と記号（中黒・句読点など）・全角と半角（NFKC）・英字の大文字と小文字・カタカナとひらがなで、どれも読み手が同じ答えと受け取る違いに限った。別の読みや略称（漱石・本能寺）は揃え方では決まらないので、引き続き別名に書く。部分一致や似た綴りを正解にする揃え方は入れない（「富士山の頂上」を正解にすると、答えを含む長い文を送れば当たってしまう）。

揃え方は漢字クイズの回答の読み方（`src/kanji-quiz/answer.ts`）と似ているが、共有しない。漢字クイズは読み（ひらがな）だけを比べ、記号を含む発言を雑談として外すのに対し、こちらは漢字・英字を含む名前を比べ、記号は除いて比べるためである。

## 正解者は1つのトランザクションで1人に決める（#377）

解答の行は、質問と同じく交換のIDを鍵に作る（`reserveGuess`）。正誤は Worker が JavaScript で照らすので、行を作る文の中では決められない。そこで正解だったときは、「ゲームがまだ開催中なら解答を正解にする」「正解になったらゲームを終える」「正解にならなかったら受け付けなかったことにする（`closed`）」の3つの文を1つのトランザクション（`solveGame`）で行う。D1 のトランザクションは順に実行されるので、ほぼ同時に届いた2つの正解のうち、先に実行された方だけが正解になる。表の側でも、1つのゲームの正解は1行だけという一意の索引で守る。

照合までのあいだにゲームが終わっていた正解（ほかの人の正解・配信者の打ち切り）は、ポイントを返す。届いたときにはゲームが開催中だったが、正解者にはなれないからである。不正解の解答は、照合までにゲームが終わっていても届いたときの判定どおり不正解として交換を完了にする。

## 正解のときは、ゲームを終えてから報酬を止める（#377）

配信者の打ち切りでは報酬を先に交換できないようにしてからゲームを終えるが、正解のときは逆の順にした。正解者は通知が届いた順に決まる事実で、報酬の切り替え（Twitch への通信）の成否で取り消すものではないからである。切り替えに失敗しても、終えたあとに届いた質問と解答は「開催中でない」としてポイントを返すので、視聴者のポイントは答えの出たゲームに消えない。失敗は `chat-deduction-rewards-failed` として残し、配信者が `/rewards/` で直せるようにする。

正誤は、交換を更新するトークンを取る前に決める（質問では LLM より先にトークンを取るのと逆）。質問のときにトークンを先に取るのは LLM の枠を無駄にしないためで、解答の照合は LLM を呼ばないので、その理由が当てはまらない。トークンが古いだけで正解者が出なかったことにはしない。

## 合成ページには、ゲームを終えるまで正解を渡さない（#378）

合成ページの素材は、最後に始めたゲームの区分とカードの一覧を丸ごと受け取る（`worker/chat-deduction-board.ts` の `readChatDeductionBoard`）。正解の表記はゲームを終えたあと（`ended_at` がある）にだけ載せる。合成ページの応答と押し出しはオーバーレイ用キーさえあれば読め、OBS のブラウザソースの中身は配信者の手元の開発者ツールからも見えるので、開催中に載せると画面に出していなくても答えが漏れうるからである。「正解は○○でした」は終えたあとに届く正解の表記だけから作る。

## カードにするのは、答えた質問と正誤を決めた解答だけにする（#378）

ポイントを返した質問・解答（ゲームの外・待ち時間の内・上限・LLM が答えられなかった・照合までにゲームが終わっていた）は映さない。視聴者にとっては無かったことになる交換で、映すと「答えてもらえなかった質問」が並んで、ゲームの進み方が読み取りにくくなるためである。答え待ち・照合待ちも映さない（LLM の答えが出てから1枚として出るほうが、出現のアニメーションで変化に気づける）。

質問と解答は別の表にあるが、1つの一覧にして答え・正誤を決めた順（`settled_at`）に並べる。配信を見ている人が知りたいのは「何が分かってきたか」と「誰が外したか」の流れで、質問と解答を分けて並べると時系列が切れるからである。合成ページは新しいものを上にして5枚まで並べ、それより古いカードは出さない（並べる数は中央の板に収まる数）。

## 押し出しの失敗は、開始・終了では502、交換の処理では記録にする（#378）

ゲームを始めた・終えた・質問に答えた・解答の正誤を決めたたびに、カードの一覧を AlertChannel の目印 `chatDeduction` で押し出す。開始・終了の経路で押し出せなかったときは、意見ボードと同じく、始めた・終えたことは取り消さずに502（`chat-deduction-push-failed`）を返す。報酬の切り替えはもう済んでおり、それを巻き戻すほうが配信者にとって分かりにくいからである。質問と解答は Twitch へ応答を返したあと（`waitUntil`）なので、押し出せなくても投げずに `chat-deduction-push-failed` を記録し、交換の更新は続ける（押し出しの失敗で視聴者のポイントを宙に浮かせない）。どちらの場合も、合成ページはつなぎ直したときと5分おきに読み直して追いつく。

## 板は画面の横ではなく中央に大きく出す

段階4（#378）では、作業机と同じく画面の横の余白に置く縦長の素材（600×760px）にした。しかしこのゲームは配信中ずっと流すものではなく、遊んでいるあいだは質問と答えの流れそのものが配信の主役になる。横の余白の小さな文字では、視聴者が「何が分かってきたか」を読み取りにくい。そこで素材の推奨の大きさを配信画面と同じにし（`src/overlay/layout.ts`）、カードの板を箱の中央に大きく置く（`chat-deduction.css`。板は 1280×1040px を上限に箱へ収める）。文字を大きくしたぶん、返事（60文字まで）が2行に折り返したカードでも板からあふれないよう、並べるカードを6枚から5枚に減らした。漢字クイズ・意見ボードと同じく、遊ぶあいだだけ表示し、ほかの場面ではオーバーレイの表示を切り替えて隠す使い方を想定する。

## 板を画面いっぱいに広げ、カードを3列×4行の格子に並べる

中央の板（1280px 幅）に縦一列で5枚を並べる形では、配信画面の左右が空いたまま、早い質問から画面の外へ消えていった。推理では「これまでに何が分かったか」を一度に見渡せることが肝心なので、板を箱いっぱいに広げ、カードを3列×4行（12枚）の格子に古いものから読む順に並べた（`view.ts` の `MAX_VISIBLE_CARDS`）。新しいものを上に積む並びをやめたのは、格子では左上から読むのが自然で、カードが増えるたびに全部の位置がずれるのを避けるためである。古いカードが外れても何問目かが分かるよう、質問にはゲームの初めから数えた通し番号を付けた。

- 行の数は、1920×1080 の配信画面で質問と1文がそれぞれ2行に折り返したカードが収まる数を、実際の画面で見比べて決めた。5行（15枚）では返事の2行目が切れた
- 正誤の印はカードの左ではなく上の行（通し番号・名前と同じ行）に置き、本文にカードの幅いっぱいを使う。答えの色はカード全体の塗り・枠・下側の厚みで伝わるので、印が小さくても見分けられる
- 見た目は、白地に原色・状態を色面で伝える・下側の厚み・丸みのある形、という型に寄せた。暗い半透明の板と細い色の線より、遠目に「はい」と「いいえ」の数の偏りが読み取れるため。OBS のブラウザソースは OS の明暗と関係なく映るので、色はライトの値に固定している
- 終えたときの正解の帯は、下端ではなく見出しの位置に重ねる。下端に重ねると、最後に並ぶ正解のカードを隠してしまうためである
- 板の背景は透明にし、見出しの帯とカードだけを白地と影で浮かせる。はじめは板そのものを画面いっぱいの白地にしていたが、遊んでいるあいだ配信画面（ゲームの画面やカメラ）がまったく見えなくなった。透明にすると、カードの隙間とまだカードの無い行から配信画面が見え、どんな画面の上でも影で見出しとカードの輪郭が読める
- 素材の箱はタテヨコ100%のまま、板の上下左右に配信画面のおよそ5%（上下54px・左右96px）の余白を取る。カードが12枚そろっても、画面の縁は配信画面のまま残すためである。余白のぶんカードが低くなるので、質問と返事がそれぞれ2行に折り返したカードが4行に収まるよう、文字を約0.9倍にした（3行に減らすと一度に見渡せる質問が減るため、文字を小さくするほうを選んだ）
- 合成ページは縮小されず、素材の箱はオーバーレイの実際の画素に対する割合で置かれる。そのため大きさを画素で固定すると、1280×720 の配信ではカードがあふれる。大きさはすべて 1920×1080 での画素数に、配信画面に合わせて縮む1画素ぶんの長さ（`--u`。`100vh / 1080` と `100vw / 1920` と `1px` の最小）を掛けて決める。文字と余白だけを縮めても、カードの内側の余白・枠・厚みが固定のままでは 1280×720 で4行に収まらないため、すべてを同じ割合で縮める。container query の単位なら箱の大きさに合わせられるが、OBS のブラウザソースの Chromium が古い版では使えないため、ビューポートの単位にした（素材はオーバーレイいっぱいに置く前提）
- 終えたときの正解の帯は、見出しの帯と同じ高さにする（正解の文字を見出しと同じ大きさにし、枠のぶん内側の余白を詰める）。帯が高いとカードとの間が詰まって窮屈に見えるため

## 終えたゲームは、正解を1分映してから消す

段階4（#378）では、最後に始めたゲームを、次のゲームを始めるまで映し続けていた。実際に使うと、遊び終えたあとも板が画面に残り続け、配信者がオーバーレイの表示を手で切り替えないと消えなかった。そこで、終えたゲームは「正解は○○でした」を1分（`ENDED_GAME_REVEAL_MS`）映してから板ごと消す。

消す判断は Worker ではなく合成ページの表示（`src/chat-deduction/view.ts`）が、終えた時刻（`endedAt`）とその端末の時計から行う。Worker の応答から終えたゲームを外す形にすると、1分たった瞬間に押し出しが無いので、合成ページは次に読み直すまで消えない。開き直したときにもう1分を過ぎていれば、最初から映さない。端末の時計がずれていれば映す長さもずれるが、数秒のずれは問題にならない。

プレビューのサンプル（`demo.ts`）は終えた時刻が固定なので、消すと正解の場面が映らない。サンプルでは消さない（`hideEndedGame: false`）。管理画面に「画面から消す」ボタンを置く案もあったが、配信中に押す操作を増やさないため自動で消す形にした。

## 音は、一覧の差から合成ページが鳴らす

場面ごとに BGM と効果音を選べるようにした（枠は BGM・開始・回答・不正解・正解・打ち切りの6つで固定。`src/chat-deduction/sound.ts`）。回答の音を はい・いいえ・分からない で分ける案もあったが、枠を増やすと選ぶ手間が増えるので1つにした。設定の形・検証・保存（KV の `chat-deduction-sound`）・選ばれている素材を消させない扱いは漢字クイズの音と同じにし、画面は漢字クイズのようなトリガーのページではなく、ゲームを操作する `/chat-deduction/` に置いた（このゲームはトリガーの動作ではないため）。

漢字クイズは1回の出題の長さが決まっているので、経過時間から鳴らす時刻の表を作る。このゲームは長さが決まっておらず、場面は Worker の押し出しで進む。そこで Worker はできごとを別に送らず、押し出す一覧（`ChatDeductionBoard`）に音の設定（音声の URL）を載せ、合成ページが前の一覧との差から鳴らす音を決める（`src/chat-deduction/sound-cues.ts`）。一覧と別に音の設定を読ませると、設定を読み終える前に届いた押し出しの音を鳴らせないためである。

- 効果音は押し出しで届いた一覧でだけ鳴らし、開いたとき・つなぎ直したとき・5分おきの読み直しでは鳴らさない。読み直しで鳴らすと、つなぎ直すたびに昔のカードの音がまとめて鳴るため
- BGM は読み直しでも一覧に合わせる。開催中に合成ページを開き直しても流れ、見逃した終わりでも止まるようにするため
- 正解で終えたときは正解の音だけを鳴らし、打ち切りの音は鳴らさない（打ち切りの音は配信者が「終える」で終えたときだけ）
- BGM を流しているあいだは、配信の BGM を下げておく長さ（2分）を1分おきに送り直す。漢字クイズ・市町村紹介は終わる時刻が分かるので1回で足りるが、このゲームは終わりが分からない。長さを区切って送り直すのは、合成ページが閉じられても配信の BGM が下がったまま残らないようにするため
- 保存した音は開催中の合成ページへ押し出さず、次の押し出し・読み直しの一覧から使う。保存のたびに押し出すと、失敗の扱い（保存を取り消すか）を新たに決める必要があり、ゲームの前に選んでおく使い方では困らないため
- Audio 要素の操作は漢字クイズの `sound-player.ts` と同じものが使えるので、`src/core/sound-player.ts` に移して共有した
