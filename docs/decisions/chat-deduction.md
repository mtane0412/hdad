# チャットで推理（`/chat-deduction/`）

視聴者が「はい／いいえ」で答えられる質問を繰り返して答えを絞り込み、当てるゲームを、issue #375〜#378 の4段階で作る。ここには段階1（#375）までの判断を書く。参考にした既存のゲームはあるが、その名前はリポジトリに残さず、機能の名前は「チャットで推理」とした。

## 質問と解答はチャンネルポイントで受ける

チャットの発言から質問と解答を拾う案（`!q`・`!a` のコマンド、または「？」で終わる発言を質問とみなす）もあったが、チャンネルポイントの報酬（ユーザー入力つき）で受けることにした。質問1件ごとに LLM を呼ぶので、雑談の疑問文まで拾うと呼び出しの回数が視聴者の発言数しだいになる（`docs/principles.md` の方針8）。ポイントを払う形なら、参加する意思のある質問だけが届く。報酬はゲームのあいだだけ交換できるようにし、ゲームの外では視聴者の画面に出さない。

## 報酬は HDAD が作り、既存の報酬を選ばせない

Twitch が報酬の更新（交換できるかどうかの切り替えを含む）を許すのは、同じ Client ID で作った報酬だけである（`docs/decisions/rewards.md`）。Twitch のダッシュボードで作った報酬を選ばせると、ゲームを始めるときに初めて403で失敗する。そこで `/chat-deduction/` に「報酬を作る」を置き、HDAD が2つの報酬を作って ID を控える。選択欄すら置かないので、打ち間違い・選び間違いも起きない（方針2）。必要ポイントや説明を変えたいときは、HDAD が作った報酬なので `/rewards/` でそのまま変えられる。

切り替えには `is_enabled` だけを送る Helix の更新（`setCustomRewardEnabled`）を足した。既存の `updateCustomReward` は全項目を送るので、ゲームの開始と終了のたびに配信者が `/rewards/` で変えた値を読み直して送り返す必要があり、読み書きのあいだに変えた値を戻してしまうおそれがあるためである。

報酬は待ち行列に入れる形（`should_redemptions_skip_request_queue: false`）で作る。受け付けなかった質問のポイントを返す（交換を CANCELED にする。#376）には、交換が未完了のまま残っている必要があるためである。

## 切り替えに失敗したら、開始も終了も黙って進めない

開始では、ゲームの行を作ってから報酬を交換できるようにする。報酬を切り替えられなかったときに行を残すと、視聴者が参加できない「開催中」のゲームができてしまうので、行を消して始めなかったことにする。2つの報酬は順に切り替えるので、片方だけ交換できるようになっている場合があり、交換できない状態へ戻してから失敗を返す。戻すのにも失敗したら、そのこともメッセージに添えて `/rewards/` で確かめるよう促す（方針4）。

終了では、先に報酬を交換できないようにし、それが済んでから行を終える。逆の順にすると、報酬の切り替えに失敗したときに「終わったのに交換できる」状態が残り、視聴者のポイントが答えの出ないゲームに消える。

## 問題集は自前で持ち、正誤は別名との照合で決める

問題（人物・場所・出来事・もの）は `src/chat-deduction/problems.json` に配信者が確かめたものだけを持つ（漢字クイズの問題集と同じ考え方）。質問への答えは LLM に作らせるが、材料は問題集の正解と事実メモだけに限り、メモに無いことは「分からない」と答えさせる（#376）。LLM の知識だけで答えさせると、もっともらしい作り話で視聴者を誤った方向へ導いても気づけない。

解答の正誤は LLM に判定させず、別名の一覧との完全一致で決める（#377）。正解かどうかでゲームが終わるので、同じ解答が呼び出しのたびに違う判定にならないようにするためである。表記の揺れは、問題を作るときに別名として書き足して吸収する。

## 問題集は Worker と画面で同じものを読む

問題集は、Worker（開始のときの問題の確かめ・質問への答え・解答の照合）とアプリのページ（問題を選ぶ欄）の両方が読む。2か所に書き分けると食い違うので、漢字クイズと同じく Worker から `src/chat-deduction/` を読み込む例外にした（`.claude/rules/implementation.md`）。
