# 利用者向けの説明の置き場（`README.md` と `docs/guide/`）

## README を入口だけにした

`README.md` は 711 行まで肥大化していた。壁紙のパラメータ表からWebhookの署名の確かめ方まで、1つのファイルに全機能の説明が縦に積まれていたため、次の2つが同時に起きていた。

- **初めて見た人が全体像をつかめない** — リポジトリを開いて最初に読む場所なのに、5つ目の画面の説明を読み終えても「何ができるものか」が分からない
- **1機能を直すたびに衝突する** — 機能を追加する issue ごとに同じファイルの別の場所へ追記するため、差分が読みにくい

そこで 2026-09-28 に、機能ごとの説明を `docs/guide/<話題>.md` へ原文のまま切り出し、`README.md` には「何ができるか」「使いはじめ方（Deployボタン）」「文書への行き先」「開発コマンドの要約」「ライセンス」だけを残した。

## 機能ごとに1ファイルにした（分類ごとにまとめなかった）

「素材」「アシスタント」のような分類ごとの1ファイルにはしなかった。`.claude/rules/` が話題ごとに分かれていて、直す機能と直す文書が1対1で対応するほうが、約束・経緯・利用者向けの説明の3つを同じ粒度で追えるためである。トリガーの決め方（元の「アラートの設定と素材」）だけは、アラートを使う人が続けて読むものなので `docs/guide/alerts.md` に寄せた。

## `docs/guide/` を作った（`docs/` 直下に置かなかった）

`docs/decisions/` と同じ話題名のファイル（`chat.md`・`bot.md` など）が並ぶため、`docs/chat.md` と `docs/decisions/chat.md` のどちらを指しているのかが読み手にも書き手にも紛れる。ディレクトリを分け、`docs/guide/` は**利用者向けの説明**、`docs/decisions/` は**判断の経緯**と役割で区切った。

## ライセンスを MIT にした

`LICENSE` が無く、`package.json` にも `license` が無かったため、フォークして自分の配信で使うことを勧めている（Deployボタン）のに、利用の条件が示されていなかった。フォークと改変を妨げない最も短い条件として MIT を選び、`LICENSE` と `package.json` の `license` の両方に書いた（`private: true` のままなので npm には公開しない）。
