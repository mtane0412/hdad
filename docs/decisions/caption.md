# 字幕（素材の種類 `caption`）

issue #190。アプリの枠の音声認識（issue #189。`src/transcript/recognition-context.tsx`）が認識した暫定・確定の文を、合成ページの素材「字幕」へ流す。ゆかコネNEO が出していた字幕を置き換えるためのもので、翻訳（issue #191）とゆかコネNEO の中継の撤去（issue #192）はこの後に続く。

## 配り方は手書きの Durable Object を別の名前で使う

字幕を配る仕組みとして、新しい Durable Object のクラスを足さず、**手書きの中継 `DrawChannel`（`worker/draw-channel.ts`）を、名前 `caption` の別のインスタンスとして使う**。

- 役割が手書きと同じである。送る側（アプリの枠）から見るだけの側（合成ページ）へ、中身を読まずに配る。送る側と見るだけの側を受け入れるときの目印（タグ）で分けるところも同じで、オーバーレイ用キーだけでは字幕を出せない
- インスタンスを分ければ、手書きの線と字幕は互いの接続にも負荷にも混ざらない（手書きは1本の線で毎秒20〜30通流れる）
- 同じ作りのクラスを2つ持たずに済み、Durable Object の追加（`wrangler.jsonc` のマイグレーション）も要らない。新しいクラスを足すと PR ブランチのプレビュービルド（Workers Builds）が失敗することも避けられる

採らなかった案:

- **アラートの配送（`AlertChannel`）に相乗りする**: アラートは「Workerが押し出し、DOは配るだけ」で、接続から接続へ中継する作りを持たない。話しているあいだは1秒に数通流れるので、アラートの配送がこの負荷を被る
- **新しいクラス（`CaptionChannel`）を足す**: 名前は分かりやすくなるが、中身は `DrawChannel` の写しになる。翻訳（issue #191）で字幕の中継先が中身を読む必要が出たら、そのときに分ける

翻訳（issue #191）も、訳文をアプリの枠が字幕の中継先へ送る形にしたので、中継先は中身を読まないままでいられる（下の「翻訳」）。

経路は手書きと同じ置き分けで、送る側は配信者のセッションで守る `GET /api/admin/caption/socket`（`worker/caption-routes.ts`。WebSocketはGETなので `Origin` も自分で確かめる）、見るだけの側はオーバーレイ用キーで守る `GET /api/overlay/caption`（`worker/overlay-routes.ts`）である。

## 送るのは認識しているタブだけ

アプリの枠の中でも、字幕の中継先へつなぐのは Web Locks の鍵を取って認識している1つのタブだけにする。鍵を待っているタブもつなぐと、そのタブが送る「途中の文が空」の知らせが、認識しているタブの字幕を消してしまう。

話している途中の文は、認識の状態が変わるたびではなく**途中の文そのものが変わったときだけ**送る（状態はつなぎ直しの回数などでも変わる）。空になったことも送る（話し終えた・認識が途切れたことを字幕から消すため）。確定した文は、記録（`POST /api/admin/transcripts`）とは別に、届いたその場で字幕へ送る（記録の応答を待つと字幕が遅れる）。

つながっていないあいだの分は貯めずに落とす。字幕は流れていくもので、つなぎ直してから古い文が現れるほうが紛らわしい。

## 見た目の既定を決め切る

`docs/principles.md` の方針1に従い、行数・位置・消えるまでの時間を設定項目にしない。値は `src/caption/captions.ts` と `src/caption/caption.css` だけが持つ。

- **2行まで**（`CAPTION_LINES`）。確定した直前の1文と、いま話している途中の文が並ぶ。それより多いと配信の画面を隠す
- **確定した行は6秒で消す**（`FINAL_LIFETIME_MS`）。2026-10-01 の配信では1発話が平均14文字ほどで、読むのに3〜4秒かかる。次の発話が続けて確定しても前の行は上に残るので、少し長めに取る
- **1行は末尾の76字まで（訳文は160字まで）。先頭は「…」で落とす**（`CAPTION_MAX_CHARS`・`TRANSLATION_MAX_CHARS`・`tailOf`）。Web Speech API は話し続けるあいだ文を確定しないので、2026-10-02 の配信では 229 発話のうち 20 件が76字を超え、最長は268字（折り返すと約7行・高さ約420px）だった。箱は配信画面と同じ大きさなので「はみ出したら隠す」では止まらず、2行と訳文で画面の半分を埋めた。新しく話した言葉が見えるよう末尾を残し、残す部分の前半に空白（話の間・英語の単語の切れ目）があればそこから始める。CSSで箱の高さを制限する案は、文字の途中の高さで切れ、何が映るかをテストで確かめられないので採らなかった。長い確定文を区切りで分けて順に映す案は、確定文がまとめて届くので話した時刻とずれ、仕組みも重くなるので採らなかった。字数での見積もりなので、英数字の多い行は見た目の行数とずれる
- **途中の文は10秒書き換わらなければ消す**（`INTERIM_LIFETIME_MS`）。認識していたタブが閉じられると「途中の文が空」の知らせが届かず、話しかけの文が配信画面に残り続けるため
- **箱の下端に中央寄せ、白い太字に黒の縁取り**。板を敷くと何も話していないときにも板の分だけ画面を隠すので、文字だけにする。素材の箱は配信画面と同じ大きさを推奨にし（`src/overlay/layout.ts` の `RECOMMENDED_ITEM_SIZES`）、下端の余白はCSSで取る（サイドスーパー・再生中の曲と同じ考え方）

映す行は届いた時刻と「いまの時刻」だけから決め（`visibleCaptions`）、合成ページの描画ループが毎フレーム呼ぶ。消すためのタイマーを持たない。表示（`src/caption/view.ts`）は前と同じ行なら要素に触れない。

## 失敗の出し方

手書きと同じく、**字幕の箱には切断を出さない**。字幕の箱はふつう配信画面と同じ大きさに置くので、失敗の表示（箱全体を塗る）が配信画面全体を覆う（手書きの issue #174 と同じ問題）。箱に出すのは一度もつながらないときと、届いた1通が読めないときだけである。

送る側の失敗（つながらない・切れた）は、コネクターのページの Web Speech API の区画に出す（`RecognitionContextValue` の `captionWarning`）。認識と記録は字幕とは関係なく続ける。

## 翻訳（issue #191）

確定した発話を Worker で英語に訳し、字幕の原文の下に添える。ゆかコネNEO が出していた翻訳の字幕を置き換えるためのものである。

### 経路は記録と分ける

訳文は、確定した発話の記録（`POST /api/admin/transcripts`）の応答には載せず、**別の経路 `POST /api/admin/translations`（`worker/translation-routes.ts`）で受け取る**。当初はこの節の前に書いたとおり記録の応答に載せるつもりだったが、次の理由で分けた。

- 記録は配信中しか行わないが、訳は配信の前の試し（字幕の見え方を確かめる）でも要る
- 記録は失敗すると同じメッセージIDで送り直す（`src/transcript/delivery.ts`）。訳を同じ要求に混ぜると、送り直しのたびに訳し直して料金と無料枠を使う
- 訳は提供元によって数秒かかる。記録の応答を訳に待たせると、記録の失敗と訳の失敗を見分けにくくなる

どちらの経路もセッションで守る。訳すたびに料金や無料枠を使うので、配信画面に映りうるオーバーレイ用キーでは呼ばせない。

### 訳文と原文はIDで結ぶ

アプリの枠は確定した1件ごとに UUID を作り、`final` と `translation` の両方に載せる（`src/caption/message.ts`）。記録のメッセージID（`webspeech:<UUID>`）とは別に作る。記録は送り直しで状態が変わるもので、字幕とは切り離しておきたいためである。

合成ページは訳文を同じIDの確定した行の下に添え、**訳文が届いた時刻から `FINAL_LIFETIME_MS` 映す**（訳は原文より遅れて届くので、原文の時刻のままだと訳を読む前に消える）。**添える先の行がもう消えていれば訳文は捨てる**（消えた行を訳文で呼び戻すと、話の流れから遅れた字幕が現れて紛らわしい）。行数の上限（`CAPTION_LINES`）は原文の行で数え、訳文は原文の行の一部として扱う。訳文は原文より小さい文字で出す（同じ大きさだと、どちらが元の発話か見分けにくく、画面も隠しすぎる）。

### 訳すのは確定した文だけ・英語だけ

暫定の文は訳さない。認識が書き換わるたびに訳すと、料金と字幕のちらつきが増える。訳す先は英語だけで、設定項目にしない（`docs/principles.md` の方針1。2言語にすると DeepL Free の月50万字を超える見込みでもある）。

### 提供元を選べるようにする

提供元は `worker/translation-config.ts`（KVは `translation-settings`）が決め、`/llm/` の区画（`src/llm/translation-card.tsx`）で選ぶ。

| 提供元 | 呼び方 | 文脈（直前の2件） |
|---|---|---|
| 訳さない（既定） | 呼ばない | — |
| LLM | `worker/llm.ts` に箇所 `translation` を指名する。提供元とモデルは LLM の設定の表の行で選ぶ | 指示に添える |
| m2m100 | Workers AI の `@cf/meta/m2m100-1.2b`（`source_lang: 'ja'`・`target_lang: 'en'`） | 渡せない |
| DeepL | DeepL API Free（`api-free.deepl.com`。`target_lang` は `EN-US`）。鍵はシークレット `DEEPL_API_KEY` | `context` で渡す（課金されない） |

- **既定は「訳さない」にした**。提供元を選ぶまで料金も無料枠も使わない。どれを既定にするかは、実配信で質と遅れを比べてから決める（issue #191 の完了の条件）
- **LLM のモデルの選び方は二重に持たない**。LLM の呼び先を決めるのは `worker/llm.ts` だけという約束（`docs/decisions/llm.md`）に合わせ、`LLM_USAGES` に `translation` を足した。翻訳の区画は「LLM で訳す」ことだけを選ぶ
- **選択の置き場所を `/llm/` にした**。LLM でない提供元も並ぶが、使用状況（`llm_usage`）を同じ表で見られるほうが料金の見当を付けやすい。LLM の箇所の表とは保存のボタンを分けた（KVのキーも検証も別で、片方の問題点のせいでもう片方を保存できなくならないようにする）
- **直前の2件を文脈として渡す**。1件の発話は平均14文字と短く、主語や指示語を取り違えやすい。文脈はアプリの枠が覚えている直前の確定した2件で、Worker は3件以上を拒む
- **Google 翻訳は見送った**（issue #191 では候補だったが、この段階では Cloud Translation API の課金アカウントの登録と、Apps Script を経由する方式のどちらにするかを決めていない）

### 使用状況と失敗

LLM で訳した回数は `llm.ts` が記録する。m2m100・DeepL で訳した回数も `worker/translation.ts` が `llm_usage` の箇所 `translation` へ足し込む（`/llm/` の「字幕の翻訳（LLM）」の行に並ぶ。DeepL の提供元は `deepl`・モデルは `deepl-free`）。DeepL の無料枠の残りは `GET /api/admin/translation/deepl-usage`（DeepL の `/v2/usage`）から読み、鍵があるときだけ区画に出す。

**失敗は黙って別の提供元へ落とさない**（`docs/decisions/llm.md` と同じ）。訳せなかったら502で理由を返し、`collection_failures` に `translation-failed` として残す。アプリの枠は原文を訳の前に送っているので、訳せなかった1件のために原文の字幕は止まらない。理由はコネクターのページの区画に出し、次に訳せたら消す。

LLM 以外の提供元は15秒で待つのをやめる（`TRANSLATION_TIMEOUT_MS`）。確定した行は6秒で消えるので、それより遅い訳は添える先が無い。
