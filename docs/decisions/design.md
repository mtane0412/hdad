# ページUIの見た目（デザインの土台）

## shadcn の初期値のままだと、AIが作った画面に見える

ページUIを機能ごとに足していくうちに、どのページも「ページの見出し → 箱（見出し＋灰色の説明文）→ 入力欄 → 黒いボタン」という同じ型になり、AIが作った画面に見えるようになった。2026-10-16 に本番の全16ページを明暗で撮って数えたところ、値のばらつき（任意値25件・生の色クラス10件）は小さく、問題は shadcn の初期値（無彩色・Geist・見出し18px／箱の見出し16pxで階層が平ら）がそのまま全ページの型になっていることだった。説明文付きの箱は43個中32個あり、ページ名と箱の見出しが同じページ（手書き・視聴者・テキスト）もあった。

## 好きな道具（Linear・Cloudflare）を実測して決めた

配信者が好きな道具は Linear と Cloudflare のダッシュボードで、好きな点は「Webアプリとしてシンプルで機能的、整理されて迷わない、データの型がわかる、要所でグラフィカル」だった。両者を同じ方法で計測すると、どちらも欧文は Inter、本文は 13px/500 で、見出しは大きさではなく太さと灰色の濃さで分けていた。Cloudflare の灰色は shadcn の初期値と同じ値で、AI臭さは灰色の値そのものからは来ていない。

計測した値を本番の画面に差し込んで比べると、配色・書体・箱の描き方を差し替えるだけでは印象の差は小さかった。効くのは区画の型と、データの型ごとの見せ方（状態の点・等幅の識別子・右揃えの数値など）と、図の置き場所である。そこで次の段階に分けた。

1. 土台: 色・書体・大きさ・区画（この記録）
2. データの型ごとの表示部品と見本ページ
3. トリガーとチャンネルポイントを「1項目＝1行」の一覧にする（行はその場で下に開く。トリガーのページは「トリガー／演出の設定／配信画面への出し方」のタブに分ける）

## Linear の組み方（案A）を選んだ

Cloudflare 寄り（灰色の帯の見出しで区画を箱に入れる）と Linear 寄り（箱を作らず区切り線だけ、灰色の地に本文のパネルを浮かせる）を同じページに当てて比べ、配信者が Linear 寄りを選んだ。

- 色は無彩色ではなく、Linear と同じく、ごくわずかに青みのある灰色（色相285）にする
- 和文の書体は Inter が持たないので OS の角ゴシックに任せる（Linear も同じ）
- 暗い表示では主ボタンが明るい灰色になり、押せないボタンと見分けにくかった（2026-10-16 の棚卸し）。主ボタンの明るさを上げた

## コントラスト比をテストで確かめる

トークンを見た目の好みで変えると、読めない組み合わせを作りうる。`src/app/theme.test.ts` が `app.css` の明暗のトークンを読み、文字と背景の組み合わせを WCAG 2 のコントラスト比で測る。最初に書いた時点で、shadcn の初期値の `--muted-foreground` が `--muted` の上で 4.34:1 しかなく、下限（4.5:1）を下回っていたことが見つかった。

## 色は意味の名前で持ち、生の色を Lint で禁止する

土台のPR（#390）の時点で、生の色クラスはコメントの「未挨拶」（琥珀色）・文字起こしの状態の点（緑・琥珀色）・保存できた印（緑）・手書きの下地（黒）の10件だった。どれも意味（対応待ち・成功）を持つ色なので、色の名前ではなく意味の名前のトークン（`--attention`・`--positive`）にした。種類を見分けるだけの色（トリガーの効果の種類など）は、良い・悪いの意味を持たせない `--tag-*` の10色に分けた。点や印は文字ではないので、コントラスト比は 3:1 を下限にしてテストに足した。

値の数が少ないうちに Lint で禁止したのは、AIが機能を足すたびに `text-amber-500` のような値を書き足すと、土台の約束がまた崩れるためである。配置の任意の値（`grid-cols-[...]`）は禁止しない。ページごとに列の組み方が違い、トークンにすると約束が増えるだけになるためである。

## 一覧の部品はリストにし、行を開く形まで部品が持つ

1項目＝1行の一覧（`DataTable`）は、最初は CSS grid の div に表の役割（table・row・columnheader・cell・rowgroup）を付けて組んだ。しかし実際にページへ当てると、行そのものを「押すと下に開くボタン」にするため、行とセルの構造に収まらなかった。そのためチャンネルポイント・アップロード・テキスト・視聴者の4ページは部品を使わず、それぞれ `ul`・`li` と見た目だけの見出しで同じ形を組み直していた（2026-10-16 の Interface Inventory で、部品が見本ページでしか使われていないと分かった）。

そこで部品のほうをページが実際に使っている形に合わせた。名前の付いたリスト（`ul`）に、行を `li`、列の見出しを見た目だけ（`aria-hidden`）にし、行を開くボタン（`aria-expanded`、開いているときだけ `aria-controls`）・開閉の矢印の場所・開いた詳細までを `DataTableRow` の `expand` に持たせた。開くのは1件ずつなので、どれを開いているかはページが持つ。行のボタンの名前は項目の名前から始める（チャンネルポイントのアイコンは、見た目では名前の左に置き、読み上げの順では名前の後ろにした）。列の幅は表に1回だけ渡し、CSS 変数 `--columns` で見出しと行に配る。

トリガーの一覧は、項目ごとの枠の中に複数の設定の行を持ち、区分ごとに畳めるので、この部品には移していない。

## 一覧の形を2つに分ける

行を押して下に開く `DataTable` と、shadcn の `Table` で行の中に入力欄を並べる表は、どちらも残す。分けかたは保存の単位である。

- **1件ずつ保存する項目**（チャンネルポイント・テキスト・視聴者のメモ）と、読むだけの項目（アップロード）は `DataTable`。開いた1件だけを書き換えて保存する
- **一覧ごと1回で保存する表**（チャットボットのコマンド・自動モデレーションのルール・BGMの曲）は `Table` の行に入力欄を並べる。表計算のように全部の行を見比べながら書き換え、まとめて保存するので、行を閉じて中身を隠す形は合わない
- 数を並べるだけの表（ダッシュボードの配信の一覧・LLMの使用状況）も `Table`

## 保存のボタンの型をそろえる

Interface Inventory では、保存のボタンの文言が「保存」「保存する」「音を保存」「コマンドを保存する」の4通りあった。トリガーのページの「演出の設定」のタブには「音を保存」が2つ（市町村紹介と漢字クイズ）並んでいた。未保存の印も、点と語（`StatusDot`）の場所と地の文の場所があった。ボットのページだけは、変更があるときにだけ保存のボタンを出していた。

そこで保存のボタンは `SaveBar`（`src/components/save-bar.tsx`）で出すことにした。

- 文言は「〜を保存する」。同じページに保存のボタンが2つ以上あっても取り違えないよう、何を保存するかを書く。開いた行の中では「保存する」と見せ、読み上げの名前に項目の名前を含める
- 未保存の印は、ボタンの横に `StatusDot`（対応待ちの色の点＋語）で出す
- ボタンはいつも出し、押せなくするのは保存の最中だけにする。変更が無いあいだも押せなくはしない。トリガーやオーバーレイには、読み込んだ値をそのまま保存し直すと形が整うこと（効果の無い行を送らない など）を確かめるテストがあり、変更が無くても保存に意味があるためである
- 1つのボタンでページ全体を保存するページ（トリガー・オーバーレイ）だけ、画面の下に貼り付ける

例外が2つある。下部バーのテキストの窓（`src/text/text-bar.tsx`）は、本文1つだけを書き換える小さな窓なので `SaveBar` を使わず、文言だけを「本文を保存する」にそろえた。この窓では本文を変えないあいだは押せないままにする。自動で書き換えているテキストは、保存すると手動に切り替わるので、変えていない本文を押し間違えて保存すると自動が止まってしまうためである。文字起こしの「ミュートを見張るOBSの入力」（`src/transcript/recognition-section.tsx`）も、入力欄1つと Enter で送る小さなフォームなので `SaveBar` を使わず、文言だけを「入力の名前を保存する」にした。
