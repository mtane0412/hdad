# トリガーの管理画面（`/triggers/`）

トリガーの管理画面（`/triggers/`）はアプリのページ（`src/admin/trigger-page.tsx`）で、素材の追加と削除だけはアップロードのページ（`/media/`、`src/admin/media-page.tsx`）に分けてある（トリガーのページは置いてある素材から選ぶだけである）。

どちらも「ボタンを押す → Workerを呼ぶ → 成功なら知らせ、失敗なら理由を出す」という同じ形をとるので、その状態と表示は `src/admin/page-actions.tsx` の `usePageActions` にまとめる（失敗を何行に分けて出すかだけをページが渡す）。ログインの確認とログアウトはアプリの枠が受け持ち、オーバーレイ用キーは枠から受け取る（再発行したら枠へ知らせる）。

Workerの呼び出し（`api.ts`。呼び出しと失敗の扱いは `src/core/api.ts` に任せ、`fetch` を差し替えてテストする。`worker/` の型は読み込めないので、応答の型をここで定義して形を確かめる）と入力欄の値の変換（`form.ts`）は画面から分けてテストする。

## 配信者はトリガーを作らない

**配信者はトリガーを作らない。** 起きうる出来事が区分（チャット・イベント・開発）ごとに**最初から固定で並んでいて**、そこに効果（動作）を追加していく（`form.ts` の `menuGroups` がそのまま画面の構成になる）。画面にイベント種別の選択欄も条件の追加ボタンも無く、開いた行に出るのは絞り込みのパラメータ1つ（`TriggerParamField`）と効果だけである。

**効果をひとつも持たない行は保存しない**（`hasAnyAction`・`toTriggerInputs`）ので、有効・無効の印も「トリガーを外す」操作も持たない（効果をすべて外した状態が「何も起きない」を表す）。読み込みと追加のたびに `withFixedRows` が、パラメータを持たない項目の行を追加して一覧の並び順にそろえる（保存する順も画面の並びと同じになる）。

## 複数の設定を持てる項目

**絞り込みが「別のもの」を指す3項目（報酬・言葉・ユーザー）だけは、項目の中に設定を複数持てる**（`MenuItem.addLabel` があるものがそれで、`multiple` はそこから導く）。報酬ごとに違う効果を付けるのが主な使い方なので、1行に限ると使えないためである。

日数（`comeback`）と広告（`automatic`）は絞り込みが1つで足りるので1行にする（「どちらでも」の行と「自動だけ」の行が並ぶと、既定メニュー化で解消した重複の分かりにくさが戻る）。

## 広告の開始と終了

**広告の開始と終了は1つの項目にまとめる**（`MenuItem.phases`。`AD_BREAK_ITEM`）。Workerへ送る形は `adBreakBegin`・`adBreakEnd` の2件のままで、まとめるのは画面の中だけである。

1つの行が複数のイベント種別を持つとき、**効果は種別ごとに分けて持ち（`ActionFields` を `MenuPhase.heading` 付きで並べる）、絞り込みのパラメータは行で共通**にする（開始と終了で「自動で入ったものだけ」を別々に選べても、食い違った設定に意味がないためである）。

片方だけが保存されていたときは `withFixedRows` が保存済みの行から絞り込みを引き継いで足りない行を作り、両方が保存されていて食い違うとき（別々の項目だったころの設定）は黙って寄せずに行の見出しの下で知らせる（Fail-Fast）。

## 区分の分け方

区分は**チャット**と**イベント**の2つで、チャットの並びは挨拶の3つ（細かい順＝優先順位）→ `everyMessage` → `keyword`・`fromUser` にする。

広告を「配信」という別の区分に置かないのは、配信者から見れば広告も応援と同じ「配信中に起きるイベント」の1つで、項目が2つだけの区分を作ると見出しのほうが中身より目立つためである。挨拶が排他であることは項目ごとには書けないので、区分の説明（`MenuGroup.description`）で知らせる。

Workerが返す問題点の位置（`triggers[0]`）は番号では場所が伝わらないので、送った順の項目の名前へ読み替える（`describeProblem` に名前を渡す）。メニューの並びと日本語の名前・差し込み語の対応は `form.ts` が持ち直す（`worker/` の型は読み込めないためである）。

## 一覧の見せ方

トリガーは項目が多いので、一覧では要約だけを見出しに出して折りたたみ、開くのは1件ずつにする（開いている位置はページが持ち、行を外したら後ろの位置をずらす）。

**カードは区分（チャット・イベント・開発）ごとに置き**（`TriggerGroup`）、その中に項目の枠（`ITEM_BOX`）を並べる。一覧の全体を1枚のカードで囲まないのは、その中に区分の見出しと項目の枠が入れ子で並び、どこまでが1つのまとまりか読み取りにくいためである。項目の枠にはカードの見た目（地色・影）を持たせない（カードの中にカードが並んで見えてしまう）。

**項目はすべて同じ枠に入れて並べる。** 1行だけの項目ではその枠自体がアコーディオンになり、複数の設定を持てる項目では枠の見出しの下に設定の行と「追加する」ボタンが入る（枠を持つ項目と持たない項目が混ざっていたころは、同じ一覧の中に押せる枠とただの見出しが並び、どこまでが1項目なのか読み取れなかった）。

階層は**カードと字の大きさで示す。** 区分の見出しは項目の見出しより大きくし、項目の見出しは枠の中に置く（どちらも同じ大きさだったころは区分と項目を見分けられなかった）。区分はカードの見出しを押して畳める（畳んだ状態はページが区分の名前で持つ。既定はすべて開く）。

見出しに出す要約は、**絞り込みの文言（`rowParamSummary`）と効果（`rowActionLabels`）に分ける**。効果はひと続きの文につながずバッジで1つずつ出し、ひとつも無ければ「効果なし」と出す（文末まで読まずに効果の有無が分かるようにするためである）。

## 差し込み語

**差し込み語は文言の欄ごとに、押して入れるボタンで並べる**（`MessageField`。並べるのはその項目で置き換わる語だけで、入るのはカーソルの位置である）。手で打つと綴りや括弧の間違いに気づくのが「配信中に置き換わらなかったとき」になるためで、一覧の下に「使える差し込み語」を書き並べていたころは、どの欄で使えるのかも打ち間違いも画面からは分からなかった。

文言の組み立て（`form.ts` の `insertPlaceholder`）は入力欄の要素を触る部分から分けてテストし、カーソルの移動は値が書き換わったあとに行う（`useEffect`。先に動かすと入力欄の値の書き換えで末尾へ戻る）。AIへの指示の欄にはボタンを出さない（文面はAIが書くので差し込み語を持たない）。

保存ボタンは一覧の下に貼り付け（`sticky`）、読み込んだ（保存した）時点の入力欄の中身と今の中身が食い違えば「未保存の変更があります」と添える（一覧が長く、一番下まで送らないと保存できない状態を避けるためである）。確認は `window.confirm` ではなく `AlertDialog` で行う。`/api/*` は `npm run dev` の中でも動く。
