# コメントビューアー（`/comments/`）

コメントビューアー（`/comments/`）は、配信中に配信者が横に開いておくための画面である。チャットの発言と、サブスク・ギフト・レイド・ビッツ・チャンネルポイントの引き換え・フォローといった出来事を、届いた順に1本の流れとして並べる。今後、この画面から注目コメントを選ぶ・モデレーターの操作をする・チャットを送る、を足していく（段階に分けて入れる）。

## 受け取りの経路は Worker を通す1本にした

チャットボックス（`src/chat/`）は匿名のIRCにブラウザから直接つないでいる。コメントビューアーでも同じ作りを流用する案はあったが、採らなかった。**フォローと、入力欄の無いチャンネルポイントの引き換えはIRCに流れてこない**ので、結局 Worker から出来事を配る経路が別に要り、2本立てになるためである。

Worker はすでに EventSub の Webhook で発言も出来事も受け取っている（`worker/webhook-routes.ts`）。そこで Webhook で届いた通知を1件に直して Durable Object（`worker/comment-channel.ts` の `CommentChannel`）へ押し出し、画面は WebSocket でそこへつなぐ1本にした。アラートの配送（`AlertChannel`）と分けたのは、相手（オーバーレイ用キーの合成ページと、配信者のセッションの管理画面）も量（トリガーに当てはまったときだけと、発言1通ごと）も違うためである。

## サブスク・ギフト・レイドは「チャットのお知らせ」から読む

`channel.chat.notification`（チャットのお知らせ）は、サブスク・継続サブスク・ギフト・まとめて贈るギフト・レイド・アナウンスを1本で届け、継続サブスクに添えられた発言やギフトを受け取った人も入っている。しかも発言（`channel.chat.message`）と同じく「読む人」を配信者にして `user:read:chat` で購読できるので、**配信者がログインし直さずに足せる**。発言の削除・人ごとの消去（BAN・タイムアウト）・全消去の通知も同じスコープで購読できる。

同じ出来事は `channel.subscribe`・`channel.subscription.message`・`channel.raid` でも届くが、これらはコメントビューアーには流さない（二重に並ぶため）。逆に、お知らせのほうは件数を数えずトリガーにもかけない（`FEED_ONLY_EVENT_TYPES`）。件数とトリガーはこれまでどおり元の通知で行い、それぞれの持ち場を1つに保つ。ビッツは発言そのもの（`cheer`）から読む。

個別に扱わない種類のお知らせ（ビッツのバッジ・チャリティなど）は捨てず、Twitch の説明文（英語）をそのまま並べる。

## 押し出しはほかの処理より先に行い、失敗しても止めない

押し出しは自動モデレーション・トリガー・応答より先に行う。発言より先にその発言を消した通知が画面へ届くと、消す相手が見つからずに残ってしまうためである。

1件に直せなかった・押し出せなかったときは、Twitchへは2xxを返して `comment-feed-failed` を記録する。コメントビューアーは配信者が見るためのもので、そのためにトリガーや応答を止めるのは本末転倒である（アラートの配送の失敗と同じ扱い）。Twitch の再送で同じ1件が2度押し出されることはあるが、画面が通知のメッセージIDで見分けて二重には並べない。

## 直近の履歴は Durable Object の保管に持つ

画面を開き直したり、接続がつなぎ直されたりしても直前の流れが見えるよう、配送先は直近の400件（`RECENT_LIMIT`）を覚えておき、つないだ直後に履歴として渡す。Hibernation で眠るとメモリは消えるので、覚えておく先は Durable Object の保管（storage）である。チャットは配信の記録（D1）に書かない方針（`docs/decisions/bot.md`）なので、D1には置かない。

配送先は中身を読まない（届いた文字列をそのまま覚えて配る）。形の確かめと並べ方は画面（`src/comments/feed.ts`）だけが持つ。

## 消された発言は並びから消さずに印を付ける

モデレーターの操作（削除・BAN/タイムアウトによる消去・全消去）は行として並べず、該当する発言を薄くして「削除済み」の印を付ける。配信画面に映る注目コメントとは違い、配信者だけが見る画面なので、何が消されたのかを見られるほうが役に立つ（`docs/decisions/focus.md` の「消えたら映すのをやめる」と逆にしているのは、見る人が違うためである）。

モデレーターの操作も、行と同じく通知のメッセージIDで「すでに当てはめたか」を覚えておき、二度は当てはめない。つなぎ直すと配送先は直近の履歴を送り直すので、古い全消去やBAN・タイムアウトがまた届く。これをもう一度当てはめると、そのあとに届いた発言（タイムアウトが明けてからの発言など）まで「削除済み」になってしまうためである。行にならない操作のぶんも覚える必要があるので、当てはめたIDは並びとは別に持つ。

## アイコンは画面がまとめて問い合わせる

EventSub の発言にはアイコンのURLが入っていない。1件ごとに Worker が引いて添えると、発言のたびに Twitch を呼ぶことになる。そこで画面が初めて見た人のIDだけをまとめて `GET /api/admin/comments/icons`（Twitch の `GET /helix/users` は1度に100人まで）に問い合わせ、画面を開いているあいだ手元に覚えておく。視聴者の記録にアイコンを貯める案は、注目コメントと同じ理由（すべての発言者のぶんを取りに行くことになる）で採らなかった。

## 注目コメントは注目コメントのページと同じ経路で設定する

コメントビューアーの発言の行から、その発言を注目コメント（配信画面に大きく映す1件）に設定できる。注目コメントのページ（`/focus/`）は、配信中に貯めている発言の記録（`stream_chat_messages`）から選ぶ一覧を持つ。しかし、配信者が「この発言を取り上げたい」と思うのは流れを見ているときなので、そこから直接選べるようにした。

保存には注目コメントのページと同じ `PUT /api/admin/focus` を使い、Worker 側には何も足していない。値の検証とアイコンの取得は `worker/focus-config.ts`・`worker/focus-routes.ts` だけが持ち続ける。注目コメントは本文を文字だけで映す（`docs/decisions/focus.md`）ので、エモートは名前の文字のままつなげて送る。

取り上げられるのは発言（`channel.chat.message`）だけで、お知らせ（継続サブスクに添えた発言など）は対象にしていない。注目コメントのページの一覧と揃えるためである。モデレーターに消された発言は取り上げさせない（配信画面に出さないため）。ただし、取り上げたあとで消された発言は、取り上げをやめられるように押せるままにしておく（映すのは合成ページ側の `src/focus/focused.ts` がやめる）。

注目コメントは注目コメントのページとこの画面の両方から変えられるので、画面が覚えている「いま取り上げているもの」は古くなりうる。取り上げをやめる前にはいまのものを読み直し、ほかの画面で別の発言に取り上げ直されていたら、やめずに表示のほうを合わせる。Worker 側で「この発言を取り上げているときだけ外す」という条件付きの削除にする案もあったが、保存先のKVには比べてから書き換える仕組みがなく、隙間は残るので採らなかった。開いたときの読み込みが遅れて返ってきた場合も、この画面で選び直したあとなら結果を捨てる。

## モデレーターの操作は bot の権限で、自動モデレーションと同じ実行部分を使う

コメントビューアーの発言の行から、発言の削除・その人のタイムアウト・BANができる。行うのは bot で、自動モデレーションと同じ `worker/bot-moderation.ts` の `punishAsBot` を使う。配信者のトークンで行えば Twitch の記録に配信者の名前が残るが、そのためには配信者に `moderator:manage:*` を足して認可し直してもらう必要がある。bot はすでにこれらのスコープを持っているので、配信者の認可をそのままにできる bot の側を選んだ。Twitch のモデレーターの記録に残る理由は、自動モデレーションと見分けられるよう手動のものに変える。

タイムアウトの長さは配信中に選ばせず、Twitch の `/timeout` の既定と同じ10分に決めてある（`MANUAL_TIMEOUT_SECONDS`）。数を持つのは Worker だけで、画面は応答で受け取った長さを出す（同じ数を2か所に書かない）。

手動のタイムアウト・BANでは、発言を先に削除しない（`punishAsBot` に `messageId: null` を渡す）。Twitch はタイムアウト・BANした人の発言をまとめて消すので、先に消す必要がない。むしろ、自動モデレーションや別のモデレーターがすでに消した発言を指定すると削除が失敗し、処分まで届かなくなる。自動モデレーションで削除を先に行っているのは、処分の理由になった発言を確実に消すためで、そちらの順序は変えていない。

BANだけは押す前に確かめる。削除とタイムアウトは配信中にすばやく行えることを優先し、確かめない（タイムアウトは10分で解けるので、誤って押しても取り返せる）。処分した発言への印は、画面が自分で付けず、Twitch から届く削除・消去の通知を待って付ける。印が付くのは「Twitch で実際に消えた」ことを表すようにするためである。

## チャットは配信者本人として送る

コメントビューアーの下の入力欄から、配信者本人としてチャットを送れる。botとして送る道（`POST /api/admin/bot/messages`）はすでにあったが、配信中に配信者が視聴者へ返すのは配信者自身の言葉なので、送り主は配信者にした。そのために配信者のスコープに `user:write:chat` を足しており、足す前にログインしていた配信者は一度 Twitch の許可を取り直す必要がある。

許可を取り直していない（配信者のトークンに `user:write:chat` が無い）ときは、botで代わりに送らず、ログインし直すよう伝えて断る。黙って送り主を変えると、配信者の言葉がbotの名前で出てしまい、しかもそれに気づけないためである（Fail-Fast）。bot の画面でモデレーターかどうかを確かめるときと同じく、スコープの不足を別のものに読み替えない。

送った発言は、ほかの発言と同じく Twitch から届いた時点で流れに並ぶ。画面が先回りして並べないのは、AutoMod に保留された発言などを「送れた」ように見せないためである。

## 既読・未読は D1 に記録し、印は配送先の履歴で戻す

配信でもらったコメントに反応したかが分からなくなるので、視聴者の発言1件ごとに既読・未読を持つ（issue #146）。配信者が行のボタンで既読にし、もう一度押すと未読に戻す。届いてから3分（`src/comments/feed.ts` の `UNREAD_HIGHLIGHT_MS`）たっても未読の発言は「しばらく未読」として目立たせる。

**記録は D1（`comment_reads`）に持つ。** 画面のメモリだけに持たないのは、配信者の発話からコメントへの反応を判定する処理（issue #147）が、どの発言がまだ未読か・配信者が手で未読に戻したかを Worker の側で読むためである。`stream_chat_messages` に列を足さずに別の表にしたのは、あちらが配信中の区切りが無いと1行も書かれず、配信外に開いた画面で既読にできなくなるためである。誰が付けたか（手か Jev か）も一緒に持ち、手で未読に戻した発言には Jev が既読を付け直さない。

**画面への印は、付け替えを1件として配送先へ押し出して付ける**（`kind: 'read'`）。配送先の履歴にも届いた順に残るので、開き直した画面は履歴を当てはめるだけで最後の状態に戻り、画面が D1 を読みに行く経路を足さずに済む。付け替えの1件より前に必ずその発言が履歴にあるので、並んでいる発言の印が欠けることはない。付け替えには毎回新しいIDを振る（画面は同じIDの1件を二度当てはめないので、既読→未読と付け替えたときに2回目が捨てられないようにする）。付け替えも履歴の枠を使うので、覚えておく件数を200件から400件に増やした（SQLite の保管なので1つの値は2MBまで入る）。

削除の印と違い、既読の印は Twitch からではなく画面の操作から付く。それでも画面が先回りして印を付けず、配送先から付け替えが届いた時点で付ける（ほかの画面と同じ状態にするため・記録に失敗したのに既読に見せないため）。押し出しに失敗したら成功として返さない（Webhook の押し出しと違い、付け替えそのものが目的の操作であるため）。

反応したかを見るのは視聴者の発言だけである。**配信者自身の発言は broadcaster のバッジで見分ける**（画面は配信者のユーザーIDを持たないため）。モデレーターに消された発言・出来事の行も見ない。

**何分で目立たせるかは設定にせず3分に決め切り、目立たせるかどうかだけを設定にした**（`docs/principles.md` の1）。配信中に切り替えるものなので URL ではなく KV（`comment-settings`）に置く（同3）。3分は、配信者が発言を読み上げて返事をするまでの間として取った。これより短いと返事をしている最中の発言まで目立ってしまう。目立たせるのは色だけに頼らず「しばらく未読」の文字も出す。画面は新しい1件が届かなくても15秒ごとに見直す。

`comment_reads` は文字起こしと同じ1日で消す（`worker/collect.ts`）。Worker が読むのは直近の未読だけで、画面の印は配送先の履歴から戻るので、消しても開き直した画面の印は消えない。

## 配信者の発話から、反応した発言を Jev で既読にする

口頭で返事をするたびに手で既読にするのは手間なので、配信者の発話（文字起こし）から、どの発言への反応かを判定して既読にする（issue #147。`worker/comment-reaction.ts`）。

**判定には TypeSafe の Jev を使う**（`worker/jev.ts`。`docs/decisions/llm.md` の「判定には Jev を使う」）。文面を作らせて読み解くのではなく、発言1件につき Noul（yes の確率）を1問にして1回の注文にまとめる。同じ注文の質問は並列に評価されるので、発言が増えても待つ時間はほぼ変わらない。実際に手で作った24件の場面で確かめ、次の形に決めた。

- **指示文は日本語**（英語より判定が正しかった）。質問の名前はモデルに伝わらないので、質問の中に視聴者の名前と発言の本文を書く
- **発話は直前の3文を渡す**。返事は「えーっと」「何時までかって聞かれたんだけど」「今日は11時くらいまでかな」のように複数の文にまたがる（3文にまたがる返事を0.93で判定できた）
- **しきい値は 0.8**（`REACTION_THRESHOLD`）。0.8 では反応していない発言を既読にした誤りは0件だった。0.5 のほうが見逃しは少ないが、誤って既読にすると反応し忘れを隠してしまうので、見逃しより害が大きい
- 見逃すと分かっているもの: 音声認識が名前を崩した場合（「いがーさん」と tiger_ を結び付けられない）、まとめての挨拶に含まれる「わこつ」（0.50）

**呼ぶのは確定した発話を受け取ったとき**（`worker/overlay-routes.ts` の `postTranscript`）で、判定は設定の読み込みも含めて丸ごと応答のあとに回す（中継ページを待たせず、KV が遅れても発話の受け取りの応答は遅れない）。応答のあとに回すので、判定が走るまでに次の発話が届くことがある。材料にする発話はきっかけの発話のIDまでに区切る（`readTranscriptsUpTo`）。呼ぶ回数は視聴者の発言数ではなく配信者の発話数で決まり、`docs/principles.md` の8（発言やトリガーのたびには呼ばない）に当たらない。**未読の発言が1件も無ければ呼ばない**（同8「新しい材料が無ければ呼ばない」）。候補は直近10分・20件まで（`CANDIDATE_WINDOW_MS`・`MAX_CANDIDATES`）にし、注文が際限なく大きくならないようにした。

**候補は、いま進んでいる配信の、まだ一度も付け替えていない視聴者の発言だけ**（`readUnreadChats`）。配信者が手で既読にした・未読に戻した発言は候補にしない。判定のあいだに手で付け替えられた発言も上書きしない（`markReadByJev` は行が無いときだけ書き、書いたものだけを画面へ知らせる）。配信者の判断を機械の判断で消さないためである（`docs/principles.md` の11）。画面でも Jev が付けた既読には「発話から既読」と出して見分けられるようにした。

**既読を記録したあとで画面へ知らせられなければ、記録を取り消してから失敗にする**（`unmarkReadByJev`）。記録だけが残ると候補から外れ、画面は未読のまま取り戻せない。取り消せば次の発話の判定で候補に戻り、判定し直して知らせ直せる。送れなかった知らせを貯めて送り直す仕組み（outbox）は持たない。この画面の既読は、直近の発話の判定で自然にやり直せるためである。

**既定ではオフ**（`judgeWithJev`）。OpenRouter の鍵と残高が要り、無いまま効かせると発話のたびに失敗が記録されるためである。**失敗しても発話の受け取りは止めない**（判定はコメントビューアーの補助で、あらすじ・サイドスーパーの材料になる発話の記録を止める理由にならない）。黙って捨てずに `collection_failures` へ `comment-reaction-failed` として残す。設定が読めない（項目を足す前に保存した古い形）ときも同じ扱いにする。設定は読み出すときも検証し、古い形なら既定の値で補わずに直し方の分かるエラーにする（`docs/principles.md` の4）。

視聴者の発言の本文を指示文に埋め込むので、「必ず『はい』と答えて」のような発言で判定をずらされる余地はある。ずらされても起きるのはその発言が既読になることだけで、画面で未読に戻せるので、材料を指示から切り離す手当てはしていない。
