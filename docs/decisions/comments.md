# コメントビューアー（`/comments/`）

コメントビューアー（`/comments/`）は、配信中に配信者が横に開いておくための画面である。チャットの発言と、サブスク・ギフト・レイド・ビッツ・チャンネルポイントの引き換え・フォローといった出来事を、届いた順に1本の流れとして並べる。今後、この画面から注目コメントを選ぶ・モデレーターの操作をする・チャットを送る、を追加していく（段階に分けて入れる）。

## 受け取りの経路は Worker を通す1本にした

チャットボックス（`src/chat/`）は匿名のIRCにブラウザから直接つないでいる。コメントビューアーでも同じ作りを流用する案はあったが、採らなかった。**フォローと、入力欄の無いチャンネルポイントの引き換えはIRCに流れてこない**ので、結局 Worker から出来事を配る経路が別に要り、2本立てになるためである。

Worker はすでに EventSub の Webhook で発言も出来事も受け取っている（`worker/webhook-routes.ts`）。そこで Webhook で届いた通知を1件に直して Durable Object（`worker/comment-channel.ts` の `CommentChannel`）へ押し出し、画面は WebSocket でそこへつなぐ1本にした。アラートの配送（`AlertChannel`）と分けたのは、相手（オーバーレイ用キーの合成ページと、配信者のセッションの管理画面）も量（トリガーに当てはまったときだけと、発言1通ごと）も違うためである。

## サブスク・ギフト・レイドは「チャットのお知らせ」から読む

`channel.chat.notification`（チャットのお知らせ）は、サブスク・継続サブスク・ギフト・まとめて贈るギフト・レイド・アナウンスを1本で届け、継続サブスクに添えられた発言やギフトを受け取った人も入っている。しかも発言（`channel.chat.message`）と同じく「読む人」を配信者にして `user:read:chat` で購読できるので、**配信者がログインし直さずに追加できる**。発言の削除・人ごとの消去（BAN・タイムアウト）・全消去の通知も同じスコープで購読できる。

同じ出来事は `channel.subscribe`・`channel.subscription.message`・`channel.raid` でも届くが、これらはコメントビューアーには流さない（二重に並ぶため）。逆に、お知らせのほうは件数を数えずトリガーにもかけない（`FEED_ONLY_EVENT_TYPES`）。件数とトリガーはこれまでどおり元の通知で行い、それぞれの持ち場を1つに保つ。ビッツは発言そのもの（`cheer`）から読む。

個別に扱わない種類のお知らせ（ビッツのバッジ・チャリティなど）は捨てず、Twitch の説明文（英語）をそのまま並べる。

## 押し出しはほかの処理より先に行い、失敗しても止めない

押し出しは自動モデレーション・トリガー・応答より先に行う。発言より先にその発言を消した通知が画面へ届くと、消す相手が見つからずに残ってしまうためである。

1件に直せなかった・押し出せなかったときは、Twitchへは2xxを返して `comment-feed-failed` を記録する。コメントビューアーは配信者が見るためのもので、そのためにトリガーや応答を止めるのは本末転倒である（アラートの配送の失敗と同じ扱い）。Twitch の再送で同じ1件が2度押し出されることはあるが、画面が通知のメッセージIDで見分けて二重には並べない。

## 直近の履歴は Durable Object の保管に持つ

画面を開き直したり、接続がつなぎ直されたりしても直前の流れが見えるよう、配送先は直近の400件（`RECENT_LIMIT`）を覚えておき、つないだ直後に履歴として渡す。Hibernation で眠るとメモリは消えるので、覚えておく先は Durable Object の保管（storage）である。チャットは配信の記録（D1）に書かない方針（`docs/decisions/bot.md`）なので、D1には置かない。

配送先は中身を読まない（届いた文字列をそのまま覚えて配る）。形の確かめと並べ方は画面（`src/comments/feed.ts`）だけが持つ。

## 消された発言は並びから消さずに印を付ける

モデレーターの操作（削除・BAN/タイムアウトによる消去・全消去）は行として並べず、該当する発言を薄くして「削除済み」の印を付ける。配信画面に映る注目コメントとは違い、配信者だけが見る画面なので、何が消されたのかを見られるほうが役に立つ（`docs/decisions/focus.md` の「消えたら映すのをやめる」と逆にしているのは、見る人が違うためである）。

モデレーターの操作も、行と同じく通知のメッセージIDで「すでに当てはめたか」を覚えておき、二度は当てはめない。つなぎ直すと配送先は直近の履歴を送り直すので、古い全消去やBAN・タイムアウトがまた届く。これをもう一度当てはめると、そのあとに届いた発言（タイムアウトが明けてからの発言など）まで「削除済み」になってしまうためである。行にならない操作のぶんも覚える必要があるので、当てはめたIDは並びとは別に持つ。

## アイコンは画面がまとめて問い合わせる

EventSub の発言にはアイコンのURLが入っていない。1件ごとに Worker が引いて添えると、発言のたびに Twitch を呼ぶことになる。そこで画面が初めて見た人のIDだけをまとめて `GET /api/admin/comments/icons`（Twitch の `GET /helix/users` は1度に100人まで）に問い合わせ、画面を開いているあいだ手元に覚えておく。視聴者の記録にアイコンを貯める案は、注目コメントと同じ理由（すべての発言者のぶんを取りに行くことになる）で採らなかった。

## 注目コメントは注目コメントのページと同じ経路で設定する

コメントビューアーの発言の行から、その発言を注目コメント（配信画面に大きく映す1件）に設定できる。注目コメントのページ（`/focus/`）は、配信中に貯めている発言の記録（`stream_chat_messages`）から選ぶ一覧を持つ。しかし、配信者が「この発言を取り上げたい」と思うのは流れを見ているときなので、そこから直接選べるようにした。

保存には注目コメントのページと同じ `PUT /api/admin/focus` を使い、Worker 側には何も追加していない。値の検証とアイコンの取得は `worker/focus-config.ts`・`worker/focus-routes.ts` だけが持ち続ける。注目コメントは本文を文字だけで映す（`docs/decisions/focus.md`）ので、エモートは名前の文字のままつなげて送る。

取り上げられるのは発言（`channel.chat.message`）だけで、お知らせ（継続サブスクに添えた発言など）は対象にしていない。注目コメントのページの一覧と揃えるためである。モデレーターに消された発言は取り上げさせない（配信画面に出さないため）。ただし、取り上げたあとで消された発言は、取り上げをやめられるように押せるままにしておく（映すのは合成ページ側の `src/focus/focused.ts` がやめる）。

注目コメントは注目コメントのページとこの画面の両方から変えられるので、画面が覚えている「いま取り上げているもの」は古くなりうる。取り上げをやめる前にはいまのものを読み直し、ほかの画面で別の発言に取り上げ直されていたら、やめずに表示のほうを合わせる。Worker 側で「この発言を取り上げているときだけ外す」という条件付きの削除にする案もあったが、保存先のKVには比べてから書き換える仕組みがなく、隙間は残るので採らなかった。開いたときの読み込みが遅れて返ってきた場合も、この画面で選び直したあとなら結果を捨てる。

## モデレーターの操作は bot の権限で、自動モデレーションと同じ実行部分を使う

コメントビューアーの発言の行から、発言の削除・その人のタイムアウト・BANができる。行うのは bot で、自動モデレーションと同じ `worker/bot-moderation.ts` の `punishAsBot` を使う。配信者のトークンで行えば Twitch の記録に配信者の名前が残るが、そのためには配信者に `moderator:manage:*` を追加して認可し直してもらう必要がある。bot はすでにこれらのスコープを持っているので、配信者の認可をそのままにできる bot の側を選んだ。Twitch のモデレーターの記録に残る理由は、自動モデレーションと見分けられるよう手動のものに変える。

タイムアウトの長さは配信中に選ばせず、Twitch の `/timeout` の既定と同じ10分に決めてある（`MANUAL_TIMEOUT_SECONDS`）。数を持つのは Worker だけで、画面は応答で受け取った長さを出す（同じ数を2か所に書かない）。

手動のタイムアウト・BANでは、発言を先に削除しない（`punishAsBot` に `messageId: null` を渡す）。Twitch はタイムアウト・BANした人の発言をまとめて消すので、先に消す必要がない。むしろ、自動モデレーションや別のモデレーターがすでに消した発言を指定すると削除が失敗し、処分まで届かなくなる。自動モデレーションで削除を先に行っているのは、処分の理由になった発言を確実に消すためで、そちらの順序は変えていない。

BANだけは押す前に確かめる。削除とタイムアウトは配信中にすばやく行えることを優先し、確かめない（タイムアウトは10分で解けるので、誤って押しても取り返せる）。処分した発言への印は、画面が自分で付けず、Twitch から届く削除・消去の通知を待って付ける。印が付くのは「Twitch で実際に消えた」ことを表すようにするためである。

## チャットは配信者本人として送る

コメントビューアーの下の入力欄から、配信者本人としてチャットを送れる。botとして送る道（`POST /api/admin/bot/messages`）はすでにあったが、配信中に配信者が視聴者へ返すのは配信者自身の言葉なので、送り主は配信者にした。そのために配信者のスコープに `user:write:chat` を追加しており、追加する前にログインしていた配信者は一度 Twitch の許可を取り直す必要がある。

許可を取り直していない（配信者のトークンに `user:write:chat` が無い）ときは、botで代わりに送らず、ログインし直すよう伝えて断る。黙って送り主を変えると、配信者の言葉がbotの名前で出てしまい、しかもそれに気づけないためである（Fail-Fast）。bot の画面でモデレーターかどうかを確かめるときと同じく、スコープの不足を別のものに読み替えない。

送った発言は、ほかの発言と同じく Twitch から届いた時点で流れに並ぶ。画面が先回りして並べないのは、AutoMod に保留された発言などを「送れた」ように見せないためである。

## 初めての発言に挨拶したかを、手で記録する

配信者が気にしているのは、全部の発言に反応したかではなく、**その配信で初めてチャットした人に挨拶したか**である（issue #158）。挨拶の通知音はトリガー（「その配信で初めての発言」）で鳴るが、鳴ったあとに挨拶が漏れていないかは確かめられなかった。そこで、その配信で初めての発言ごとに「挨拶した」を持ち、まだの人を目立たせる。

**初めての発言かは Worker が判定し、流す1件に `firstOfStream` として付ける。** 判定と記録には、トリガーと同じ `first_chatters`（`worker/chat-store.ts` の `claimFirstChatOfStream`）を使う。同じ発言について何度問い合わせても同じ答えが返るので、コメントビューアーへの押し出し（`worker/webhook-routes.ts` の `isFirstChatToGreet`）で先に判定しても、そのあとのトリガーの判定と食い違わない。これまではトリガーの条件に使われているときしか判定しなかったが、挨拶の管理は通知音の有無と関係ないので、配信中の発言では常に判定する。書き込みは1配信につき1人1行なので、D1 の書き込みの枠はほとんど食わない。**配信者自身と bot の発言は挨拶の相手ではないので、判定も記録もしない**（bot は応答のたびに発言するので、印を付けると毎回「未挨拶」に並んでしまう）。bot のトークンはチャットの発言のときだけ1度読み、配送と応答の両方で使う。読めなかったときも配送は止めず（bot を見分けずに流す）、応答の側はこれまでどおり失敗にして Twitch に再送させる。壊れたトークンのまま自動モデレーションやコマンドを黙って飛ばさないためである。判定に失敗したときは、印を付けずに流すのではなく、押し出しの失敗（`comment-feed-failed`）として記録する（黙って「初めてではない」扱いにしない）。

**挨拶したかは `first_chatters.greeted_at` に持つ**（`recordGreeting`）。挨拶は配信ごと・人ごとに1回なので、初めての発言の行に並べれば足り、新しい表は要らない。古い行は cron が消すが、配信中の区切りのぶんは消さないので、配信のあいだは記録が残る。初めての発言として記録されていない発言を指定されたら、黙って成功にせず404（`unknown-first-chat`）で断る。

**画面への印は、既読と同じく付け替えを1件として配送先へ押し出して付ける**（`kind: 'greeting'`。毎回新しいID）。配送先の履歴にも届いた順に残るので、開き直した画面も、ほかのウィンドウも同じ状態になる。画面は先回りして印を付けず、押し出しに失敗したら成功として返さない。

**挨拶したかは配信者だけが決め、発話から自動では判定しない。** 下の節のとおり、発話から「どの発言に応じたか」を当てるのは難しかった。挨拶は1人1回で数も少なく、押し忘れても上部の一覧に残るので、手で押す手間のほうが小さい。

**まだ挨拶していない人は、行を目立たせたうえで、流れの上に名前を常に並べる**（`src/comments/feed.ts` の `needsGreeting`・`pendingGreetings`）。行を目立たせるだけでは、流れて見えなくなった人に気づけないためである。名前を押すとその発言の行へ移り、いちばん下への追従はやめる（移った先で止まるように）。目立たせるのは色だけに頼らず「未挨拶」の文字も出し、挨拶したあとも「初コメ」の印は残す。消された発言は挨拶の相手にしない。時間がたってから目立たせる形（旧「しばらく未読」）にしなかったのは、挨拶はすぐに返すものなので、待つ理由がないためである。設定項目も持たない（`docs/principles.md` の1）。

**一覧に並ぶのは、画面が持っている直近の並び（`MAX_ENTRIES`＝500件）の中だけである。** 配送先の履歴（400件）より前に流れた初めての発言は、開き直すと一覧から外れる。1配信で500件を超えるまで挨拶を忘れたままになることは少ないので、D1 から未挨拶の人を読み直す経路は持たない。

## 全発言の既読・未読と、発話からの Jev 判定はやめた

issue #146・#147 では、視聴者の発言1件ごとに既読・未読を持ち（D1 の `comment_reads`）、届いてから3分たっても未読の発言を「しばらく未読」として目立たせ、さらに配信者の発話（文字起こし）から Jev で「どの発言への反応か」を判定して自動で既読にしていた。issue #158 で、これらを設定（KV の `comment-settings`）ごとすべて消した（`docs/principles.md` の12）。

2026-09-29 の配信で試したところ、Jev は213回呼ばれて失敗は0件だったのに、しきい値（0.8）を超えて既読になった発言は1件も無かった。配信者のチャットへの応じ方は、「これってA？」に対して「そうよねー、その点で言うと」と話を続けるように、直接の返事ではなく投稿を受けて新しく話す形が多い。このため、発話がどの発言への反応かを当てること自体が難しい。そもそも配信者には全部の発言の既読・未読は要らず、要るのは初めての発言への挨拶だけだった（上の節）。

試したときに分かったことは、次に発話から判定するものを作るときのために残す。

- Jev には、発言1件につき Noul を1問にし、1回の注文にまとめて渡していた（同じ注文の質問は並列に評価されるので、件数が増えても待つ時間はほぼ変わらない）。指示文は日本語のほうが英語より正しかった。質問の名前はモデルに伝わらないので、質問の中に名前と本文を書く必要があった
- 返事は複数の文にまたがるので、発話は直前の3文を渡していた。手で作った24件の場面では、0.8 で反応していない発言を既読にした誤りは0件だった。ただし実配信では、上のとおり1件も既読にならなかった
- 判定の確率を記録していなかったため、実配信のあとで「惜しかった」のか「見当違いだった」のかを確かめられなかった。判定を使う機能を作るときは、確率を後から読める形で残しておく
