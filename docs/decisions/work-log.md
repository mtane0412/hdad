# 作業ログ（素材の種類 `workLog`）

作業配信に途中から来た人は、いま何をしていて、ここまでに何が進んだのかが分からない。サイドスーパーは「いま」を2行で出し続けるが、「今日ここまでにやったこと」は画面に無かった。そこで開発の出来事（コミットの push・PR のマージ。issue #210 で Worker に届くようになったもの）と章の見出しを時刻つきで積み上げ、合成ページの素材「作業ログ」として配信画面に並べることにした（issue #211）。

## 機械が作った見出しと、実際に起きた出来事を見分けて出す

章の見出しは cron が LLM に作らせたもので、外れることがある。コミットやマージは実際に起きたことである。両者を同じ顔で並べると、見ている人は機械の推測を事実として読んでしまう（方針11）。そのため1行ごとに種類（`commit`・`merge`・`chapter`）を持たせ、画面では種類の印の言葉（「コミット」「マージ」「AIのまとめ」）と見た目（出来事は塗りの印と太字、章は枠線だけの印と斜体の淡い文字）の両方で区別する。印の言葉を「章」ではなく「AIのまとめ」にしたのは、見ている人が「章」と読んでも誰が書いたかが分からないためである。

章から出すのは見出しだけで、要約は出さない。配信画面の1行に収まらず、読み返すのはダッシュボードの配信の詳細で足りるためである。章の時刻は区間の始まりにした。区間の終わりは章ができた時刻に近く、その区間の中で起きたマージより上に並ぶと「この話のあとにマージした」と読めなくなるためである。

## トリガーとは関係なく並べる

作業ログは「その配信で実際に起きたこと」の記録なので、トリガーの「開発」の項目に効果を付けているかどうかに左右されないようにした。GitHub の受け口（`worker/github-routes.ts`）は、配信中に届いた push・マージを、トリガーの動作を実行したあとで必ず作業ログに残して押し出す。配信外に届いたものはトリガーと同じく捨て、作業ログにも残さない（配信外の作業を今日のログに含めない）。

作業ログに出す1行は、トリガーの差し込み語と同じ読み解き（`worker/alert-event.ts` の `extract`）から作る（`worker/work-log.ts` の `devEventOf`）。push はコミットのメッセージの1行目（`{message}` と同じもの）、マージは「#番号 タイトル」にした。リポジトリ名は出さない。Webhook を設定するのは配信者自身のリポジトリで、毎行に同じ名前が並ぶだけになるためである。

## 開発の出来事を D1 に残す形

issue では「再送の判定に使う記録と兼ねるか」を実装時に決めることにしていた。兼ねずに、新しい表 `dev_events`（`migrations/0023_dev_events.sql`）を足した。トリガーの再送を見分ける鍵（`replied_chat_messages`）は動作ごとの鍵で、保持期間が過ぎると消える。作業ログは出来事ごとの配信の記録で、章（`stream_chapters`）と同じく消さずに残したい。粒度も寿命も違うものを1つの表に押し込むと、どちらかの都合でもう一方が壊れる。

`dev_events` の主キーは `github:<X-GitHub-Delivery>` にした。GitHub の Redeliver は同じ値を使うので、再送は主キーで1行にまとまる。残すときは配信中の区切りを `INSERT ... SELECT` の中で引き（`transcripts` と同じ考え方）、再送では何も書き換えずに最初の1行を返す（`worker/work-log-store.ts` の `recordDevEvent`）。再送で押し出し直す1行の時刻を、最初に届いた時刻のままにするためである。

## 押し出しはアラートの配送先に相乗りする

増えた1行は、アラートと同じ Durable Object（`worker/alert-channel.ts` の `AlertChannel`）から WebSocket で押し出す。新しい Durable Object を足すと PR ブランチのプレビュービルドが失敗するためで、BGM の切り替えを相乗りさせたときと同じ判断である。受け取る素材がアラートと違うので、3つ目の目印（`workLog`）を付けた接続へだけ配る。

GitHub の受け口では、押し出しに失敗したら500で返す。GitHub の Recent Deliveries から Redeliver で届け直せるようにするためで、そのときトリガーの動作は鍵で弾かれ、作業ログは同じ1行のまま押し出し直される。合成ページは id で重ねるので2行にならない。いっぽう cron の章づくり（`worker/collect.ts` の `makeStreamChapter`）では、押し出しの失敗を章づくりの失敗と分けて `work-log-push-failed` として記録し、章は残して区間も進める。作り直すと LLM の枠を使ううえ、合成ページは次の読み直しで取り戻せるためである。終わった配信の章（配信の終わりで切った最後の章）は押し出さない。合成ページが映すのは配信中の配信のログだけだからである。

## 開き直したときの取り戻し方と、件数の上限

合成ページは、開いたとき・WebSocket がつながるたび・5分おきに `GET /api/overlay/work-log` を読み、いま配信中の配信の出来事と章を新しい順に取り戻す。押し出しだけに頼らないのは、OBS を開いていない間・接続が切れていた間に増えた行を取りこぼさないためである。5分おきに読むのは、配信の前後に OBS を開いたままにするのが普通の使い方で、配信が切り替わったときに前の配信の行を消す必要があるためで、cron の間隔より細かくする意味は無い。読み直しは一覧を置き換えるが、読んでいる間に押し出された行は結果に重ねる（古い読み出しで新しい行を消さないため）。

件数の上限は20行（`WORK_LOG_LIMIT`）にした。Worker も合成ページも上限で古いものから落とし、D1 の行は消さない。配信画面に何行映すかは素材の枠の大きさで決め、あふれた古い行は CSS で隠す。行数を設定項目にしなかったのは、枠の大きさを変えれば同じことができ、設定を増やさない（方針1）ためである。上限を20にしたのは、追加したときの枠（560×640px）に収まる10行ほどの倍あれば、配信者が枠を縦に伸ばしても足りるためである。
