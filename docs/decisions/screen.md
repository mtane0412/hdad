# 配信画面の取り込み（`/screen/`）

あらすじ（`worker/stream-summary.ts`）とサイドスーパー（`worker/side-super.ts`）が材料にしてきたのは、**配信者が言葉にしたこと**（`transcripts`）と**視聴者が書いたこと**（`stream_chat_messages`）だけだった。配信者が黙って画面を操作している時間帯は材料が生まれず、文字起こしが0件の区間では cron がLLMを呼ばない（`worker/collect.ts`）ため、あらすじがまったく進まない。配信画面には、そのどちらにも現れない情報（開いている資料の見出し・固有名詞・日付・検索語）が出ている。これを3つ目の材料にするのが issue #122 で、ここに書くのは**撮って記録し、読み取った文字を篩にかけるところまで**（Phase 1〜3）の判断である。

## 撮る経路は obs-websocket にした

Twitch の `thumbnail_url` は5分前後でしか更新されず、高頻度で読んでも同じ画像を受け取るだけなので使えない。OBS の obs-websocket なら任意のタイミングで撮れる。

https のページから `ws://localhost` へつなぐのは混在コンテンツにあたるが、ブラウザがループバックを安全な接続元として例外扱いするため通る（文字起こしの中継が同じ前提で実機確認済み。`docs/decisions/transcript.md`）。そのため `host` は `localhost` と `127.0.0.1` しか受け取らない。

ライブラリ（`obs-websocket-js`）は入れない。使うのは名乗り（Identify）と2つの要求だけで、認証も SHA256 を2段重ねるだけなので WebCrypto で足りる。

## 撮るのは現在のプログラムシーン1枚

ソースを列挙して選ばせる形は採らない。ゲームだけでなくブラウザや資料のウィンドウも材料になるので、「どのソースを撮るか」を決めさせると配信者が配信のたびに設定を見直すことになる。プログラムシーンを撮れば、いま映っているものがそのまま材料になり、**配信者が入力するソース名はゼロ**で済む（`docs/principles.md` の「設定項目を増やさない」）。

幅は1280にした。1280と1920の両方でブラウザの本文がOCRで読めることを実測で確かめてあり、`GetSourceScreenshot` は obs-websocket が Complexity Rating 4/5 とする重い要求なので、ゲームと配信のエンコードと同居させるために狭いほうを選ぶ。

## パスワードは Worker の設定に置いた

obs-websocket のパスワードの置き場は3つ考えられた。

- **Worker の設定（KV）に置く**（採用）。読み上げの設定（`docs/decisions/speech.md`）と同じ形で、管理画面から変えられる
- 認証を切って localhost のみで待ち受ける前提にする
- 裏方のページのURLに載せる

採用したのは1つ目である。3つ目はURLがOBSのソース設定に平文で残り、配信中に変えられない。2つ目は配信者にOBS側の設定変更（認証を切る）を求めることになり、同じPC上の他のプロセスからOBSを操作できるようにしてしまう。

**引き換えに、オーバーレイ用キーが漏れるとOBSの全操作権も渡ることになる**（`GET /api/overlay/screen` の応答にパスワードが入るため）。オーバーレイ用キーはもともと合成オーバーレイのURLに載って配信者のOBSの中にあるもので、漏れたときは `/triggers/` で再発行できる。認証を切る選択肢も残す（パスワードを空にすれば認証のやりとりを行わない）ので、その判断は配信者に委ねる。

### パスワード違いは、つながらなかったのと別の文面にする

当初は、名乗り（Identify）が通る前に接続が閉じたケースをすべて「つながりませんでした。OBSが起動しているか…混在コンテンツかもしれません」の一文にまとめていた。実際にパスワードを取り違えた配信（2026-09-28）で、この文面のせいで待ち受けポート・IPv4とIPv6の食い違い・OBS内蔵CEFの混在コンテンツを順に疑うことになり、原因にたどり着くまで遠回りした。obs-websocket はパスワードが違うと**つないだ直後にクローズコード 4009 で切る**ので、接続そのものは成立している。

そこで `src/screen/connection.ts` は、名乗りが通る前のクローズをコードで3つに分ける。4009 はパスワード違いとして直し方（接続情報を表示の値を入れ直す・認証を切っているなら空にする）を出し、4000以上のそのほかのコードは「つながったが名乗りの途中で切られた」として OBS 側の設定を指し、コードが無い（または4000未満の）ときだけ従来の起動・混在コンテンツの文面を出す。**クローズコードは必ず文面に載せる**（配信者が OBS の資料で引けるようにするため）。

## 撮った画像はこのサイトに置かず、Gyazo に上げる

OCRを自前で持たず Gyazo に任せる。Workers AI の画像モデルに頼らずに日本語混じりの画面を読めるためである。R2（`MEDIA`）に画像を貯める形も採らない。材料として要るのは**画面に出ている文字**であって画像そのものではなく、15秒〜60秒ごとに撮った画像を配信のあいだ貯め続ける意味がない。

- **`access_policy` は `anyone`、`metadata_is_public` は `false`** にする。はじめは `only_me` にしていたが、手書きの描く画面の背景に最後の1枚を敷くために `anyone` へ変えた（`only_me` の画像は、一覧の応答に付く期限付きの署名なしではブラウザから読めない。`docs/decisions/draw.md`）。配信画面はもともと公開している映像で、配信していないあいだの画面は上げないので、URLを知っていれば見られる形で差し支えないと配信者が判断した。Gyazo はProアカウントを持ち続ける前提で、積極的に使ってよい部品として扱う
- メタデータ（OCRのテキストを含む）は公開しない。2026-09-11 に Gyazo が受けた不正アクセスでは、画像のメタデータ（OCRのテキストと画像ID）が流出している
- **OCR のテキストは `metadata.ocr` の下にある。** 公式ドキュメント（https://gyazo.com/api/docs/image ）は `ocr` をトップレベルに置くと書いているが実際は違う。ドキュメントどおりに書くと永久に空として扱う（OCRを取りに行く Phase 2 で効いてくる）
- API の回数は足りる。15秒間隔・4時間の配信でアップロード960回＋OCR取得960回の計1920回で、Gyazo の1日12,500回に収まる

**上げ先のコレクションは設定で選べるようにした**（`collection_id`。Gyazo のアップロードAPIの任意のパラメータ）。配信画面は配信のたびに何百枚も積み上がるので、指定しないと配信者のGyazoの一覧がそれで埋まる。指定しない運用も許す（空なら項目ごと送らない）。

コレクションIDは**保存するときに形（32桁の16進数）を確かめる**。Gyazo が受け取れない値を保存すると、撮った1枚を上げるたびに失敗し、配信中にそれと気づけないためである。ただし Gyazo の画面からはURLごとコピーするのが自然なので、**貼られたURLからIDを取り出すのは画面（`src/screen/screen-page.tsx` の `collectionIdOf`）が行う**（入力欄の値の変換は画面、値の検証は Worker という分け方はそのまま）。

**コレクションIDは裏方のページに渡さない。** `GET /api/overlay/screen` が返すのは撮るのに要る4つ（ホスト・ポート・パスワード・間隔）だけで、上げ先は Worker が設定から読む。撮る側に持たせると、貼ったURLや裏方のページの都合で上げ先が変わりうるうえ、渡す必要のないものをオーバーレイ用キーの向こうへ出すことになる。

## 配信していなければ、Gyazo へ上げない

`POST /api/overlay/screen` は、配信中の区切り（`stream_sessions` の `ended_at IS NULL` の行）が無ければ**上げる前に**捨て、捨てたことを応答（`{ recorded: false }`）で裏方のページに知らせる。上げてから記録するかどうかを決める形にすると、配信前の準備画面や配信後のデスクトップまで Gyazo に残ってしまう。捨てるのを失敗にしないのは、配信の前後にOBSを開いたままにしておくのが普通の使い方だからである（文字起こしの受け口と同じ考え方）。

一方、**Gyazo のアクセストークン（`GYAZO_ACCESS_TOKEN`）が設定されていないときは失敗させる**（Fail-Fast）。黙って捨てると、材料が貯まっていないことに配信が終わるまで気づけない。トークンは任意のシークレットで、`.dev.vars.example` ではコメントアウトしてある（Deploy to Cloudflare ボタンの入力欄に必須の項目として出さないため。OpenRouter の鍵と同じ扱い）。

## 記録は画像IDだけ

`screen_captures`（`migrations/0016_screen_captures.sql`）が持つのは画像ID・配信の区切り・撮った時刻の3つだけである。`image_id` を主キーにするのは、同じ画面を撮ったときに Gyazo が同じ画像IDへ畳むためで、画面が変わらないあいだは行が増えない。そのとき `captured_at` は最初のまま残す（その画面を最初に見た時刻が分からなくなるため）。

古い行は cron（`worker/collect.ts`。1日より前。配信中の区切りのぶんは残す）が消す。保持期間を文字起こしに揃えるのは、どちらも配信中だけ持つ材料だからである。

## 裏方のページの3つ目にした

撮る側は映すものを持たないので、合成ページ（`overlay/stage/`）の素材にはせず、裏方のページ（`overlay/backstage/`）の3つ目として載せた（`docs/decisions/backstage.md`）。1つの裏方の失敗でほかを止めない約束もそのまま適用する。

**既定では動かさない**（`?screen=true` を書いたときだけ動く）。読み上げと文字起こしと違い、OBS側のWebSocketサーバーと Worker 側の Gyazo のトークンの両方が要るので、何も用意していない配信者のブラウザソースが起動のたびに失敗を出さないようにする。

## 読み取った文字は cron が取りに行く（Phase 2）

Gyazo のOCRは上げた直後には生成が終わっていない（実測で約10〜13秒）。上げる `POST /api/overlay/screen` の中で待つ形は採らない。裏方のページが次の1枚を撮るまでの時間を削ってしまううえ、待っても生成が終わっている保証がないためである。代わりに5分おきの cron（`worker/collect.ts` の `fetchScreenOcr`）が、まだ取れていない行をまとめて取りに行く。cron の間隔（5分）は生成にかかる時間よりはるかに長いので、ふつうは最初の1回で取れる。

**取りに行く先は `metadata.ocr.description` である。** 公式ドキュメント（https://gyazo.com/api/docs/image ）は `ocr` をトップレベルに置くと書いているが、実際の応答は違う。ドキュメントどおりに書くと永久に空として扱い、材料が1文字も貯まらない。2026-09-28 に実際の応答で確かめた形は次のとおりである（トップレベルに `ocr` は無く、`metadata.ocr` は `locale` と `description` を持つ）。

```
image_id, type, created_at, permalink_url, thumb_url, url, access_policy, metadata
metadata: app, title, url, desc, links, user, ocr, original_title, original_url
metadata.ocr: locale（'ja'）, description（読み取った文字）
```

**取りに行くのは1枚ずつ（`GET /api/images/:image_id`）である。** 一覧（`GET /api/images`）の応答には `metadata.ocr` そのものが入らないので、まとめて取る形は採れない。上げた枚数だけ呼び出しが要るが、15秒間隔・4時間の配信でもアップロードと合わせて1920回で、Gyazo の1日12,500回に収まる。

**空の読み取りは「取れなかった」として扱い、諦めるまでの回数を持つ**（`worker/screen-store.ts` の `OCR_MAX_ATTEMPTS` は3回）。生成が終わっていないときも、文字が1つも写っていない画面のときも、Gyazo が返すのは同じ「空」なので区別できない。区別できない以上、両方を取り直しの対象にしたうえで上限で止めるほかない。上限が無ければ、文字の無い画面を配信のあいだじゅう叩き続けることになる。`ocr_text` は NULL が「まだ取れていない」、空でない文字列が「取れた」で、上限に達した行は `ocr_attempts` で引かれなくなり、保持期間（1日）で消える。

**1枚で失敗したら、その回の残りは取りに行かない。** 失敗の理由（トークンが無効・Gyazo が落ちている）はたいてい次の1枚でも同じで、続けても外への呼び出しを無駄に使うだけである。失敗は `collection_failures`（`screen-ocr-failed`）に残し、収集そのものは止めない。画面の文字は補助的な材料なので、Gyazo が使えない日に配信の記録（視聴者数・フォロワー数）まで止めない（人物像づくりと同じ扱い）。

**ただし「その画像が無い」（404）だけは、その1枚を諦めて先へ進む**（`abandonOcr`）。配信者が Gyazo から画像を消すと起こりうるが、これは次の1枚には当てはまらない理由である。ここで止めると、取りに行く順が撮った順である以上その1枚が先頭に居座り続け、以降どの収集でも後ろの1枚へ永久にたどり着けなくなる。

1回の収集で取りに行くのは30枚までとした（`SCREEN_OCR_BATCH_SIZE`）。15秒間隔で撮っていれば5分で20枚ほど貯まるので取りきれる枚数であり、Workers が1回のリクエストで出せるサブリクエストの上限への備えでもある。

## 読み取った文字は、篩を通してから積む（Phase 3）

読み取った文字（`screen_captures.ocr_text`）をそのまま材料にすることはしない。画面には HDAD 自身が出している文字（サイドスーパー・チャットボックス・字幕）が映り込むうえ、同じ画面を撮り続けるあいだ同じ文字が毎回丸ごと返るためである。篩（`worker/screen-ocr.ts`）を通し、残った行だけを `screen_lines`（`migrations/0018_screen_lines.sql`）に積む。

**篩は3段である。**

1. **自前の文字の除去**。Worker が自分で持っている文字（`side_supers`・`stream_chat_messages` と `viewers.display_name`・`transcripts`）と照らす。落とし方は3通りで、丸ごと含む（飾りや吹き出しの記号が付いて読み取られたとき）・一部でしかない（チャットボックスの端で見切れたとき）・よく似ている（OCRの揺れ）。**ただし短すぎる自前の文字では照合しない**（1文字の表示名で画面の本文まで落としてしまうため）
2. **中身のない行の除去**。正規化して3文字未満、または数字だけの行
3. **既出の除去**。その配信で既に渡した行に近ければ落とす。**初出は必ず残す**

**比べ方を完全一致にしないのが、この篩の要である。** OCRは同じ画面でも毎回違う文字を返す（実測で「電承」→「電」、「2008」→「2006」、「att**i**de」→「art**i**de」）。実測では、完全一致だと同じ場面を撮った2枚目の削減率が15%に留まり、文字2連の重なり（Dice係数0.7）にすると99%になった。**画面が変わらない限り渡る文字がほぼゼロになる**ことが、高頻度で撮ることを成り立たせている。しきい値を下げると別の内容まで同じ行として畳み、上げると揺れを吸収できない。

**「恒常表示の除去」を独立した段としては持たない。** 分けて持つ形も試したが、初出の本文まで落ちて一度も LLM に届かなかった。同じ役目は既出の除去が果たす（画面に出続けているものは、2枚目以降で既出になる）。

**正規化（`normalizeScreenLine`）はNFKC・小文字化・空白除去・記号落としに留め、文字そのものは落とさない。** これ以上畳むと、本当に変わった行まで同じに見える。

異体字・旧字体の揺れ（「黒田」が「黑田」として返る）には対応表を持たずに始める。「黑」と「黒」は別の文字なので2連の重なりが 0.25 にしかならず自前の文字の除去をすり抜けるが、残るのは短い断片1行で害が小さい。

### 通し終えた印を、行の有無で代用しない

`screen_captures.sifted_at` を追加して印にする。**残った行が0行でも印を付ける。** 同じ画面を撮り続けるあいだ0行になるのが普通なので、`screen_lines` に行があるかどうかで代用すると、そうした1枚を収集のたびに引き直すことになる。

篩は外を呼ばないので、Gyazo のトークンが無くても通す（前の収集で取れているぶんが残っていることがある）。材料（自前の文字・既出の行）は配信の区切りごとに一度だけ読み、同じ収集の中で残った行はその場で既出に追加する（そうしないと、2枚目以降が1枚目と同じ行を積む）。照らす範囲は直近だけにした（発言と発話は50件、既出の行は300行）。画面に映るのは直近のぶんだけであり、配信の序盤まで遡っても落とせる行は増えない一方、全部と照らす形にすると配信が長くなるほど1枚あたりの比較が増えていく。

`worker/screen-ocr.ts` は**LLMもD1も触らない純粋な関数だけ**を持つ（`buildStreamSummaryPrompt` を分けているのと同じ形）。読むのは呼び出し側（`worker/collect.ts` の `siftScreenOcr`）の仕事である。

## 画面の文字を第3の材料として差し込む（Phase 4）

篩を通った行（`screen_lines`）を、あらすじ（`worker/stream-summary.ts`）とサイドスーパー（`worker/side-super.ts`）の材料に追加する。見出しは役割どおりに分けた。あらすじには「# そのあと画面に新しく現れた文字（古い順）」（前回のあらすじから後に現れたぶん）、サイドスーパーには「# 直近に画面へ現れた文字」（直近のぶん）である。あらすじは積み上げる仕組みなので続きだけを読み、サイドスーパーは毎回その時点から作り直すので直近だけを読む、という元からの違いをそのまま引き継いでいる。

サイドスーパーの見出しを「いま画面に出ている文字」にしなかったのは、篩が残すのが「新しく現れた行」だけだからである（同じ画面を映し続けているあいだは1行も増えない）。そこにあるのは画面の写しではなく「最近変わったところ」なので、見出しもそう名乗る。

### 材料にする順も目印も、撮った時刻ではなく積んだ時刻で決める

**`screen_lines` に `sifted_at`（篩を通して積んだ時刻）を持たせ、読む順も目印もこれで決める**（`migrations/0019_stream_summary_screen_cursor.sql`）。最初は撮った時刻（`captured_at`）で組んだが、2か所で壊れる。

- **遅れて積まれた1枚が、一度も材料にならない。** OCRの生成が間に合わない1枚は次の収集へ回るので（`OCR_MAX_ATTEMPTS`）、あとから撮った1枚のほうが先に積まれることがある。撮った時刻を目印にすると、遅れて積まれた1枚は目印より前に入り、読まれないまま保持期間で消える
- **サイドスーパーが作り直されない。** 篩は cron のいちばん最後に走る（`collect` の並び）ので、積まれたばかりの行の撮った時刻は、その回より前のサイドスーパーを作った時刻より必ず古い。「前回より新しい材料があるか」を撮った時刻で見ると、常に偽になる

積んだ時刻であれば、あとから積まれた行は必ず目印より後ろに来る。そのぶんLLMへ渡る順は厳密な「画面に現れた順」ではなくなるが（遅れて取れた1枚が後ろに回る）、材料の取りこぼしが無いほうを採った。

目印は `stream_summaries` の `screen_until`・`screen_until_id`・`screen_until_line` の3つで持つ。時刻だけでは足りないのは、同じ収集で積んだ行は時刻が同じであり、件数の上限で分かれると残りが次からの「この時刻より後」に一度も入らないためである（`transcripts` の目印と同じ理由）。**1枚の中の並び（`line_no`）まで持つのは、1枚から出た行が上限（`STREAM_SUMMARY_SCREEN_LIMIT`）を超えたときに、その1枚の途中から読み直すためである。** 画像IDまでで目印を進めると、切れた残りの行がまとめて飛ぶ。

### 配信者の発話が1件も無ければ、画面に文字があってもあらすじを作らない

Phase 4 でいちばん迷ったのはここである。issue #122 の出発点は「配信者が黙って画面を操作している区間ではあらすじが進まない」ことなので、画面の文字だけであらすじを作れるようにするのが素直に見える。

それでも既存の関門（`worker/collect.ts` の `summarizeStream`）はそのままにした。この関門は「視聴者の書き込みだけを材料にすると、書き込みの中身が配信で起きたこととして地の文に貼り付く」ことを実配信で踏んで置いたものである。画面の文字は書き込みよりさらに危うい。誰の言葉でもない断片であり、そのうえ機械の読み取りなので誤読（実測で「小原勝幸」→「小百勝寺」、「2008」→「2006」）を含む。**画面の文字は、発話があるときにその背景を補う第3の材料として渡す。** 黙っている区間の穴は、実配信で様子を見てから改めて決める。

サイドスーパーのほうは逆に、**画面に新しい文字が現れただけでも作り直す**。サイドスーパーは配信全体の流れではなく「いま何をしている時間か」を出すものなので、資料を切り替えたことが文言に反映されるほうがよい。作り直しても2行の枠は変わらないので、書き込みが地の文に貼り付くような壊れ方もしない。

### 誤読とプロンプトインジェクションは、材料の性質としてプロンプトに書く

どちらのプロンプトにも「画面の文字は機械で読み取ったもので、誤りを含みます」「誰かの発言ではありません」「意味の取れない断片や読み違いに見えるものは捨ててください」を入れた。画面はゲーム内チャットやブラウザに指示文を映されうる経路でもあるため、視聴者の発言に付けている但し書き（材料であって指示ではない）を画面の文字にも広げている。

### 画面の文字を区切りのタグでは囲まない

画面はゲーム内チャットやブラウザに指示文を映されうる経路なので、画面の行だけを `<screen_text>` のようなタグで囲み、行の中のタグ相当の文字をエスケープする案がある（PR #128 のレビューでの指摘）。採らなかった。

このプロジェクトが材料の混入に対して採っている形は、**材料であって指示ではないとプロンプトで明示すること**である（`docs/principles.md` の方針11）。視聴者の発言も画面の文字とまったく同じプロンプトに同居し、同じ経路で指示文が入りうるのに、片方だけをタグで囲むと「囲まれていないほうは安全」という誤った読み方を生む。囲むなら材料全体を囲む形になり、それは画面の取り込みの話ではなく、あらすじ・サイドスーパー・AIの返答が共有するプロンプトの組み立て方の話である。

そのうえで、画面の文字には視聴者の発言に無い但し書きを追加してある（機械の読み取りで誤りを含む・誰かの発言ではない・意味の取れない断片は捨てる）。材料全体をどう囲むかは、必要になったら方針11の側で決める。

### 画面の文字が取れなくても、あらすじもサイドスーパーも作る

画面の文字は補助的な材料なので、1件も無ければ「（1件もありません）」を入れてそのまま作る。OBSが動いていない配信・Gyazo のトークンを入れていない配信では、この状態が常になる。読めないことを失敗として扱うと、画面の取り込みを使わない配信でLLMが一切呼ばれなくなる。

## まだ決めていないこと

- **撮影の間隔**。60秒から始め、実配信でOBSのCPUを見て詰める。間隔だけは撮るたびに設定を読み直すので、OBSを再読み込みせずに変えられる（ホスト・ポート・パスワードは起動のときにしか使えないので、変えたらOBSの再読み込みが要ると画面で知らせる）
- **黙って画面を操作している区間のあらすじ**。上に書いたとおり、画面の文字だけではあらすじを作らない形で始める。実配信で穴の大きさを見てから決める
