# 配信画面の取り込み（`/screen/`）

あらすじ（`worker/stream-summary.ts`）とサイドスーパー（`worker/side-super.ts`）が材料にしてきたのは、**配信者が言葉にしたこと**（`transcripts`）と**視聴者が書いたこと**（`stream_chat_messages`）だけだった。配信者が黙って画面を操作している時間帯は材料が生まれず、文字起こしが0件の区間では cron がLLMを呼ばない（`worker/collect.ts`）ため、あらすじがまったく進まない。配信画面には、そのどちらにも現れない情報（開いている資料の見出し・固有名詞・日付・検索語）が出ている。これを3つ目の材料にするのが issue #122 で、ここに書くのは**撮って記録するところまで**（Phase 1）の判断である。

## 撮る経路は obs-websocket にした

Twitch の `thumbnail_url` は5分前後でしか更新されず、高頻度で読んでも同じ画像を受け取るだけなので使えない。OBS の obs-websocket なら任意のタイミングで撮れる。

https のページから `ws://localhost` へつなぐのは混在コンテンツにあたるが、ブラウザがループバックを安全な接続元として例外扱いするため通る（文字起こしの中継が同じ前提で実機確認済み。`docs/decisions/transcript.md`）。そのため `host` は `localhost` と `127.0.0.1` しか受け取らない。

ライブラリ（`obs-websocket-js`）は入れない。使うのは名乗り（Identify）と2つの要求だけで、認証も SHA256 を2段重ねるだけなので WebCrypto で足りる。

## 撮るのは現在のプログラムシーン1枚

ソースを列挙して選ばせる形は採らない。ゲームだけでなくブラウザや資料のウィンドウも材料になるので、「どのソースを撮るか」を決めさせると配信者が配信のたびに設定を見直すことになる。プログラムシーンを撮れば、いま映っているものがそのまま材料になり、**配信者が入力するソース名はゼロ**で済む（`docs/principles.md` の「設定項目を増やさない」）。

幅は1280にした。1280と1920の両方でブラウザの本文がOCRで読めることを実測で確かめてあり、`GetSourceScreenshot` は obs-websocket が Complexity Rating 4/5 とする重い要求なので、ゲームと配信のエンコードと同居させるために狭いほうを選ぶ。

## パスワードは Worker の設定に置いた

obs-websocket のパスワードの置き場は3つ考えられた。

- **Worker の設定（KV）に置く**（採用）。読み上げの設定（`docs/decisions/speech.md`）と同じ形で、管理画面から変えられる
- 認証を切って localhost のみで待ち受ける前提にする
- 裏方のページのURLに載せる

採用したのは1つ目である。3つ目はURLがOBSのソース設定に平文で残り、配信中に変えられない。2つ目は配信者にOBS側の設定変更（認証を切る）を求めることになり、同じPC上の他のプロセスからOBSを操作できるようにしてしまう。

**引き換えに、オーバーレイ用キーが漏れるとOBSの全操作権も渡ることになる**（`GET /api/overlay/screen` の応答にパスワードが入るため）。オーバーレイ用キーはもともと合成オーバーレイのURLに載って配信者のOBSの中にあるもので、漏れたときは `/triggers/` で再発行できる。認証を切る選択肢も残す（パスワードを空にすれば認証のやりとりを行わない）ので、その判断は配信者に委ねる。

## 撮った画像はこのサイトに置かず、Gyazo に上げる

OCRを自前で持たず Gyazo に任せる。Workers AI の画像モデルに頼らずに日本語混じりの画面を読めるためである。R2（`MEDIA`）に画像を貯める形も採らない。材料として要るのは**画面に出ている文字**であって画像そのものではなく、15秒〜60秒ごとに撮った画像を配信のあいだ貯め続ける意味がない。

- **`access_policy` は `only_me`、`metadata_is_public` は `false`** にする。人に見せる必要がないうえ、2026-09-11 に Gyazo が受けた不正アクセスでは画像のメタデータ（OCRのテキストと画像ID）が流出している。配信者は「上げるのは公開済みの配信画面だけなので許容する」と判断したが、取り込む範囲は最小限にとどめる
- **OCR のテキストは `metadata.ocr` の下にある。** 公式ドキュメント（https://gyazo.com/api/docs/image ）は `ocr` をトップレベルに置くと書いているが実際は違う。ドキュメントどおりに書くと永久に空として扱う（OCRを取りに行く Phase 2 で効いてくる）
- API の回数は足りる。15秒間隔・4時間の配信でアップロード960回＋OCR取得960回の計1920回で、Gyazo の1日12,500回に収まる

## 配信していなければ、Gyazo へ上げない

`POST /api/overlay/screen` は、配信中の区切り（`stream_sessions` の `ended_at IS NULL` の行）が無ければ**上げる前に**捨て、捨てたことを応答（`{ recorded: false }`）で裏方のページに知らせる。上げてから記録するかどうかを決める形にすると、配信前の準備画面や配信後のデスクトップまで Gyazo に残ってしまう。捨てるのを失敗にしないのは、配信の前後にOBSを開いたままにしておくのが普通の使い方だからである（文字起こしの受け口と同じ考え方）。

一方、**Gyazo のアクセストークン（`GYAZO_ACCESS_TOKEN`）が設定されていないときは失敗させる**（Fail-Fast）。黙って捨てると、材料が貯まっていないことに配信が終わるまで気づけない。トークンは任意のシークレットで、`.dev.vars.example` ではコメントアウトしてある（Deploy to Cloudflare ボタンの入力欄に必須の項目として出さないため。OpenRouter の鍵と同じ扱い）。

## 記録は画像IDだけ

`screen_captures`（`migrations/0016_screen_captures.sql`）が持つのは画像ID・配信の区切り・撮った時刻の3つだけである。`image_id` を主キーにするのは、同じ画面を撮ったときに Gyazo が同じ画像IDへ畳むためで、画面が変わらないあいだは行が増えない。そのとき `captured_at` は最初のまま残す（その画面を最初に見た時刻が分からなくなるため）。

古い行は cron（`worker/collect.ts`。1日より前。配信中の区切りのぶんは残す）が消す。保持期間を文字起こしに揃えるのは、どちらも配信中だけ持つ材料だからである。

## 裏方のページの3つ目にした

撮る側は映すものを持たないので、合成ページ（`overlay/stage/`）の素材にはせず、裏方のページ（`overlay/backstage/`）の3つ目として載せた（`docs/decisions/backstage.md`）。1つの裏方の失敗でほかを止めない約束もそのまま適用する。

**既定では動かさない**（`?screen=true` を書いたときだけ動く）。読み上げと文字起こしと違い、OBS側のWebSocketサーバーと Worker 側の Gyazo のトークンの両方が要るので、何も用意していない配信者のブラウザソースが起動のたびに失敗を出さないようにする。

## まだ決めていないこと

- **撮影の間隔**。60秒から始め、実配信でOBSのCPUを見て詰める。間隔だけは撮るたびに設定を読み直すので、OBSを再読み込みせずに変えられる（ホスト・ポート・パスワードは起動のときにしか使えないので、変えたらOBSの再読み込みが要ると画面で知らせる）
- **OCRの取得と差分の抽出**（issue #122 の Phase 2〜4）。同じ画面を撮り続けたときに LLM へ渡る文字をほぼゼロにする篩（文字2連の重なり・Dice係数0.7）は実測で成立を確かめてあるが、このPRには入っていない
