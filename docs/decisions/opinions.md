# 意見ボード（`/opinions/`・素材の種類 `opinions`）

配信でテーマを出し、視聴者がチャットに書いた意見を観点ごとに並べて映したかった。dd2030 の「いどばたビジョン」（対話から課題と解決策を取り出し、論点を育てていく仕組み）を配信のチャット向けに組み直したもので、4段階の issue に分けた（#306 抽出と表示・#307 観点の提案・#308 取りこぼしの救い出しと論点の統合・#309 配信後のまとめ）。ここは #306〜#308 の判断を記す（#307 は「観点の提案（#307）」、#308 は末尾の「取りこぼしの救い出しと論点の統合（#308）」）。

## 配信のチャットで議論を拾うときの難しさ

配信のチャットは、意見を集める場として次の点で扱いにくい。設計はそれぞれへの答えとして決めた。

| 難しさ | 例 | 対策 |
|---|---|---|
| 同じ意見が何度も流れる | 「〇〇すればいい」が10人から届く | LLM が既にある意見への統合（join）に振り分け、意見を増やさない |
| 1つの意見が細切れで届く | 「AIのコメ返しは」「ちょっと寂しいかも」 | 同じ人が20秒以内に続けて書いたものをつなげ、続きを待つ（`worker/opinion.ts` の `readyUtterances`） |
| 前の発言を知らないと意味が分からない | 「それな」 | 返信先の発言を添えて LLM に渡し、短い返信は規則で落とさない |
| 意見ではない | 「草」・エモート・コマンド・別の話題 | 規則で落とせるものは LLM に渡さない。残りは LLM が ignore に振り分ける |
| 指示や荒らしが混ざる | 「以前の指示を無視して〜」 | 発言は材料であって指示ではないと伝え、返事を照合する。配信者が意見を隠せる |

## 人ではなく意見を単位にする（Polis 式を採らない）

Polis のように、視聴者に文への賛否を投票させて「投票の仕方が似ている人」のまとまりを地図に出す案も検討した。点が動いていく様子は配信向きだが、まとまりが形になるには、ある程度の人数が何度も投票する必要がある。この配信の規模では形になりにくく、Twitch の投票機能も誰が何に入れたかを返さない（自前でチャットの票を数えることになる）。そこで、意見を単位にして観点ごとに並べる形にした。

## 多数決に見せない

意見を「抽出して並べて俯瞰できる」ことを優先し、多数決に見える要素を合成ページから外した。

- **人数を映さない。** 似た意見は黙って1件にまとめ、人数は管理画面にだけ出す。合成ページへの読み出し（`readOverlayBoard`）は人数を返さない
- **人数で大きさや並びを変えない。** 論点は左右3つずつの枠に作った順で交互に置き、枠の高さは列の中の論点の数で等分する（意見の件数では変えない）。論点の中は新しい順にする（下の「1つの論点の意見を件数で切らない」）
- **賛否で塗り分けない。** 意見は札の種類（課題・解決策・問い・気づき）で区別する。いどばたビジョンの課題と解決策に、問いと気づきを足した
- **紹介する意見は人数で選ばない。** 中央の「いま紹介している意見」は、意見を作った順に8秒ずつ回す（`src/opinions/entry.ts` の `spotlightAt`）。少数の意見にも同じだけ出番が回る

案の比較（論点の島・帯・観点の俯瞰）は、モック（https://claude.ai/artifact/9kMTCDxamqPWcRE7LGisZu ）で行い、観点の俯瞰（案C）を採った。島は人数で円の大きさを変え、帯は人数で長さを変えるので、どちらも多数決に見えた。

### 1つの論点の意見を件数で切らない（issue #403）

はじめは1つの論点に出す意見を3件までにし、論点は前から3つずつ左・右の列に詰めていた。2026-10-16 の本番では、意見13件のうち11件が1つの論点に入り、論点が3つしか無かったため、画面に出たのは5件だけで、右の列は空のまま左上だけが埋まった（#401 のフィードバック「表示できる数に限界がある？」「左上に少しだけしか表示されてなかった」）。

- **論点は左右へ交互に置く。** 論点が少ないときに片側だけが埋まらないようにするため（`src/opinions/entry.ts` の `splitTopics`）
- **件数ではなく枠の高さで切る。** 論点の中の札はすべて置き、枠に収まらない古い札を見た目で隠す。隠れた意見も「いま紹介している意見」で回ってくる
- **枠の高さは列の中の論点の数で等分し、意見の件数では変えない。** 件数に合わせて枠を伸ばすと、意見の多い論点ほど大きく見えて多数決に見えるため。論点が1つしかない列ではその論点が列いっぱいを使うが、これは置き場所で決まる大きさで、件数では決まらない
- **収まるかは JavaScript で測らず CSS で決める。** 札の並びを縦向きの折り返す flex にすると、収まらない札は丸ごと次の列（枠の外）へ送られ、`overflow: hidden` で隠せる。測る方法は、合成ページの箱の大きさを変えたときや書体を読み込んだあとに測り直す仕組みが要るので採らなかった。折り返しでは各列の先頭の札が必ず置かれるため、1枚だけで枠より高い札（見出しが長い・箱が小さいとき）は下が切れるが、2枚目以降が途中で切れることはない

## 振り分けは新しい発言だけを扱う

LLM には、いまの論点と意見の一覧と新しい発言だけを渡し、発言ごとの振り分けを返させる。毎回すべての発言から振り分け直すと、配信が長くなるほど1回の入力が増えて無料枠を食うためである（あらすじを積み上げるのと同じ考え方。方針8）。

はじめは論点も作り直さず積み上げる形にしたが、#402 で、論点だけは意見の全体から作り直すように改めた（下の「論点を意見の全体から作り直す（#402）」）。意見そのもの（1文・札の種類・もとのコメント）はいまも作り直さない。

埋め込みのベクトルで意見を2次元に落とす方法（広聴AI 式）も採らなかった。意見が増えるたびに配置が動き、2次元の距離もほとんど意味を持たないためである。

## 返事を照合し、外れたらその回の発言を「失敗」にする

LLM の返事は信用しない（方針11）。渡した発言がすべてちょうど1回ずつ振り分けられていること、知らない意見・論点を指していないこと、札の種類・文字数・論点の数が上限に収まっていることを確かめ、1つでも外れたら切り詰めたり補ったりせずに拒む（方針4。`worker/opinion-sort.ts` の `parseOpinionSorting`）。

拒んだ回と LLM を呼べなかった回の発言は、振り分け待ちに残さず「失敗」（`opinion_comments.status = 'failed'`）にして、`opinion-sort-failed` を記録する。振り分け待ちに残すと、同じ発言で毎回失敗し続けて無料枠を食い続けるためである。黙って「関係ない」にもしない。失敗した発言は #308 で配信者が救い出せるようにする。

振り分けの結果は、論点・意見・コメントの状態を1つの batch で書く。作った意見をコメントから指すために、意見の最初のもとのコメントのID（`first_comment_id`。表で重ならない）を鍵にする。途中で失敗して「意見だけ増えてコメントが振り分け待ちのまま」という食い違いを作らないためである。

## 振り分けの間隔は Durable Object のアラームで刻む

cron（5分おき）では、配信中の議論に付いていけない。書いた意見が1分以内に画面へ出るよう、テーマを出しているあいだだけ45秒おきに振り分ける。Worker はタイマーを持てないので、`AdBreakTimer` の別のインスタンス（名前 `opinions`。`worker/opinion-timer.ts`）のアラームで刻む。新しい Durable Object のクラスを足すと PR のプレビューのビルドが失敗するため、ポモドーロ・漢字クイズと同じく既存のクラスに相乗りした。テーマが開いているかはアラームが鳴るたびに D1 を読んで決める（Durable Object は時計であって判定者ではない）。

間隔（45秒）は、続きを待つ時間（20秒）より長く、大きいモデルの応答（十数秒）を待っても次の回と重ならない長さにした。新しい発言が無い回は LLM を呼ばない。

## コメントはテーマを出しているあいだだけ貯める

チャットの全文は貯めないという方針の、意識して設けた例外である（`stream_chat_messages` と同じ）。意見のもとの発言を配信者が確かめられるようにし、拾えなかった発言を救い出せるようにするために、テーマを出しているあいだのコメントだけを `opinion_comments` に貯める。規則で落としたものも理由を付けて残す。

チャットの受け口（`worker/webhook-routes.ts`）は、まず開いているテーマを読み、出していなければ通知の断片も読み解かない。断片の読み取りはコメントビューアーと共有しており（`worker/comment-feed.ts` の `readChatBody`）、形の崩れた通知でコメントビューアーと同じ失敗を二重に記録しないためである。貯める処理の失敗は投げずに `opinion-record-failed` として記録し、作業机のコマンドやコマンドの応答を止めない。

## 振り分けのモデルは大きいものを既定にする

振り分けは、決まった形の JSON とラベル（C1・T3・O12）を守らせ、発言を40文字の1文にまとめさせる。軽いモデルでは形を外して照合で拒まれる回が増えると見込み、あらすじと同じ大きいモデルを既定にした。テーマを出しているあいだにしか呼ばないので、回数は配信者が決められる。

## 観点の提案（#307）

### 並べずに1つだけ問いかける

まだ誰も触れていない切り口は、候補を並べて見せず、LLM が1つだけ選んで視聴者への問いかけにする（合成ページの中央下の「こんな観点からも聞いてみたい」）。並べると、配信者がどれを拾うかを選ぶ手間が増え、画面も論点の枠と見分けにくくなるためである。問いかけはテーマの行（`opinion_themes.prompt`）に1つだけ持ち、履歴は持たない。

### 作り直すきっかけを「答えが届いた」に限る

問いかけを振り分けのたびに作り直すと、画面が落ち着かず、LLM の呼び出しも振り分けと同じ回数に増える。そこで、作り直すのは次の3つに限った。

- 問いかけがまだ無いあいだに、新しい意見ができたとき（テーマを出した直後は、材料が無いので作らない）
- 振り分けの LLM が、発言のどれかを「問いかけへの答え」（`answersPrompt`）と返したとき
- 配信者が `/opinions/` で「別の問いかけにする」を押したとき

「答えか」は別の呼び出しで尋ねず、振り分けの LLM に返させる。振り分けは発言を1件ずつ読んでいるので、同じ呼び出しで判断させれば回数が増えない。作り直す必要があるかは、その回の振り分けの結果と、振り分けに渡した問いかけだけから決まるので、「作り直し待ち」の印を表に持たない。作り直しに失敗したら前の問いかけを残し、次の答えが届くまで作り直さない（失敗のたびに作り直すと、無料枠を食い続けるため）。

問いかけが上限（40文字）を超えたら、切り詰めずに拒んで前の問いかけを残す（方針4）。切り詰めた問いは、問いとして意味が通らないことが多いためである。

### Jev で振り分けの前に絞り込む（いまは記録だけ）

規則（コマンド・エモートだけ・短い反応）を通った発言には、まだ雑談や荒らしが混ざる。振り分けの LLM にも ignore を選ばせているが、入力が増えるほど形を外して拒まれる回が増える。そこで、振り分けの前に Jev の Noul で「テーマについての意見・課題・提案・問いか」を尋ね、確率がしきい値に届かない発言を LLM に渡さない形にした。Jev は質問を並列に評価するので、その回の発言（最大30件）をまとめて1回で尋ねる。返信は返信先の発言を添えて尋ねる（「それな」だけを見て落とさないため）。

しきい値（`OPINION_FILTER_THRESHOLD`）は、実配信で落としすぎていないかを確かめるまで 0 にして、確率を `opinion_comments.jev_score` に記録するだけにした。意見を落とすのは取り返しがつきにくく（#308 で救い出せるとはいえ、配信中には見えない）、確率の分布を見てから決めるほうが安全なためである。しきい値は Jev の版（`JEV_MODEL`）ごとに決め直す。

Jev の失敗は、黙って全件を通さず、その回の発言を失敗にする（方針4。振り分けの LLM の失敗と同じ扱い）。一方、OpenRouter の鍵が無い配信者では Jev を呼べない。振り分けは既定で Workers AI なので、鍵が無くても意見ボードは使えてきた。鍵が無いことで毎回すべての発言を失敗にすると、意見ボードそのものが使えなくなるため、**鍵が無いときだけ**絞り込みを飛ばすことにした（配信者の判断。市町村紹介の共通点が鍵の有無で作るかを決めるのと同じ考え方）。これは鍵の有無で決まる分岐で、Jev の失敗を飛ばすのとは違う。

Jev で落とした発言は、規則で落とした `dropped` と分けて `filtered` にする。#308 で救い出すときに、どちらで落ちたかを配信者が見分けられるようにするためである。SQLite は CHECK を書き換えられないので、`opinion_comments` を作り直して移した（`migrations/0034_opinion_prompts.sql`）。

## 取りこぼしの救い出しと論点の統合（#308）

### 新しい意見は LLM に下書きさせ、配信者が直して保存する

落としたコメントを「新しい意見にする」とき、1文・札の種類・論点を配信者が一から書く案と、LLM に下書きさせる案があった。配信中に40文字の1文と論点を考えるのは手間なので、**LLM に下書きさせ、保存は配信者が直してから行う**形にした（配信者の判断）。下書きは保存しないので、LLM が勝手に意見を増やすことはない。

下書きの箇所は振り分けと同じ `opinionSort` を使い、新しい箇所を足さなかった。発言から意見を作るという同じ仕事で、モデルの向き不向きも同じだからである。下書きの照合は、配信者の入力の検証（`parseRescuedOpinionInput`・`topicChoiceProblem`）をそのまま通す。LLM の返事と配信者の入力で、受け付ける範囲を食い違わせないためである。

### 論点は配信者がまとめる

細かく分かれすぎた論点は、配信者が「ほかの論点とまとめる」で1つにする。まとめ先の名前を残し、名前を変えたければ「名前を変える」を使う。はじめは「LLM にまとめ直させると、論点が呼び出しのたびに入れ替わって配信画面が落ち着かない」として LLM にまとめ直させなかったが、#402 で LLM にも論点を作り直させるように改めた（下の「論点を意見の全体から作り直す（#402）」）。配信者が整えた名前は、作り直しでも変えない。

まとめると論点は消えるので、振り分けの LLM を待つあいだにまとめられた論点を、返事が指すことがある。そのときは意見を書かず、コメントを振り分け待ちに残して次の回に振り分け直す（`applySorting`。コメントの状態の更新を、意見が書けたときに限った）。論点が上限（6つ）に達していたときも同じにした。どちらも、LLM の返事を失敗として捨てるほどの誤りではないためである。

### 締め切ったあとも救い出せる

配信の終わりにテーマを締め切ってから落ち着いて整理したい、という使い方を考え、救い出しと論点の整理は**最後に開いたテーマ（管理画面に出ているもの）なら締め切ったあとも**行えるようにした（配信者の判断）。締め切ったときに振り分け待ちだったコメントは、締め切ったあとは振り分けられないので、救い出しの一覧に出す。開いているあいだの振り分け待ちは出さない。振り分けのアラームと同じコメントを取り合い、二重に意見になるのを避けるためである。

### 規則・Jev・LLM・失敗を分けて数える

コメントの内訳は、規則で落としたもの（理由ごと）・Jev が落としたもの・LLM が無関係としたもの・振り分けに失敗したものを分けて出す。どこで取りこぼしているかが分かれば、規則やしきい値（`OPINION_FILTER_THRESHOLD`）を直す手がかりになるためである。

## 配信後の振り返り（#309）

### テーマと配信を、テーマを開いた時刻で結ぶ

テーマと配信（`stream_sessions`）は直接つながっていない。結び付きを表に持つ案（テーマを開くときに配信のIDを書く）は、配信の開始の検知が cron や Webhook に依存し、開く時点でまだ配信が記録されていないことがあるため採らなかった。代わりに、テーマを開いた時刻（`opinion_themes.opened_at`）が配信の開始から終了（配信中なら現在）に入るかで結ぶ（`worker/opinion-store.ts` の `readThemeReviews`）。配信の前に開いたまま配信に入ったテーマは、その配信には出ない。この取りこぼしより、マイグレーションと書き込みの経路を増やさないことを優先した。

### 振り返りでは人数を出し、隠した意見も残す

合成ページに人数を出さない方針（多数決に見せない）は、視聴者の見るものにだけ当てはまる。配信者が後から読む振り返りでは、人数が「どの意見がどれだけ共感されたか」を読み返す材料になるので、管理画面と同じく出す。隠した意見も、隠した判断を見返せるよう hidden つきで残す。意見にならなかったコメントは、原文を並べると画面が長くなり、救い出しは `/opinions/` で行うので、件数の内訳だけにした。

### テーマごとの区切りを持つ

振り返りはテーマ1つを1つの区切り（`OpinionThemeReview`）として返す。締め切ったときの機械のまとめ（合意が見える点・意見が分かれた点・残った問い）は、この区切りの中に足す。配信者のメモと混ぜず、機械が作ったものと分かる見出しを付ける。

### コメントビューアーには印を付けない

コメントビューアー（`/comments/`）の行に「意見になった」「落とした」の印を付ける案は見送った（配信者の判断）。救い出しは `/opinions/` の一覧で完結し、コメントビューアーに意見ボードの表を読ませると、両者の結び付きが増えるためである。

## 配信後のまとめ（#309）

### まとめは機械が作ったものとして分け、配信者のメモと混ぜない

テーマを締め切ったとき、集まった意見から「合意が見える点・意見が分かれた点・残った問い」を LLM に作らせる。配信者が確かめた結論ではなく、意見を読んだ機械の要約なので、`/opinions/` では「AIのまとめ」の見出しと「機械が作成」の印を付けた別の枠に出し、意見の一覧（配信者が隠す・整理する対象）とは混ぜない。人数は材料にもまとめにも入れない。「多数派」「少数派」といった言い方で優劣が付くと、多数決に見せないという方針（#306）が振り返りで崩れるためである。合成ページにはまとめを渡さない。

### 締め切りは応答を待たせず、まとめの失敗で締め切りを取り消さない

まとめは 70B 級のモデルが全意見を読むので数秒かかる。締め切りの応答に載せると、配信者の「締め切る」が待たされ、LLM の失敗で締め切りが失敗に見える。そこで、締め切り自体は先に成功させ、まとめは応答のあと（`waitUntil`）に作る。振り分けのように Durable Object のアラームに預ける案もあったが、締め切りのたびに1回しか呼ばず、間隔を見張る必要もないので、既存の `waitUntil`（アラートの動作が使っている）にした。作れなかったときは行を書かずに `opinion-summary-failed` を記録し、配信者は `/opinions/` の「まとめを作る」でやり直す。自動では再試行しない（無料枠を食い続けないため。方針4）。

### 返事は切り詰めずに拒む

まとめの返事は `parseOpinionSummary` だけが照合する。JSON でない・欄が配列でない・項目が多すぎる（5個まで）・長すぎる（80文字まで）・項目が空・全部の欄が空、のどれかなら、切り詰めたり補ったりせずに拒む（問いかけの照合と同じ方針）。前のまとめがあれば、作り直しに失敗しても残す。意見が無い（またはすべて隠している）テーマは LLM を呼ばず、まとめを書かない。

### 作り直しは配信者が押す

締め切ったあとに意見を隠す・論点をまとめると、まとめが古くなる。自動で作り直すと、整理のたびに LLM を呼んで無料枠を使うので、配信者が「まとめを作り直す」を押したときだけ作る。

### 箇所を分ける

箇所は `opinionSummary` として振り分け・問いかけと分けた。仕事の性質（全体を読んで JSON の3欄を作る）と呼ぶ回数（締め切りごとに1回）が違い、使用状況とモデルを別に選べるようにするためである。既定は振り分けと同じ大きいモデル。

### 保存先は専用の表にした

テーマの行に列を足す案もあったが、まとめは締め切ったあとに作り直して置き換える別の寿命のデータで、3つの欄を持つ。そこで `opinion_summaries`（テーマのIDが主キー）を足した（`migrations/0035_opinion_summaries.sql`）。各欄は文字列の JSON 配列で、読むときに形を確かめ、壊れていれば黙って空にせず投げる。ダッシュボードの配信の詳細へ出す作業は、テーマのIDで読める `readThemeSummary` を使って別に行う。

### ダッシュボードの振り返りでは、まとめを読むだけにする

ダッシュボードの配信の詳細には、テーマの区切りの中に `/opinions/` と同じ「AIのまとめ」の枠（`src/opinions/summary-card.tsx`）を使い回して出す。機械が作ったものと分かる見た目を1か所で保つためである。作り直しのボタンは置かない。作り直せるのは最後に開いたテーマだけ（`POST /api/admin/opinions/themes/:id/summary`）で、過去の配信のテーマにボタンを出すと押しても404になるうえ、振り返りは記録を読む場所だからである。締め切っていないテーマには枠を出さない（まとめは締め切ったときに作るため）。

## 論点を意見の全体から作り直す（#402）

2026-10-16 の本番で、テーマ「ネタバレ・指示厨対策」の意見13件のうち11件が論点「指示厨の特徴」に入った。中には「指示コメントにはハートをつけてもらう」「強制タイムアウトし、三度でBANする」のような対策も含まれ、論点の名前と中身がずれていた。論点は上限の6つまで3つ空いていたが、LLM は新しい論点を作らなかった（#401 のフィードバック「カテゴリーの再グルーピングがされない」）。原因は2つで、振り分けの指示文に論点を分ける基準が無かったことと、論点を作り直さない作りだったことである。Talk to the City や広聴AI と同じく、集まった意見の全体からまとめを作り直す考え方に改めた。

### 「作り直さず積み上げる」「LLM にまとめ直させない」を覆した理由

はじめの2つの理由は、次のとおり外れると判断した。

- **入力が増えて無料枠を食う**: 1つのテーマの意見は数十件の規模で、作り直しの材料は意見の1文（40文字まで）とラベルだけである。毎回ではなく意見が5件増えたとき（`REGROUP_OPINION_STEP`）と締め切ったときに限るので、1つのテーマで数回にとどまる。発言そのものはこれまでどおり新しいものだけを振り分けの LLM に渡す
- **論点が入れ替わって画面が落ち着かない**: 分け直した論点を、もとの論点のうち意見の重なりが最も大きいものに対応させ、論点のIDを保つ（`worker/opinion-regroup.ts` の `planRegrouping`）。合成ページの枠の位置は論点の作った順（ID）で決まるので、名前と中身が変わっても位置は変わらない

あわせて、振り分けと作り直しの両方の指示文に、論点を分ける基準（`TOPIC_CRITERIA`。名前が中の意見すべてに当てはまること・「〇〇の特徴」と「〇〇への対策」は分けること）を入れた。

### 作り直すのは割り当てと名前だけにする

意見の1文・札の種類・もとのコメントは作り直さない。意見は人の発言と結び付いており（人数ともとのコメント）、作り直すたびに文が変わると、配信者が隠した・救い出した意見の扱いが崩れるためである。

### 対応づけは重なりの大きい組から決める

もとの論点と分け直した論点の組ごとに、もとの論点の隠していない意見のうち分け直した論点に入った数（重なり）を数え、大きい組から1対1で対応させる（同じ数なら先に作った論点・応答で先の論点）。対応しなかった分け直した論点は新しく作って後ろに足し、対応しなかったもとの論点は消す。ハンガリー法のような最適な割り当ても考えたが、論点は6つまでで、大きい重なりから決めれば画面の上でも「大部分を引き継いだ論点が位置を継ぐ」と説明できるので、貪欲に決めた。

### 隠した意見は材料にせず、行き先だけ決める

隠した意見は LLM に渡さない（合成ページに出す論点の名前の材料に、荒らしの文を入れないため）。もとの論点が残ればそのまま残し、消えるなら、その論点の意見を最も多く受け取った論点へ移す（意見の行き先を無くさないため）。隠した意見しか無い論点は作り直しに加えず、その数だけ論点の上限を減らし、その名前を使わせない（表の UNIQUE と上限6つを守るため）。

### 配信者が整えた名前は固定する

issue では「配信者が付けた名前・まとめた論点を上書きしてよいかは実装時に決める」としていた。配信者が「名前を変える」で付けた名前と、「ほかの論点とまとめる」でまとめ先にした論点の名前は、作り直しでも変えないことにした（`opinion_topics.title_locked`）。配信者が選んだ名前を機械が黙って書き換えると、整えた意味がなくなるためである。中の意見は入れ替わりうる（固定するのは名前と位置だけ）。意見の割り当てまで固定すると、名前と中身のずれ（#402 の発端）を配信者の操作のあとは直せなくなるためである。

はじめは、重なりで対応したあとに固定した論点の名前を戻す形にしたが、LLM が固定した名前を別の論点に付けると名前が重なり、LLM を呼んだあとで作り直しごと拒むことになった。重なりが小さい固定の論点が対応からあぶれて消えることもあった（いずれも `/code-review` の指摘）。そこで、固定した名前を LLM に「必ずそのまま使う名前」として渡し、使っていなければ照合で拒み、その名前の論点を重なりより先に、もとの論点へ対応させる形に改めた。

### 引き受けは数で覚え、失敗しても戻さない

作り直すかどうかは、前に引き受けたときの意見の数（`opinion_themes.regrouped_opinions`）と比べて決め、確かめと書き込みを1つの文で行う（`claimRegroup`）。LLM が失敗した・返事が照合を通らなかったときも数は戻さない。戻すと、同じ盤面で振り分けの回ごとに失敗し続けて無料枠を食うためである（振り分けの失敗をその回の発言の「失敗」にするのと同じ考え方）。次は意見がさらに5件増えたときに作り直す。

### 待つあいだに盤面が変わったら書かない

計画は読んだときの盤面に対して立てるので、LLM を待つあいだに配信者が隠す・救い出す・名前を変える・まとめるなどをしたら、書かずに見送り `opinion-regroup-failed` を記録する（`applyRegrouping`）。振り分けは同じアラームの中で作り直しの前に終えているので、振り分けと取り合うことはない。

はじめは書く前に盤面を読み直して比べていたが、比べてから書くまでのあいだの変更を見落とす（`/code-review` の指摘）。D1 の batch は1つのトランザクションなので、batch の最初の文で盤面を文字列にして比べ、違えば NOT NULL に当たる行を入れようとして batch ごと失敗させる形にした。盤面の文字列は、論点の名前を UTF-8 の16進にして並べ方の違いを避ける（JavaScript と SQLite で文字の比べ方が違うため）。

仮の名前ははじめ NUL 文字で始めていたが、D1 での NUL の扱いが確かでないので、論点の名前の上限（12文字）より長い普通の文字列にした。

### 振り分けの回では最後に、締め切りではまとめと並べて行う

作り直しは LLM に意見の全体を渡すので、時間がかかる。振り分けの回では問いかけを待たせないよう最後に行う。締め切りでは、経路の `waitUntil` が応答のあと30秒ほどで打ち切られるため、まとめと順に待たずに並べて行う。まとめは論点の名前ではなく意見から作るので、作り直す前の論点を材料にしてよいと判断した。

### 箇所を分ける

箇所は `opinionRegroup` として振り分けと分けた。仕事の性質（全体を読んで全件を漏れなく分ける）と呼ぶ回数が振り分けと違い、使用状況とモデルを別に選べるようにするためである（まとめを `opinionSummary` に分けたのと同じ）。既定は大きいモデル。

### CPU の上限

作り直しはアラーム（`AdBreakTimer`。Workers Free の CPU 上限は1回10ms）の中で振り分けのあとに行う。LLM を待つ時間は CPU に数えられず、CPU を使うのは指示文の組み立て・返事の照合・対応づけ・盤面の比較である。手元（Apple Silicon・Node.js）で意見60件・論点6つの盤面を測ると1回あたり約0.14msで、上限に対して十分に小さい。


## 締め切ったテーマを1分で消す

はじめは、締め切ったテーマを次のテーマを出すまで合成ページに残していた（結果を見せ続けるため）。しかし実配信で「終わったのに残り続ける」と言われ、まず下部バーの「演出を消す」を足し（`docs/decisions/overlay-stage.md`）、続けてチャットで推理の終えたゲームと揃えて、締め切ってから1分で消すことにした。どの演出がいつ消えるかを配信者が覚えやすいよう、長さは `src/core/ended-reveal.ts` の `ENDED_REVEAL_MS` を両方で使う。

- 消すかどうかは合成ページが現在時刻と `closedAt` だけから決める（描画とパラメータの約束どおり、フレーム間の状態を持たない）。そのため OBS で読み込み直しても戻らず、Worker の応答は変えない
- 「演出を消す」の片付け（`dismissed_at`）は残す。1分を待たずに下げたいときのためである
