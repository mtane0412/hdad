# 手書きの判断の記録

配信中に描いた線を配信画面へ出す仕組み（issue #131）について、なぜこの形にしたかを残します。いま守るべき約束は `.claude/rules/draw.md` にあります。

## 別のアプリを描画に使い、ウィンドウキャプチャで取り込む形は採りませんでした

Excalidraw のような描画アプリを別のウィンドウで開き、OBSのウィンドウキャプチャで取り込む方法が最初の案でした。これを採らなかったのは、キャプチャ対象のウィンドウ・切り抜き位置・透過の設定を配信のたびにやり直すことになり、安定しないためです。

ブラウザソースであれば、貼るURLは1本で、位置も大きさも透過もOBS側の設定として固定されます。この安定さは、合成オーバーレイ（`docs/decisions/overlay-stage.md`）で素材を1枚にまとめたときと同じ理由で価値があります。

## Excalidraw を描く画面に埋め込む案より、自前の手書きを採りました

`@excalidraw/excalidraw` を描く画面に埋め込み、確定した図を SVG にして送る案も検討しました。矢印・図形・テキストが最初から揃うという大きな利点があります。

採らなかったのは、**送るのが点列だけで済む自前の手書きなら、線が伸びていく過程がそのまま配信に出る**ためです。スナップショットを送る形では、完成した図が唐突に現れるだけになります。配信の素材としては、描いている手つきが見えることのほうが価値があると判断しました。

その代わり、矢印・図形・テキストは持ちません。必要になったときに、ここに書き足したうえで追加します。

## 中継先は `AlertChannel` に相乗りさせず、新しい Durable Object にしました

アラートの配送（`docs/decisions/alerts-overlay.md`）とは、向きも量も違います。

- 向き: アラートは「Workerが押し出し、DOは配るだけ」ですが、手書きは接続から届いたものを他の接続へ中継します（`webSocketMessage` の実装が要ります）
- 量: 1本の線を引くあいだに毎秒20〜30通が流れます。同じDOに通すと、アラートの配送がこの負荷を被ります

`wrangler.jsonc` の `migrations` に tag を1つ追加する手間はかかりますが、分けました。

## 描ける接続と見るだけの接続を、目印（タグ）で分けました

合成ページはオーバーレイ用キーで中継先へつなぎます。このキーはOBSのURLに入るだけでなく、配信画面に映り込むこともありえます。キーを持つだけで他人の配信画面に描けてしまうのは困るので、**描く側として受け入れるのは配信者のセッションで守られた経路だけ**にしました。

受け入れるときに `ctx.acceptWebSocket(server, [role])` で目印を付け、中継するかどうかを `getTags` で決めています。

## WebSocketの接続では、`Origin` を自分で確かめています

管理用APIの入口（`worker/http.ts` の `requireAdmin`）は、書き換えを伴うメソッドでだけ送信元（`Origin`）を確かめます。WebSocketの接続はGETなので、この確認が働きません。

WebSocketのハンドシェイクはトップレベルの画面遷移ではないため、`SameSite=Lax`（`worker/http.ts:150`）のクッキーが別サイトからの接続に付くことはありません。それでも `worker/draw-routes.ts` が `Origin` を自分で確かめているのは、**ブラウザの決まりだけに頼らないため**です。これは `requireAdmin` が「クッキーは `SameSite=Lax` だが、ブラウザが必ず付ける `Origin` でも確かめる」としているのと同じ考え方で、描かれた線が配信画面にそのまま出る以上、守りは重ねておきます。

## 座標と太さを比で持つのは、箱の大きさが揃わないためです

描く画面のキャンバスと、合成ページで手書きに割り当てられた箱は大きさが違います。画素で送ると、載せた箱の大きさによって図が歪みます。線の太さも同じ理由で箱の幅に対する比で持ちます。

縦横比まで揃わないと図は歪むので、描く画面のキャンバスは配信画面と同じ 16:9 で置き、手書きの推奨の大きさ（`src/overlay/layout.ts` の `RECOMMENDED_ITEM_SIZES`）も配信画面と同じにしています。

## 描き始めを受け取っていない線の続きは、黙って捨てます

合成ページを線の途中で開くと、描き始め（`start`）を受け取らないまま続き（`extend`）だけが届きます。描き始めの分からない線は描きようがないので捨てます。**異常ではないので知らせません**（このリポジトリの Fail-Fast に意識して設けた例外です）。

## 描く画面は、自分のキャンバスにも描きます

中継先は送り主へ返さない（返すと同じ線を二重に持つ）ので、描く画面は送ると同時に自分の集まりへも積みます。返りを待つ形にすると、描いている本人の手元だけが往復のぶん遅れて見えます。

## 線には縁取りを付けました

配信画面には明るいところも暗いところもあるので、1色で描くとどちらかで線が沈みます。そこで**同じ形を「少し太い黒」で描いてから、その上に本来の色で描く**（2度描き）ことで縁取りを作りました。

丸（点を1つだけ打ったとき）は太さではなく半径で大きさが決まるため、段ごとにパスを引き直しています。同じパスを塗り直すだけでは縁が見えません。

選べる色に黒を置いていないのも同じ理由です。縁取りが黒なので、暗い線は縁取りと溶け合って形が分からなくなります。

## 選べる色と太さは1か所（`src/draw/tools.ts`）だけが持ちます

描く画面と合成ページの両方がここを読みます。2か所に持つと、片方だけ色を増やしたときに「送れるのに受け取り側が弾く」食い違いが起きます。やりとりに載せるのは名前（`red`・`bold`）だけで、色の値と太さの比は受け取った側が引きます。

一覧にない名前が届いたときは、黙って既定に戻さずエラーにします（`colorOf`・`widthOf`）。既定で描いてしまうと、配信画面に意図しない色の線が出たまま原因に気付けません。

## 全消しはゴミ箱のアイコンだけにしました

`src/core/icon-button.ts` には「取り返しが重いコマンドは文字を残す」という注意がありますが、全消しはこれに当てはめませんでした。**ゴミ箱の形だけで何をするかが伝わる**ためです。

戻せない操作であることは色で伝えます。ただし塗りつぶしの赤はツールバーに置きっぱなしになるには目立ちすぎるので、アイコンだけを赤くしています。

## 全消しに確認を出しません

配信中に確認のダイアログを挟むほうが、押したのに消えないという事故のもとになると判断しました。

## 消しゴムは、触れた線を1本まるごと消します

なぞった範囲だけを削る消しゴムにはしませんでした。配信中に消したいのは「さっき引いた丸」「この矢印」のような線ひとつ単位で、範囲を削ると線の切れ端が残って、かえって消し残しを何度もなぞることになるためです。

1本まるごと消す形なら、合図は線の名前だけで済みます（`{ type: 'erase', id }`）。範囲を削る形では、1本を複数に分けた結果の形を送り直す必要があり、中継と保存の両方が重くなります。

当たり判定（`src/draw/erase.ts`）は、点どうしではなく「消しゴムが動いた線分」と「線の各区間」の距離で見ます。ポインタの動きは飛び飛びに届くので、点だけで見ると素早く動かしたときに細い線をまたいでも当たりません。距離は比のままではなく画素に直してから測ります（キャンバスが16:9なので、比のままだと縦と横で当たりの広さが変わります）。当たりの広さは、消しゴムの半径（箱の幅の1%）に線の太さの半分を追加したものです。

消しゴムを押しているあいだは送るだけにして、保存はポインタを離してから線を引き終えたときと同じ間引き（`src/draw/save.ts`）に乗せます。

ひとつ戻すは、消しゴムで足りるかを実際の配信で確かめてから決めます。

## 道具箱はアイコンだけで1行に収めます

はじめはペンと消しゴムに文字を添え、色・太さを並べ、背景のスイッチと濃さを別の行に置き、仕様の説明をキャンバスの上下に書いていました。配信中に使う画面としては、文字と説明が多くて目が散り、道具箱が2行にまたがっていました。

そこで、道具はすべてアイコンにして1行に収めました。色と太さは「いま選んでいるもの」をアイコンにし、押すと選択肢が開きます（選ぶと閉じます）。背景は押すたびに敷く・外すが入れ替わるアイコンにし、濃さは敷いているあいだだけ出るアイコンからスライダーを開きます。

消しゴムが「触れた線を1本まるごと消す」ことは形だけでは伝わりませんが、文字は道具箱に置かず、ホバーの名前と右端のiボタンの説明に寄せました。一度知れば足りる仕様で、毎回目に入る必要はないためです。背景を撮った時刻も同じくiボタンに寄せ、読めない・まだ無いといった気付いてほしい知らせだけを道具箱の下に出します。

## 背景には、画面の取り込みが Gyazo へ上げた最後の1枚を使います

描く画面に配信画面を敷くと、どこに描けばよいかが分かります。案は3つありました。

- **Twitch の埋め込みプレイヤー** — 採りませんでした。Twitch の埋め込みの要件に「Embeds … should not be obscured in any way by other page elements」とあり、キャンバスを重ねた時点でこれに反します。映像も数秒遅れ、配信していないと映らず、自分の描いた線が遅れて二重に映ります
- **Worker に届いた1枚を手書きの中継先（`DrawChannel`）の storage に持っておく** — 一度この形で作りましたが、やめました。費用は問題になりません（書くのは配信中に撮るたびの1回で、1日10万行の無料枠に収まる）が、1件2MBの上限のために画像を切り分けて置く仕組みが要り、「中身を読まずに中継するだけ」の中継先に画像の保管を持ち込むことになります
- **Gyazo に上げた最後の1枚を使う** — 採りました。撮った1枚は画像IDとともに D1（`screen_captures`）に記録済みなので、最新の1行を引けば背景が決まります。自前で画像を持つ仕組みが要りません

Gyazo の画像を描く画面のブラウザから直接読めるよう、画面の取り込みで上げる画像の公開範囲を `anyone`（URLを知っていれば見られる）に変えました（`docs/decisions/screen.md`）。実際の Gyazo で確かめたところ、`only_me` の画像の `url` は、認証なし・アクセストークンをクエリやヘッダーで付けても404で、一覧（`GET /api/images`）の応答に付く `jwt_token`（有効期限は約24時間）を `Authorization: Bearer` で渡したときだけ読めました。一覧には取り込み以外の配信者の画像も混ざるので、目的の1枚を一覧から探して署名を得る形は壊れやすいと判断しました。

Worker（`GET /api/admin/draw/background`）は D1 から最新の画像IDを引き、画像IDを印（ETag）にします。手元と同じ1枚なら Gyazo を呼ばずに304を返し、新しい1枚のときだけ Gyazo の `GET /api/images/:id` で画像のURLを引いて返します。画像そのものは中継しません。描く画面は Gyazo の画像の置き場（`https://i.gyazo.com`）以外のURLを背景に読み込みません。

配信していないあいだに撮られた1枚は、これまでどおり Gyazo へ上げずに捨てるので、背景は最後に配信した時点の1枚になります。`screen_captures` は古い記録を1日で消しますが、**最後に撮った1行だけは消さない**ようにしました（何日も配信しないと背景がなくなるため）。

描く画面はスイッチを入れているあいだだけ15秒おき（撮る間隔の最短）に読みに行きます。背景の濃さは既定で60%にしてあります（背景は位置の目安にすぎないので、線より目立たせません）。公開範囲を変える前に上げた画像はブラウザから読めないので、その旨を出し、次に撮られた画面から背景に出ます。

背景は撮る間隔のぶん古い画面です。動いているものを追って描く用途には向きませんが、画面の構成を見て指す用途には足りると判断しました。

## 描いたものはKVに残し、書くのは線を引き終えた時点だけにしました（issue #133）

中継先（`DrawChannel`）は開いている接続の間だけの通り道なので、OBSのブラウザソースを作り直したりOBSを再起動したりすると、それまでに描いたものが消えます。配信中にブラウザソースを作り直す場面はあるため、描いたものを残すようにしました。

保存先はKV（`worker/draw-config.ts`。鍵は `draw-strokes`）です。Durable Object のストレージに持たせる案もありましたが採りませんでした。**中継先を「配るだけの通り道」に保つため**です（設定や状態を持たせない方針は `docs/decisions/alerts-overlay.md` と同じで、ほかの設定の保存先もすべてKVに揃っています）。

書き込みの合図は**線を1本引き終えた時点（ポインタを離した時点）**だけにしました。描いている最中の点ひとつごとに書くことは、KVの書き込み回数の面でも成り立ちません。さらにそこから数秒まとめてから1度だけ書きます（`src/draw/save.ts` の `SAVE_DELAY_MS`）。続けて何本も引くあいだの書き込みをまとめるためです。

間引きを**描く画面の側に置き、Workerは受け取ったものを検証して書くだけ**にしたのは、Workerに「まだ書かない」という状態を持たせたくなかったためです（Workerは要求ごとに立ち上がるので、待っているあいだの状態を持てません）。

**全消しだけは待たずに書きます。** 消したのに残っているのは困る向きの誤りなので、遅らせません。待っている書き込みも取り消して置き換えます（消したあとに「線がある状態」を書くと、消した図が戻ってきます）。

## 保存されているものを読めるまでは、書き込みません

描く画面は開いたときに保存されているものを読みますが、その応答が返る前でも線は引けます。このとき引き終えた線をそのまま書くと、**まだ読めていない「前に描いた図」を上書きして消してしまいます**。読み出しに失敗したときも同じです。そこで読めるまでは書かず、読めなかったときは「描いたものは保存されません」と画面に出します。

読めるまでのあいだに引いた線は、読めた時点でまとめて書きます。次の線を引くまで保存されないままにしておくと、1本だけ引いて描く画面を閉じたときに残りません。

例外は全消しです。全消しは「保存されているものを全部無かったことにする」操作なので、読めていなくても書いてよく、押したあとは書き込みを始めます。全消しのほうが読み出しの応答より先に済んだときは、**あとから届いた保存ぶんを描き直しません**（消した図が戻ってきてしまいます）。

## 画面を離れるときは、待っている書き込みを書き切ります

間引き（数秒）の途中で `/draw/` を離れると、最後に引いた数本が保存されないままになります。そこで離れるときは待っている書き込みを捨てずに書きます（`src/draw/save.ts` の `flush`）。捨てる `cancel` も残してありますが、いまは使っていません。

## 「描いた直後の再読み込みで最後の数本が欠ける」のは、取り繕わずに受け入れました

KVは書き込みが他の拠点へ届くまで最大60秒かかり、加えて上の間引きで数秒待ちます。そのため**描いた直後に合成ページを読み込み直すと、最後の数本が出ない状態が起こりえます。**

これを埋めるには、描く画面と合成ページのあいだで「いまの全体像」をやりとりする仕組み（合成ページが開いたときに描く画面へ問い合わせる、など）が要ります。中継先を中身を読まない通り道に保つ方針と引き換えになるため、採りませんでした。**再読み込みは配信中に何度も起こることではなく、欠けたら描き直せば済む**という判断です。

## 保存した図は、配信をまたいでも残します

配信の開始を合図に消す案もありました（前の配信の図が次の配信に出てしまうのを防げます）。採らなかったのは、**配信の開始の検知に手書きの処理を追加することになる**割に、残っていて困る場面が実際にあるか分からないためです。消えるのは配信者が全消しを押したときだけにし、困るようなら後から追加します。

## 線1本ぶんの判定は `src/draw/strokes.ts` に置き、Workerからそれを読んでいます

保存した線は、Workerが受け取るとき（`worker/draw-config.ts`）と、画面が応答を受け取るとき（`src/draw/api.ts`）の2か所で形を確かめます。この判定（`isStroke`）を2か所に書き分けると、片方だけが通す形ができてしまいます。

判定には選べる色と太さの一覧が必要で、それは `src/draw/tools.ts` だけが持つ約束です。そこで**`worker/draw-config.ts` から `src/draw/` を読み込みました**。`worker/` が `src/` を読み込む唯一の場所です。`src/draw/strokes.ts` と `tools.ts` はDOMを使わない純粋なデータと判定だけなので、Worker用の型チェック（`tsconfig.worker.json`）でも通ります。

逆向き（ブラウザ用のコードが `worker/` を読み込む）は引き続き禁止です。Workerの型はCloudflareのランタイムのものを含むためです。

## 保存する量の上限は、画面が持っている上限をそのまま使いました

線の本数は `MAX_STROKES`（500本。毎フレーム描き直す都合で決めた数）をそのまま保存の上限にしました。1本の点の数には `MAX_POINTS_PER_STROKE`（4000点。毎秒30点なら2分ほどの連続した1本）を設けました。KVの1件の大きさに当たらないためで、上限を超えたものは黙って切り詰めずに拒みます。

何本ぶん残せば足りるかは実際に使ってから決めます。

## まだ決めていないこと

- **点のまとめ方**。いまはポインタの動き1回につき1通を送ります。フレームごとにまとめる最適化は、実配信で通信量を見てから判断します
- **保存する線の本数**。いまは画面が持つ上限（500本）をそのまま使っています。KVに書く1件が大きくなりすぎるようなら、古いものから落とす形にします
