# 漢字クイズ（issue #293・#300・#301・#302）

チャンネルポイントの交換で熟語の読みを問い、制限時間内に正答できなければ配信を止める「配信終了漢字クイズ」（#293）を、3段階に分けた。段階1（#300）は問題集と出題の演出、段階2（#301）はチャットでの回答の判定、段階3（#302）は時間切れでの配信の停止である。

## 問題は自前の問題集だけから出す

LLM や辞書（読みの付いた単語の一覧）からその場で問題を作る案は採らなかった。段階3で正答の判定が配信の強制終了に直結するため、読みの誤り（正しく答えたのに不正解になる・答えが一意に決まらない）を事前に人の目で潰す必要がある。そこで問題集をリポジトリに JSON で持ち、形の誤りはテストで止め、中身は配信者が確かめる。下書きを LLM に作らせることは妨げない。

## 級は問題ごとに手で付ける

漢検の級別の漢字表は、機械で読める公開データが見つからなかった。10級〜5級は学年別漢字配当表と対応するが、4級以上は協会独自の割り振りである。見つかった唯一のデータ（fosskers/kanji）は GPL3 のため取り込めない。そこで級は推定させず、問題集が問題ごとに持つ。

## 問題の級は、字の級と読みの級の高いほうにする

LLM の下書き（48問）を、漢検協会の「漢字ペディア」と協会の資料で裏取りしたところ、級の誤りが5件、読みの漏れが7件見つかった（2026-10-10）。級の誤りのうち4件（境内・仮病・素直を6級、納屋を5級）は、字そのものの級は合っていたが、読み（ケイ・ダイ・ケ・ス・ナ）が中学・高校で習うもので、漢検ではその級で出題されないものだった。「熟語の中で最も上の級の字」だけでは拾えないので、読みの出題される級も見る約束にした。誤りの問題は、同じ級の読みが1つしかない熟語に差し替えた。読みが複数ある語（一日・黄色など）は、辞書の見出しにある読みをすべて正解に入れて残した。

そのうえで、級を決めるのは先頭の読み（想定する読み）だけにした。黄色の「こうしょく」のように、ほかの読みには級より上で習うもの（黄のコウは中学）がある。それを正解から外すと、知っている人が正しく答えて不正解になり、強制終了に直結する害のほうが大きい。逆に、ほかの読みに合わせて級を上げると、想定する読み（きいろ）が級に対してやさしすぎる問題になる。そこで、2つ目以降の読みは正解として受け付けるためだけに持ち、級を決めないことにした（PR #303 のレビューで指摘を受けて明文化）。

## 級の一覧と問題集は src/ に置き、Worker からも読む

問題を選ぶのは Worker（段階2で判定もする）、級を「漢検準2級」と出すのは合成ページ、級を選ぶのは管理画面で、3か所が同じ級の一覧を要る。2か所に書き分けると食い違うので、`src/kanji-quiz/grade.ts` と `problems.json` を Worker からも読む（ポモドーロの `phase.ts` と同じ例外）。

## チャンネルポイントのトリガーにだけ置く

視聴者がポイントを払って出題させるものなので、ほかのきっかけ（レイド・キーワードなど）には置かせない。ツイスターがレイドだけに限っているのと同じ形で、保存時に拒み、照合で見つかったら投げる。

## 制限時間は熟語が出たときから数える

熟語は奥から近づいてくるあいだも読めるので、近づき終えてからではなく、出たときから数える。長さは定数（15秒）で持ち、設定にはしない（段階2で判定の締め切りにも使うため、場面の計算と同じ `scene.ts` に置く）。

はじめは30秒で、熟語は最初の3秒で近づき終えていた。実際に流すと30秒は間延びし、3秒で寄り切る動きは速すぎたので、制限時間を15秒に縮め、熟語は制限時間のあいだ一定の速さで近づきつづけて時間切れで等倍になるようにした（2026-10-10）。迫ってくる動きそのものが残り時間を感じさせる。

## 回答の判定は市町村紹介のクイズの形をなぞる（#301）

出題と最初の正解者は D1 の `kanji_quizzes` に持ち、正解者は1つの文（RETURNING）で決める。判定を AlertChannel に持たせない（配送者であって判定者ではない）のも、照らす処理の失敗を投げずに記録して Webhook のほかの処理を続けるのも、市町村紹介のクイズ（#251）と同じ理由である。

照合は、前後の空白を除きカタカナをひらがなに直してから、問題集の読みのいずれかと完全一致にした。部分一致・ローマ字・漢字まじりは受けない。段階3で時間切れが配信の停止に直結するので、緩く受けて誤って正解にするより、問題集の読みを漏れなく持つほうで守る（読みの漏れは前の節の約束で潰す）。

Webhook がチャットの全件で D1 を読まないよう、発言が問題集のどれかの読みと一致するときだけ D1 を読む。issue には「受付中の出題があるときだけ読む」と書いたが、受付中かどうかを D1 の外（KV など）に持つと書き込みが増え、読み違いの余地もできる。問題集の読みと一致しない発言は、どの出題に対しても正解になりえないので、この絞り込みで判定は変わらない（市町村紹介が「都道府県が1つだけ書かれた発言」で絞るのと同じ考え方）。

## 出題の行は、合成ページが流しはじめたときではなく Worker が選んだときに入れる（#301）

issue では市町村紹介と同じく「合成ページが流しはじめたときに行を入れる」としていた。しかし「同じ配信で出した問題を選ばない」判定をその行で行うと、交換が続いて合成ページの待ち行列にある問題は、まだ行が無いので「出した」に数えられず、同じ配信で同じ問題が重なりうる。そこで Worker が問題を選んだら、押し出す前に行を入れ（受付期限は空のまま）、合成ページが流しはじめたら `POST /api/overlay/kanji-quiz/open` で受付期限を書く形にした（配信者に確認して決めた。2026-10-10）。合成ページからは出題の識別子だけを受け取り、熟語は受け取らない（行の無い識別子は404）。

回答を受け付けるのは、流しはじめてから級を出し終えた（熟語が出た）ときから、制限時間に遅れの余裕（2秒）を足したところまで。熟語が出る前の回答は当てずっぽうなので受けない。合成ページも、熟語が出てから制限時間のうちに届いた正解者だけを出す。

試し再生で出した問題も「同じ配信で出した問題」に数える（配信中の試し再生も OBS の画面に映るため。配信者に確認して決めた）。配信していないときは「同じ配信」が無いので外さない。行は同じ配信の判定に使うので、長い配信でも足りるよう7日残す。選べる問題が尽きたときは、はじめは黙って重複させずに失敗として記録していたが、級ごとの重みにしたときに一巡させる形へ改めた（下の「出題の割合は級ごとの重みで持つ」）。

## 時間切れで配信を止める（#302）

### 時間切れは Worker が決め、時刻は Durable Object のアラームに預ける

合成ページの数え方で止めると、合成ページを2つ開いていたときに2回止めうるうえ、合成ページの時計とチャットの判定がずれる。そこで、合成ページが出題を開いたときに受付の締め切り（`closes_at`）を広告の終了のタイマーと同じクラス（`AdBreakTimer`）の別のインスタンス（名前 `kanji-quiz`）へ預け、締め切りに D1 を読んで正解者がいなければ停止を始める。締め切りのあとは回答を受け付けないので、そこで「正解者なし」が確定する。新しい Durable Object のクラスを足さないのは、ポモドーロと同じく PR のプレビューのビルドが失敗するためである。アラームはインスタンスごとに1つなので、判定と停止の時刻を一覧で持ち、いちばん早い時刻に仕掛ける。

### 停止の状態は D1 の行に持ち、取り消しと停止をそれぞれ1つの文で決める

停止を始めた（`stop_at`）・取り消した（`stop_cancelled_at`）・止める命令を送った（`stop_sent_at`）を出題の行に持ち（マイグレーション 0032）、それぞれ「まだ書かれていない行」だけを書き換える1つの文（RETURNING）で行う。取り消しと停止が同時に来ても一方しか通らず、同じ出題で2回止めない（方針7）。猶予が尽きたあとでも、命令を送る前（アラームの遅れのあいだ）なら取り消せるようにした。止めないほうに倒すためである。

### 猶予を知らせられなければ止めない

猶予の知らせ（`type: stopping`）を合成ページと下部バーへ押し出せなければ、始めた停止（`stop_at`）を戻し、止める時刻を仕掛けずに失敗として記録する（戻さないと、あとで下部バーから「取り消せた」ことになってしまう。PR #305 のレビューで指摘を受けた）。配信者が猶予を見られず取り消せないまま配信が止まる害のほうが、止まらない害より大きいためである。

### 猶予は時刻ではなく長さで送る

合成ページと下部バーは、知らせが届いた時刻から自分の時計で残り秒数を数える。配信者のPCの時計が Worker とずれていても、数え違えないようにするためである（届くまでの遅れのぶん、画面の数え終わりは実際の停止よりわずかに遅れる）。

### 取り消しは出題を指定しない

下部バーの取り消しボタンは、猶予のあいだの停止をすべて取り消す（`POST /api/admin/kanji-quiz/stop/cancel`）。どの出題かを画面に持たせると、開き直したときに押せなくなるためである。猶予は10秒なので、2つの出題の猶予が重なることはまずない。

### 試し再生は止めないが、猶予と取り消しまでは同じ道を通す

試し再生の出題は行に `rehearsal` を持ち、Worker は猶予を知らせるが止める時刻を仕掛けない（鍵の確保も通さない）。猶予の演出と下部バーの取り消しボタンは本番と同じ道を通るので、配信の前に試し再生で一通り確かめられる。

### 止めるのは裏方のページで、受け取る裏方がいなければ記録する

Twitch の API には配信を終わらせる手段が無いので、裏方のページ（`?stop=true`）が OBS WebSocket の `StopStream` を送る。OBS のつなぎ先は画面の取り込みと同じ設定を使う（入力欄を増やさない）。配送先（`AlertChannel` の目印 `streamStop`）は、この命令だけはすべての接続ではなく送れた1つにだけ送り（裏方を2つ開いていると StopStream が2回送られ、2回目が失敗として記録されるため。PR #305 のレビューで指摘を受けた）、受け取る接続が1つも無ければ409を返し、Worker が `kanji-quiz-stop-failed` として記録する。ほかの押し出しのように黙って落とすと、配信が止まらなかったことに誰も気づけないためである。裏方は止められたか（止められなければその理由）を `POST /api/overlay/kanji-quiz/stop/result` で知らせ、理由があれば同じ種類で記録する。

### 下部バーは開き直したときに猶予を読み直さない

下部バーは合成ページと同じ押し出しの経路で猶予を受け取り、開いたときに読み直す経路は持たない。猶予は10秒で、そのあいだに開き直すことはまずないためである。押し出しが切れているあいだは、取り消しボタンが出ないことに気づけるよう下部バーに理由を出す。

### 合成ページは停止を予告しない（2026-10-11）

はじめは猶予のあいだ合成ページに「配信終了まで ○秒」の帯を出し、数え終えたら「配信を終了します」、取り消されたら「取り消されました」と出していた。配信で試した配信者の判断で、予告なしにいきなり配信が終わるほうが面白いので、本番では帯を出さないことにした。猶予（10秒）と下部バーの取り消しは残す。正答の判定の誤りなどで止めたくないときに、配信者だけが止められるようにするためである（猶予ごとなくす案は、取り消せないまま止まる害が大きいので採らなかった）。取り消されたときも、視聴者には予告を見せていないので何も出さない。試し再生だけは、止めずに済んだことを確かめられるよう、本来止める時刻に「試し再生なので配信は止めません」を出す。

## 出題の割合は級ごとの重みで持つ（2026-10-10）

はじめはトリガーの動作が級を1つだけ持ち、その級からだけ出していた。問題集は級ごとに4問しかないので、同じ配信で4回交換されるとその級を出しきり、5回目からは毎回失敗になっていた（実配信で「全部出し終えるとエラーになる」と報告を受けた）。そこで動作は12の級すべてに重み（0〜100の整数）を持ち、級が選ばれる確率を「その級の重み ÷ 重みの合計」にした。合計100の%で入れさせる案もあったが、合計を合わせる手間が要るので、重みを入れて画面に%を添える形にした（配信者に確認して決めた）。

出しきったときは、出し終えた級を外して残りの級の重みで選び直し、重みのある級をすべて出し終えたら、出した回数がいちばん少ない問題から選び直す（一巡する）。失敗にはしない。視聴者がポイントを払って交換したのに何も起きないほうが、同じ問題が2巡目に出るより害が大きいためである（配信者に確認して決めた）。そのため出しきったときの409と素材の箱への知らせは無くなった（知らせの種類 `failure` は合成ページの読み取りに残っているが、いまの Worker は押し出さない）。試し再生は見栄えを確かめるためのものなので、級を1つ選ぶ形のまま、その級だけを出す重みで同じ選び方を通す。

級1つだけで保存されていた動作（`{ type: 'kanjiQuiz', grade }`）は、読み出しのときにその級だけ重み1として読み替える（`worker/alert-config.ts` の `withKanjiQuizWeights`）。古い形は読み替えずにエラーにする方針だが、そうするとトリガーの画面ごと読めなくなり、ほかのトリガーまで KV から入れ直すことになるため、配信者の了承を得て例外にした。保存では古い形を受け付けないので、次に保存すれば新しい形になる。
