# 作業机（素材の種類 `taskDesk`）

作業配信で、視聴者は見ているだけになりがちだった。勉強配信でよく使われている形にならい、視聴者がチャットで自分の作業を宣言すると配信画面の「作業机」に名前と作業が並び、終えたら祝われるようにした（issue #207）。

## 組み込みのコマンドにする

チャットのコマンドは、それまで配信者が管理画面で登録したものだけだった（`worker/bot-config.ts` の `EMPTY_CONFIG`）。作業机は「登録しなくても動く」ことに価値があるので、`!task <作業>` と `!done` を組み込みのコマンドにした（方針1「既定を決め切る」）。

組み込みのコマンドは、登録したコマンドより先に見る（`worker/webhook-routes.ts` の `replyToChatMessage`）。同じ名前のコマンドを管理画面で登録できると、登録した応答が届かないのに保存は通ってしまうので、`task`・`done` という名前は保存の時点で拒む（`worker/bot-config.ts`。名前の一覧は `worker/task-desk.ts` の `BUILT_IN_COMMAND_NAMES`）。

作業机に並べるのに bot は要らないので、bot を接続していなくても宣言は残して押し出す。bot が要るのは、受け付けない理由を返すときだけである。うまくいったときは bot は何も返さない。作業机に出ることが返事になるうえ、視聴者が多い作業配信でコマンドのたびに bot が返事をするとチャットが埋まるためである。コマンドのたびに LLM も呼ばない（方針8）。

自動モデレーションで処分した発言は、トリガーやコマンドと同じく宣言として扱わない（処分の判定のほうが先にある）。

## 作業の文言は上限を超えたら受け付けない

作業の文言は40文字（`MAX_TASK_LENGTH`。絵文字も1文字と数える）を上限にし、超えたら切り詰めずに受け付けず、bot がいまの文字数を添えて理由を返す（方針4）。黙って切り詰めると、本人の書いたものと違う文が配信画面に出るためである。40文字にしたのは、追加したときの枠（560×640px）で2行に収まる長さだからである。数えるのは見た目の1文字（書記素クラスタ。`Intl.Segmenter`）ずつにした。UTF-16 の長さでは絵文字が2文字に、コードポイントの数でも家族や国旗の絵文字が何文字にも数えられ、見た目より早く断ってしまううえ、bot が返す「いまは◯文字です」が本人の数えた数と合わなくなる。

## 1人1行を配信ごとに持つ

宣言は新しい表 `task_declarations`（`migrations/0024_task_declarations.sql`）に、配信（`stream_sessions`）× 視聴者を主キーにして1人1行で持つ（方針8「発言ではなく人を貯める」）。`!task` を打ち直すと同じ行の作業と宣言した時刻を差し替えて完了を外す。

打ち直しで消える前の宣言の時間は、`prior_work_ms` に足し込んで残す（下の「みんなの作業時間」。issue #209）。

配信が終わったときは、宣言を次の配信へ持ち越さず片付けることにした（issue の「実装時に決めること」）。配信を主キーに含めておけば、片付けのために消す処理は要らず、作業机が読むのは配信中の配信の行だけになる。行そのものは消さずに残し、作業した時間の合計（issue #209）の材料にする。配信外の `!task` は残さず、bot が「配信中だけ使えます」と返す（黙って捨てると、視聴者は宣言できたと思ってしまう）。

Twitch は応答が届かなかった通知を再送する。宣言の行には宣言した発言のIDを持ち、同じ発言の再送では宣言した時刻も完了も変えない（再送のあいだに `!done` していたら完了が外れてしまうため）。`!done` は未完了の行にだけ完了の時刻を付け、もう完了している行には何もしない。ただしそれだけでは、処理済みの `!done` が再送されるまでのあいだに視聴者が `!task` を打ち直すと、新しい宣言が前の `!done` で完了になってしまう（PR #214 のレビューで指摘された）。そのため `!done` の発言IDに `:taskDone` を付けた鍵を `replied_chat_messages` に残し、鍵がまだ無いときだけ完了させる。完了と鍵の記録は1つの `batch`（トランザクション）で行う。鍵だけを先に残すと、完了の書き込みが失敗したときに鍵が残り、Twitch の再送で完了し直せなくなるためである。受け付けない理由の返信は、発言のIDに `:taskDesk` を付けた鍵で二重に送らない（`reserveChatReply`）。

## 並べ方と人数の上限

作業机には12人（`TASK_DESK_LIMIT`）まで並べる。並べ方は「未完了を宣言の新しい順、そのあとに完了を完了の新しい順」にした。あふれたときに完了した人から外れ、作業中の人が完了した人に押し出されないためである。「宣言か完了の新しいほう」で並べる案もあったが、完了した直後の人が上に来るぶん、作業中の人が下に沈んで画面から外れやすくなるので採らなかった。

完了した行は、次の `!task` か配信の終わりまで出しっぱなしにする。一定時間で消す案もあったが、何人が作業を終えたかが画面に残るほうが「みんなで作業している」感覚に合う。

## モデレーションで消された宣言は作業机から外す

荒らしが `!task` に書いた文言が、モデレーターに削除されたあとも配信画面に残ると困る（`docs/decisions/focus.md` の「モデレーションされたものは配信画面に残さない」と同じ考え方）。issue #202 の LLM の材料の問題とは分けて、作業机ではこの issue で扱った。

コメントビューアーのために購読している削除の通知（`channel.chat.message_delete`・`channel.chat.clear_user_messages`・`channel.chat.clear`）を受けたとき、発言の削除ならその発言で宣言した行、BAN・タイムアウトならその人の行、チャットのクリアなら配信中の全員の行を消して押し出し直す（`worker/task-desk-command.ts` の `applyModerationToTaskDesk`）。打ち直したあとに前の宣言の発言が消されても、いまの宣言は消さない（いまの行の発言IDと一致しないため）。終わった配信の行は消さない。通知の読み取りはコメントビューアーと同じ `toFeedItem` を使い（同じ通知を2か所で読み解かない）、ほかのチャンネルの通知（古い購読が残っているとき）では消さない。

印を付けて残す案（`removed_at`）もあったが、作業机の行は1人1行の「いまの宣言」であって履歴ではないので、消すことにした。

## 押し出しはアラートの配送先に相乗りし、作業机を丸ごと送る

変わった作業机は、アラートと同じ Durable Object（`worker/alert-channel.ts` の `AlertChannel`）から WebSocket で押し出す。新しい Durable Object を足すと PR ブランチのプレビュービルドが失敗するためで、BGM・作業ログと同じ判断である。受け取る素材が違うので、4つ目の目印（`taskDesk`）を付けた接続へだけ配る。

作業ログは増えた1行を送るが、作業机は**いまの作業机を丸ごと**送る。作業机は12人までと小さく、宣言の差し替え・完了・モデレーションでの削除と変わり方が多いので、差分の重ね方を合成ページに持たせるより、届いたもので置き換えるほうが食い違わない。合成ページは開いたとき・つながるたび・5分おきに `GET /api/overlay/task-desk` で読み直す。読んでいるあいだに押し出しが届いたら、読んだ結果は捨てる（押し出しのほうが新しいため）。

押し出しと理由の返信の失敗は投げず、`task-desk-push-failed`・`chat-reply-failed` として記録する。投げると Twitch が同じ通知を再送し、返信が二重になるためである。押し出しに失敗しても、合成ページは次の読み直しで取り戻せる。

## 祝うのは映しているあいだに完了した行だけ

合成ページは行をユーザーIDごとに使い回し、同じ宣言（宣言した時刻が同じ）が未完了から完了に変わった行にだけ祝いの印（`data-celebrate`）を付ける（`src/task-desk/entry.ts` の `justCompleted`）。開いたときにもう完了している人を祝い直したり、打ち直した人の前の宣言の完了を祝ったりしないためである。

素材のデザインはレジストリ（`src/<種類>/registry.ts`）に登録する形にせず、作業ログと同じく1つの見た目に決めた（方針1）。行の下には参加のしかた（`!task`・`!done`）をいつも出す。作業配信に来たばかりの人が、見ているだけでなく参加できると分かるようにするためである。

## みんなの作業時間（issue #209）

「今日この配信でみんな合わせて 14時間32分 作業しました」と数字で見せ、ひとりで作業しているのではない感覚を出すために、宣言から配信ごとの作業時間の合計と人数を出すことにした。作業机の素材・ダッシュボードの配信の詳細・チャットコマンドの差し込み語 `{worktime}` の3か所で見せる。計算は `worker/task-desk-worktime.ts` の `sumWorkTime` だけが持つ。

**1件の時間は「宣言から完了まで」とし、完了していない宣言はいまの時刻まで、完了しないまま配信が終わった宣言は配信の終わりで打ち切る。** 配信が終わったあとまで数え続けると、閉じ忘れた宣言1件で合計が膨らみ続けるためである。打ち切る時刻は `stream_sessions.ended_at`（配信中ならいま）で、それより後の完了もこの時刻で数える（配信の区切りが次の配信の開始で後から閉じられたときに、食い違いを出さないため）。

**打ち直す前の宣言の時間は、行の `prior_work_ms`（`migrations/0025_task_declarations_prior_work.sql`）へ足し込む。** 作業机は1人1行で、`!task` を打ち直すと宣言した時刻を差し替える（#207）。そのままでは前の作業の時間が合計から消える。宣言を1件1行で持つ形に変える案もあったが、作業机の「いまの宣言」を読むための形（主キー・モデレーションでの削除・再送の見分け）を作り直すことになるので、1人1行のまま足し込む列を1つ加えた（方針8「発言ではなく人を貯める」）。足し込む時間は前の宣言から完了まで（未完了なら打ち直した時刻まで）で、同じ発言の再送では足し込まない（`declareTask` の `ON CONFLICT` の中で、差し替える前の行の値から計算する）。この列を入れる前の行は0から始まる。

**合計は配信ごとの行へ書き込まず、読むたびに宣言の行から数える。** 1配信の宣言は多くても数十行で、読むたびに足しても D1 の読み取りの枠を食わない。配信の終わりに合計を `stream_sessions` へ書き込む案もあったが、配信の区切りを閉じる道は4つ（`stream.offline` の通知・`stream.online` の通知で次の配信が始まったとき・cron が次の配信を見つけたとき・cron が配信していないと分かったとき。`worker/stats-store.ts` の `recordStreamOffline`・`recordStreamOnline`・`recordLiveStream`・`closeOpenSessions`）あり、すべてに書き込みを足すと1つ漏れたときに合計が欠ける。宣言の行は配信が終わったあと書き換えない（モデレーションでの削除も配信中の行だけ）ので、あとから数えても同じ値になる。

**誰も宣言しなかった配信は 0 ではなく null にし、ダッシュボードでは「—」、作業机では合計の行を隠す（方針6）。** 「0分」と出すと「誰も作業しなかった」と「作業机を使っていなかった」が同じ見た目になるためである。宣言の行が無い配信を null にするので、作業机を入れる前の配信も「—」になる。

**作業机の素材は、押し出しを待たずに合計を進める。** 作業机に送る合計（`TaskDeskSnapshot` の `workTime`）には、読んだ時刻（`measuredAt`）と作業中の人数（`working`）を添え、合成ページは毎フレーム「読んだときの合計＋読んでからの経過時間×作業中の人数」を映す（`src/task-desk/entry.ts` の `workTimeText`。描画は経過時間だけから決める約束に合わせた）。分が変わるたびに Worker から押し出す案は、Durable Object のアラームと押し出しが分ごとに要るので採らなかった。合成ページの時計が Worker より遅れていても、合計は減らさない。

**配信者のポモドーロの作業時間は含めない。** ポモドーロは区間の記録を持たず（タイマーの開始と一時停止の時刻だけ）、含めるには新しい記録が要る。配信者も `!task` すれば視聴者と同じく数えられる。

**`{worktime}` はチャットコマンドの応答文だけで使える。** `{bgm}` と同じく、トリガーの文言で使えるようにするには `worker/alert-actions.ts` から `fillMessage` まで合計を渡す必要があり、変更が広がるので見送った。記録が無いときは無応答にせず「まだ作業の記録がありません」に置き換える（`{summary}` と同じ考え方）。保存の時点で見積もる長さは30文字（`MAX_WORK_TIME_TEXT_LENGTH`）で、それを超える文になったら送らずに投げる。
