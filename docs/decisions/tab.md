# タブの映像の判断の記録

Chrome のタブ1枚の映像と音を配信画面へ出す仕組み（issue #163・#164）について、なぜこの形にしたかを残します。いま守るべき約束は `.claude/rules/tab.md` にあります。

## OBS のウィンドウキャプチャをやめ、タブ単位で取り込む形にしました

それまでは OBS のウィンドウキャプチャで Chrome を取り込んでいました。次の3つの悩みは、どれも「ウィンドウ単位で取り込んでいる」ことが原因でした。

- Chrome を起動し直すたびに、ウィンドウソースを指定し直さないと認識されない
- 見せたいタブと見せたくないタブの切り替えが面倒
- 画面の一部分だけを見せたいときの調整が面倒（#166 で扱います）

そこで、Chrome 拡張でタブ1枚の映像と音を取り、合成ページの素材として映すことにしました。素材にすることで、OBS のブラウザソースは増えません（`docs/decisions/overlay-stage.md`）。

## 拡張はストリームIDを渡すだけにしました（のちに取り込みと送信も拡張へ移しました）

この節と次の2節は、はじめの形（#164）の記録です。のちに「取り込みと送信を拡張へ移しました」の節のとおり変えました。

拡張から直接 WebRTC で送ったり、WebSocket で中継先へつないだりする案もありました。採らなかったのは、**拡張にログインや鍵を持たせないため**です。

拡張がつなぐと、接続元が `chrome-extension://` になり、配信者のセッションを使えません。代わりに鍵を拡張に持たせるか、`worker/tab-routes.ts` の `Origin` の確認に例外を足すことになります。送り手を HDAD のアプリのページ（`/tab/`）にすれば、配信者のセッションがそのまま使えます。

拡張は `chrome.tabCapture.getMediaStreamId({ targetTabId, consumerTabId })` で、送り手のページを受け取り先にしたIDを取ります。このIDは受け取り先のタブでしか使えないので、漏れても他人には使えません。

## IDは送り手のページの URL の # で渡します

拡張から送り手のページへIDを渡す方法は、次の3つを比べました。

| 方法 | 採らなかった理由・採った理由 |
| --- | --- |
| ページへスクリプトを差し込む（content script・`chrome.scripting`） | フォークした人ごとに HDAD のドメインが違い、ドメインごとの権限が要る。拡張のオプション画面でドメインを入れてもらう手間が増える |
| `externally_connectable` | manifest にドメインを書く必要があり、フォークごとに manifest を書き換えることになる。拡張のIDも固定しなければならない |
| **URL の # を書き換える（採用）** | `chrome.tabs.update` で # だけを書き換えれば、ページは読み込み直されずに `hashchange` で受け取れる。ドメインの権限も設定も要らない |

送り手のページは「信頼する置き場所の、パスが `/tab/` のタブ」で探します。2つ以上見つかったら、どちらへ渡すかを決めずにバッジで知らせます。受け取ったページは、読み込み直したときに期限の切れたIDで取り込み直さないよう、読んだ # をすぐ消します。

## 信頼する置き場所は、拡張のダウンロードのときに Worker が書き込みます

はじめは送り手のページを「パスが `/tab/` のタブ」だけで探していました。PR #167 のレビューで、これでは別のサイトの `/tab/` が開いていたときにそこへIDを渡してしまい、そのサイトが映したいタブの映像と音を取り込めてしまうと指摘されました（IDは受け取り先のタブで使えるため）。

そこで、信頼する HDAD の置き場所（オリジン）を拡張に教え、そこにある `/tab/` にだけ渡すことにしました。置き場所はフォークした人ごとに違うので、教え方を次の3つから選びました。

| 方法 | 採らなかった理由・採った理由 |
| --- | --- |
| 拡張の設定画面で URL を入れて保存する | ビルドし直さずに変えられるが、設定画面と入力の検証を作ることになる |
| HDAD の `/tab/` を開いたままボタンを押して登録する | 入力が要らないが、別のサイトの `/tab/` で誤って押すとそこを信頼してしまう |
| ビルドのときに環境変数 `HDAD_ORIGINS` で渡す（PR #167 でいったん採用） | 画面も保存も要らないが、公開先（`workers.dev`）のアドレスにはアカウントごとのサブドメインが入り、リポジトリにも設定にも書かれていないので、ビルドの時点では分からない。配信者が手で書くと間違える（末尾の `/` だけでビルドが失敗した）。拡張を入れる PC ごとにリポジトリを置いてビルドする必要もあった |
| **アプリからダウンロードさせ、Worker が置き場所を書き込む（採用。issue #168）** | Worker は受けたリクエストの URL から自分の置き場所を正確に知っている。`GET /api/admin/tab/extension.zip` が、ビルド済みの拡張に置き場所を書いた `config.json` を加えて返すので、書き間違いが起きず、配信者はリポジトリもビルドも要らない |

拡張は押されるたびに同梱の `config.json` を読み（`extension/src/config.ts`）、読めないときはどこでも信頼する形に黙って倒さず、バッジで「ダウンロードし直してください」と知らせます。

## 取り込みと送信を拡張へ移しました

はじめの形では、配信者が `/tab/` を Chrome で開いたままにしておかないと、合成ページへ映像を中継できませんでした。実際に使うと、これは予想以上に不便でした。配信のたびに開き忘れ、誤って閉じると映像が止まり、タブが1枚余計に並びます。そこで、取り込みと送信を拡張の **offscreen document** に移し、`/tab/` は拡張を配って案内するだけのページにしました。

サービスワーカーは眠ると変数も映像も失うので、映像を持ち続ける画面として offscreen document（`chrome.offscreen` の `USER_MEDIA`）を使います。IDは `getMediaStreamId({ targetTabId })` で取り込む側を指定せずに取ると、同じ拡張の offscreen document で使えます。送るふるまい（`src/tab/sender.ts`・`peer.ts`・`capture.ts`・`socket.ts`）は送り手のページのものをそのまま使っています。

### つなぎ方は、配信者のセッションのままにしました

拡張が中継先へつなぐと接続元が `chrome-extension://` になるので、はじめは「拡張にログインや鍵を持たせない」ために送り手のページを置いていました。移すにあたって、次の3つを比べました。

| 方法 | 採らなかった理由・採った理由 |
| --- | --- |
| ダウンロードのときに鍵を発行して config.json に書く | 鍵がディスクに残り続け、失効や作り直しの仕組みが要る |
| offscreen document に `/tab/` を iframe で埋め込む | IDは拡張の画面でしか使えず、取り込んだ映像を別のオリジンの iframe へ渡せない |
| **拡張に置き場所への権限を与え、配信者のクッキーでつなぐ（採用）** | Chrome は、拡張が権限を持つサイトへの要求を同じサイトからの要求として扱うので、SameSite=Lax のクッキーが付く。ログインが切れれば普通につながらなくなり、拡張には何も残らない |

権限（`host_permissions`）はフォークごとに置き場所が違うので、`config.json` と同じくダウンロードのときに Worker が manifest.json に書き込みます。拡張を入れるときに Chrome が「このサイトのデータの読み取りと変更」の許可を求めますが、対象はその HDAD だけです。

WebSocket は GET なので、Worker は `Origin` も確かめます。パッケージ化されていない拡張のIDは読み込んだフォルダの場所で変わるので、manifest.json に公開鍵（`key`）を書いてIDを固定し、Worker はそのIDの `chrome-extension://` だけを送り手として受け入れます。秘密鍵は持ちません（ウェブストアに出さず、パッケージ化もしないため）。IDが1つなので、本番と開発サーバーの両方に向けた拡張を同時には入れられません。配信で使うのは1つなので、この不便は受け入れました。送り手のページはもう無いので、HDAD 自身のページからの接続も受け入れません。

### 映しているタブでもう一度押すと止めます

送り手のページには「止める」ボタンがありましたが、ページが無くなると止める場所が無くなります。止めるのは「映しているタブで、映したときと同じ操作をもう一度する」がいちばん分かりやすいので、そうしました。別のタブで押したときは、これまでどおりそのタブに切り替えます。映しているあいだはボタンに「ON」を出し、合成ページにつながっていない・中継先との接続が切れたなどは「!」と説明で知らせます。状態を出す場所が拡張のボタンだけになったためです。

### 2つの入口が同じモジュールを読み込まないようにしました

拡張はサービスワーカーと offscreen document の2つの入口を持ちます。両方が同じモジュールを実行時に読み込むと、ビルドが共有のファイル（チャンク）を作ります。Worker は決まったファイルだけを zip に詰めるので、共有のファイルが漏れて拡張が動かなくなります。そこで連絡の形はあて先ごとにファイルを分け（`offscreen-command.ts`・`offscreen-event.ts`）、片方は型だけを読み込みます。決まったファイル以外ができたら、ビルドを失敗させます。

## 拡張は TypeScript で書き、別にビルドします

拡張はビルドなしの素の JavaScript にもできますが、送り手のページと同じ受け渡しの書式（`src/tab/signal.ts` の `buildStreamHash`・`readStreamHash`）を2か所に書くと食い違うので、TypeScript で書いて同じファイルを読み込むことにしました（取り込みと送信を拡張へ移したいまは、送るふるまいそのものを `src/tab/` から読み込んでいます）。拡張のビルド（`npm run build:extension`）は本体の `npm run dev`・`npm run build` の前に自動で走り（`predev`・`prebuild`）、出力（`public/tab-extension/`）を本体が静的アセットとして配ります。Worker はそれを `ASSETS` バインディングで読んで zip にします。型チェックは `tsconfig.extension.json`（`@types/chrome`）で、`npm run type-check` に含めています。

ショートカットは manifest の `_execute_action` に割り当て、ツールバーのボタンを押したのと同じ扱いにしています。ボタンかショートカットで呼ばれたときだけ、そのタブを取り込む許可（`activeTab` と同じ扱い）が得られるためです。

## 連絡の中継は、手書きとは別の Durable Object にしました

中継の作りは手書きの `DrawChannel`（`docs/decisions/draw.md`）と同じで、中身を読まず、Hibernation API で受けます。それでも相乗りさせずに `TabChannel` を足したのは、**向きが違う**ためです。手書きは描く画面から合成ページへの一方向ですが、WebRTC の連絡は両方向に流れます（合成ページが名乗り、送り手が offer を送り、合成ページが answer を返す）。

両方向に配っても、**合成ページから届いたものは送り手にだけ配り、ほかの合成ページへは配りません**。オーバーレイ用キーは配信画面に映りうるので、キーを持つだけで他の合成ページへ offer を送り込めないようにするためです。送り手として受け入れるのは、配信者のセッションで守られた経路（`GET /api/admin/tab/socket`）だけです。

## 合成ページごとに接続を分けます

OBS の別のシーンにも同じオーバーレイを置くと、合成ページが2つ以上つながります。WebRTC の接続は1対1なので、合成ページは開くたびに名前（`viewerId`）を作って名乗り、送り手は名乗った合成ページごとに接続を1本持ちます。

## ICE の候補は集め終えてからまとめて送ります

映像は同じPCの中を流れるので、STUN も TURN も使わず、ICE の候補はすぐに集まります。そこで候補を1つずつ送る連絡（trickle ICE）は持たず、集め終えた SDP を1通で送ります。連絡の種類が減り、中継先を通る回数も減ります。

## 映像は H.264 を優先します

#163 の試作で、1920×1080・30fps を同じPCの中で送ったときの負荷と遅延を測りました（macOS 26.6.2・Chrome 154・OBS 32.1.2）。

| | VP8（Chrome の既定） | H.264 |
| --- | --- | --- |
| 遅延 | 約 97ms | 約 28〜52ms |
| 符号化 | ソフトウェア | VideoToolbox（ハードウェア） |
| 送り手のページの CPU | 72% | 8% |
| 取り込みで増えた CPU の合計 | 約 +110% | 約 +60% |

そこで `setCodecPreferences` で H.264 を先頭に並べています。H.264 で送れないブラウザでは、VP8 へ黙って切り替えずに失敗させます。負荷と遅延が大きく変わるためです。

## 接続が failed になったら作り直します

試作では H.264 の最初の1回だけ、送信が 0fps のまま止まって接続が failed になりました。原因は特定できていませんが、作り直すと映りました。そこで送り手は、接続が failed になったら閉じて合成ページに名乗り直しを頼み、名乗った合成ページへ作り直します。合成ページが閉じられていれば名乗る相手がいないので、作り直しは繰り返されません。

## 同じ映像は映し直させません

WebRTC は映像と音を別々のトラックとして届け、どちらも同じ映像（`MediaStream`）を指します。はじめは届くたびに合成ページの `<video>` にセットし直していたため、実機で「タブの映像を再生できませんでした: The play() request was interrupted by a new load request」が箱に残りました。2回目のセットで読み込みがやり直しになり、1回目の `play()` が中断されたためです（映像は2回目の再生で映っていました）。

そこで受け手のふるまい（`src/tab/receiver.ts`）は、いま映しているのと同じ映像を知らせ直さないようにし、合成ページ（`src/overlay/stage.ts`）も同じ映像ならセットし直さないようにしました。

## 取り込みには上限と一緒に下限も渡します

はじめは取り込みに上限（1920×1080）だけを渡していました。すると、配信者が置いた箱とタブの縦横比が違うときに、余白が黒く映りました。合成ページの `<video>` は `object-fit: contain` で背景を透明にしてあるので、黒い帯は映像そのものに入っていました。

Chromium の `media_stream_constraints_util_video_content.cc`（`SelectResolutionPolicyFromCandidates`）を読むと、タブの取り込みは、最小の幅・高さが 1 より大きく、最小と上限で縦横比が違うときだけ、上限の中でタブの縦横比のまま送ります（`ANY_WITHIN_LIMIT`）。それ以外は既定の `FIXED_RESOLUTION` になり、上限の大きさに固定して縦横比の違う分を黒い帯で埋めます。そこで下限に 2×2 を渡すことにしました。

受け取った側で黒い帯を見つけて切り抜く案は採りませんでした。毎フレームの処理が増えるうえ、映すページ自体が黒いときに誤って切り抜くためです。

## タブを閉じたら、エラーにせず何も映しません

映しているタブを閉じるのは、配信中に普通に起こる操作です。失敗として素材の枠に赤い表示を出すと、配信画面に映ってしまいます。そこで送り手は映すのをやめたことを合成ページへ知らせ（`stop`）、合成ページは透明に戻すだけにしました。状態は送り手（いまは拡張のボタン）にだけ出します。

## 音は映像と一緒に送り、OBS のモニターで聞きます

OBS のアプリケーション別音声キャプチャで Chrome の音を拾う案は、次の3つの理由で採りませんでした。

- Chrome 全体の音を拾うので、映していないタブの音が配信に乗る
- 音だけが映像より先に聞こえる（WebRTC の遅延のぶんずれる）
- タブを切り替えても音が一緒に切り替わらない

試作で、OBS のブラウザソースは操作なしで WebRTC の音を鳴らせること、取り込んでいるあいだは元のタブの音が Chrome から聞こえなくなることを確かめました。配信者は OBS のモニターで聞きます。合成ページで音を鳴らす素材はこれが初めてなので、「OBSで音声を制御する」を有効にする手順を `docs/guide/tab.md` と `docs/guide/overlay.md` に書いています。

## 試作で確かめたこと

本実装の前に、推測が混じっていた次の4点を実機で確かめました（結果は issue #163 のコメント）。

1. 普通のページを `consumerTabId` に指定して得たIDを、そのページの `getUserMedia` で受け取れる。IDは5秒後なら使えたが、10秒後は失敗した
2. OBS のブラウザソースでも WebRTC の映像を受けられ、遅延と負荷は上の表のとおり
3. 取り込み中のタブは、裏に回しても描画が間引かれない（`visibilityState` は `hidden` になる）
4. OBS のブラウザソースは、操作なしで WebRTC の音を鳴らせる

試作は localhost で確かめたので、https（Workers）のページでも同じに動くかは、本実装を配信で使って確かめます。
